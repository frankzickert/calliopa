# BO_0224_FEAT_extension-create-export-import

Status: completed

Requested: 2026-09-09, as the follow-up of `BO_0222`. **I also want the ability inside the app to add (create) new extensions, and to export and import existing ones.** User statement.

## Where This Starts

- **An extension is a subtree of Blocks, created today only from the CLI or by an agent.** The manifest is the root, every member `partOf` it (`extension-model.md`, Extension Subtree). A new one arrives through `kernel commit` from a checkout — *a new extension arrives by adding its `manifest.json` and members in the same commit* (`ui-kernel.md`, `BO_0094`; `internal/kernel/materializer/commit.go`) — or through an agent run under the `calliopa-extension.create-extension` skill, whose output contract is *exactly one open proposal group* holding manifest, members and relations. The code-registered schema requires only `id` of an `ext.manifest` and `ext.source` (`internal/domain/schema.go`); the rest is the skill's convention and the commit path's refusals: the manifest id must equal its directory under `src/extensions/`, a manifest the graph already holds cannot be re-added, a `dependencies` entry naming no manifest refuses the manifest, and a root-mapped source is refused for a non-elevated extension. `calliopa-video`, the only extension under *Yours*, was committed that way (`BO_0203`). A manifest with no `entrypoint` is a valid extension: `calliopa-base` and `calliopa-extension` *contribute nothing and scan as present* (`ui-shell.md`, `BO_0202`). The minimal extension is `manifest.json` alone.

- **The browser never writes `ext.*`.** The bridge's `write` verb refuses the reserved type prefixes `ext.`, `kernel.`, `agent.` and the relations `partOf` and `dependsOn` (`internal/kernel/serve/write.go`): *what it establishes is content and never code*. The review's `stage` verb refuses nothing by type (`stage.go`), but a group holding an extension member is established only through the kernel's confirmation page on its second origin — *Establish an extension change?* — never by the per-member fast path (`member_decision.go`, CCGW's `per_member_refused`). No shell surface stages extension members today.

- **The kernel already writes extension truth on a browser's request, as the signed-in human.** `POST /__kernel/extensions/{id}/state` and `/version` (`BO_0218_005`, `BO_0219_004`; `internal/kernel/serve/extensions.go`) resolve the session, refuse agent class `403 human_only`, refuse cross-origin, write `kernel.extensionstate` through an operation the CLI shares (`internal/kernel/extensions`), answer `202` and promote head after the answer. The shell's Scope Boundary names them as its one exception: *a deployment act of the signed-in human, never a review of code* (`ui-shell.md`). `kernel extension list|activate|deactivate|pin|unpin` is the CLI twin (`cmd/kernel/extension.go`).

- **The Extensions section after `BO_0222`** (draft, transferred 2026-09-09 as `BO_0222_001`– `_013`): two groups, *Core* (`bundled`) and *Yours* (`individual`); each row a small tree of its change documents; a `+` per row creating a change; a `funnel` on the header opening the status filter row beneath it; the section declaring `kind: "document"`; the shell's first icon table in `src/components/shell/icons.tsx` (Phosphor regular, inlined). The header's create idiom — a `createLabel` on the section — is still unused there. The extension view carries a control row — the activation toggle, the version selector, the *head is past the served pin* line, the build followed while a promotion runs — above a read-only owner document, and its inspector shows *Active*, *Required*, *Served version*, *Pinned at* with no actions.

- **There is no archive form of an extension.** Every transfer is a working tree plus a JSON sidecar applied through the commit path. The release export (`scripts/release-distribution.sh`, `BO_0090_002`) is `kernel checkout --members` at the accepted pin, pruned to `category: bundled`, written to `distribution/seed/`: `tree/` (the materialized namespace, an extension at `tree/src/extensions/<id>/`, `ui.shell`'s root-mapped files at the tree root), `members.json` (`{members: [{extension, nodeId, type, content}], extensions: [ids]}`, `internal/kernel/materializer/members.go`; the kinds in `TransferredMemberTypes` — block types, relation types, skills, intentions, migrations — never `ext.settings`, whose absence is the correct state to arrive in), `bundle.json` and the lockfile as provenance only. The seed hook (`distribution/seed/run.sh`) applies it by *checkout at head, remove what the bundle owns, copy the tree over, `kernel commit --members`* — truth on a fresh install, a proposal on an update — and the diff decides, so an up-to-date install produces nothing to commit. There is no `kernel export`, `bundle` or `pack`; `kernel import-app-content` is unrelated (a legacy instance's content). Blob-backed sources travel as bytes: checkout fetches and verifies them through the blob route, and the commit path uploads a binary file through `PUT /v1/blobs` and checks the server's hash against its own (`ui-kernel.md`, `BO_0093`; `binary-content.md`).

- **Bytes cross the kernel front in one shape.** `PUT /v1/blobs` takes a raw `application/octet-stream` body, hashed server-side, bounded by `BLOB_MAX_BYTES` (default 100 MiB, `413 blob_too_large`; `internal/httpapi/blob_routes.go`, `internal/config`). Nothing in the kernel parses multipart, the review routes read at most 8 MiB (`mutationGateLimit`), and no shell surface uploads or downloads a file today: the artifact's media family of the old shell was the only one (`BO_0164`), and `kernel diagnose` writes to the host volume and tells the operator to `docker compose cp` it (`ui-kernel.md`). No Content-Security-Policy header is set anywhere; the walls are the anonymous gate in prod, `refuseCrossOrigin` on every POST, the human-mutation gate and the `ext.` reservation.

- **Versions and pins.** A version is the manifest's `version` label at the subtree's last established state under it; the catalog is read from `createdDataRevision`, since a revision's `dataRevision` is re-stamped when a later write archives it (`BO_0219_001`). Committing an id the graph holds is an ordinary diff-driven update — unchanged files produce no statements, `ErrNothingToCommit` when nothing differs — and the range check (`extensionstate.CheckRanges`) refuses an activation or a flip that would serve a dependency outside its declared range. A version is chosen by bumping `version`.

- **The licences allow it.** `distribution/LICENSE-CORE.md` says the Core licence *does not cover the extensions distributed with Calliopa* — the shell, `settings`, `calliopa-base`, `calliopa-extension` are Apache-2.0, *you may use, modify and redistribute them* — and that *any extension You write* is the user's own. The Core alone may not be redistributed, and no export here touches it. Extensions are not signed: integrity is the content hash per file, and trust is the person who chose the file.

- **The sibling change** (`BO_0223`) shapes an update as a tab that shows the kernel's answer, offers *Review* and *Accept and promote* through the kernel's review and extension routes, and follows the instance to *serving*. Whatever an import looks like should look like that, because an import is an update of one extension from a file instead of a release.

- **Revised at the transfer, 2026-09-09.** Both premises moved the same day. `BO_0222` is completed and served at pin 123: the 45 change documents stand in the graph, the graph property is **`changeStatus`** (CCGW reads a `status` key as the revision's lifecycle) while tools and surfaces keep saying *status*, the icon table and the filter row exist, and `kernel import-changes --file` carries a repository change document into the graph. `BO_0223` is completed and served at pin 131: `GET /__kernel/session` answers `owner`, the update routes refuse anyone but the owner with `403 forbidden`, and the Update tab already links the confirmation for `accept` and follows a promotion — the shapes the import tab reuses.

## Intent

* A person looking at the Extensions section can start a new extension in one press: a name and a sentence of purpose, and the extension exists in the graph under *Yours* — opens as its owner document, takes a change document from the row's `+` at once (`BO_0222`), and is the subtree an agent run fills with code under the `create-extension` skill. Nothing to build, nothing to promote, nothing to review.

* An extension a person is looking at can leave the instance as one file: everything the graph holds of it at a chosen version — its sources, its vocabulary, its skills, its change documents — and nothing of the instance it came from.

* That file can enter another instance, or come back into this one at a newer version, from the same section: the person picks the file, sees what it would add or change, accepts, and switches the extension on. Code arriving from a file runs nothing until the owner has accepted it and switched it on, through the gate every activation runs through.

* The CLI can do each of the three, because the CLI is the recovery path for everything the kernel does.

## The Shape

- **Three exceptions of the same kind.** The shell's Scope Boundary (`ui-shell.md`) is revised to say: the extension view and the Extensions section ask the kernel to create an extension, export one, and stage and then accept an import — acts of the signed-in human on an extension as a whole, in the class of the activation toggle — and the shell still reviews no code: an import's diff is the kernel's summary, and its acceptance goes through the kernel's confirmation page like every extension group. Each act is one kernel operation shared by a route and a CLI verb, after `extensions.SetActive`'s shape.

- **Create.** The Extensions header gains a `+` — the section's `createLabel`, *New extension*, the idiom the Documents header has — beside the `funnel` of `BO_0222`. Pressing it opens a small form under the header, in the filter row's idiom: *Name* (the extension id) and *Purpose* (one sentence), *Create* and *Cancel*, nothing stored across reloads. Submitting calls `POST /__kernel/extensions` with `{id, purpose}`. The kernel resolves the session (agent class `403 human_only`, cross-origin refused), checks the id against the rule the skill states in words and nothing enforces today, made exact here — `^[a-z][a-z0-9]*([.-][a-z0-9]+)*$`, which every id the graph holds satisfies — refuses an id an established manifest carries as `409 extension_exists` (the required and elevated sets are taken by construction), and writes **truth** as the signed-in person in one `CREATE` statement, the seed's rule that no partial subtree is ever established (`BO_0086_004`): the `ext.manifest` — `id`, `version: 0.1.0`, `category: individual`, `capabilities: {renders: []}`, no `entrypoint`, no `dependencies` — and one `ext.source` member `docs/system/system.md` carrying `# <id>`, a `## Purpose` section with the sentence, and the prefix line left for the first topic (the docs convention: *a new extension names its own two-letter prefix in its `system.md`*, `BO_0201_001`), joined by `partOf`. The answer is the listing's row for the new extension; the shell re-reads the section and opens the extension tab, whose owner document shows the purpose. The extension is active in the state's sense and contributes nothing, so no promotion runs and the served tree is unchanged; the ahead dot appears because head is past the pin, and stays until the next promotion, as for any accepted change. `kernel extension create <id> --purpose <text>` shares the operation.

- **Export.** `GET /__kernel/extensions/{id}/export?revision=N` answers a zip — the kernel's `archive/zip`, no dependency — named `<id>-<version>.calliopa-extension.zip`, for any live human session, `403 human_only` otherwise, `404` for an unknown id or a revision not in the extension's catalog; without `revision`, the extension's newest established state. Inside, the release export's own shapes, cut to one extension:

- `extension.json`: `format: 1`, `id`, `version`, `category`, `revision` (the `dataRevision` exported), `exportedAt`, `release` (the kernel's `CALLIOPA_RELEASE_VERSION`), and the counts of files, members and documents. No principal, no instance name, no activation state, no pins: nothing the instance is, only what the extension is.

- `tree/src/extensions/<id>/**`: `manifest.json`, every `ext.source` at its path with its bytes — a blob-backed source fetched through the blob route and verified against its hash, as checkout does — and `contributions/<id>.json` per `ext.uicontribution`. A root-mapped source lands at `tree/<path>`, as checkout places it; only `ui.shell` has one, and no import accepts one (below).

- `members.json`: the sidecar for this extension alone, `extensions: [<id>]`, the `TransferredMemberTypes` kinds; `ext.settings` never, by the same rule as the release.

- `documents.json`: the extension's change documents (`BO_0222`), each as `read_document` answers it — title, status, blocks with their runs — because after `BO_0222` an extension's changes are documents, not members, and an export that dropped them would lose what the `docs/changes/` files used to carry.

- `LICENSE-APACHE` when `category` is `bundled`: the Apache text embedded in the kernel and pinned by the digest test that pins the distribution's copy (`BO_0204_001`), so an exported Core extension carries its licence as the release does. An `individual` extension is its author's; nothing is added. In the shell, the extension view's control row gains *Export* after the version selector — a link the browser downloads, carrying `revision` when the selector shows a pinned version, so a person pinned to `0.1.0` exports `0.1.0` — and the inspector gains an *Export* `button` action naming the same. `kernel extension export <id> [--revision N] [--out <path>]` writes the same file.

- **Import: stage.** The Extensions header gains a third control, Phosphor `upload-simple`, *Import extension*, opening the browser's file picker for `.zip`. The shell sends the bytes raw — `POST /__kernel/extensions/import?name=<file name>`, `application/zip`, the blob route's shape, bounded by `BLOB_MAX_BYTES`, `413` past it. The kernel resolves the session and refuses anyone but the owner (`403 owner_only`, decided below), reads `extension.json` and refuses by name: an unknown `format`; a manifest whose `id` differs from its directory; an id in the required set or the elevated set (`409 extension_reserved`: those move only with a release, `BO_0223`); any root-mapped file; a `category` of `bundled`, which is rewritten to `individual` and said so in the summary — a release of this instance never ships what arrived by file. Then it does what the seed hook does, in a scratch tree of its own: checkout of the namespace at head, `src/extensions/<id>/` removed if present, the archive's tree placed there, blob sources uploaded through the blob route with their hashes checked, and `kernel commit --members` in proposal mode as the signed-in person — the sidecar naming only this extension, so nothing else is retired — with the rationale *extension import: `<id>` `<version>` from `<file>`*. The `documents.json` entries ride in the same group as `document` nodes carrying `change: <id>` and their status, ids minted here, skipping a title the extension already has a change document for. The commit path's own refusals apply unchanged: a `dependencies` entry naming an extension the instance lacks refuses the manifest and names it; nothing differing answers `409 nothing_to_import` with the version the instance already holds. The answer is the group id and a **summary**: new or update (from which version to which), files added, changed and removed, members by kind, documents, migration files under `migrations/` with the sentence that they run when the extension is served, each dependency with the version the instance holds and whether it satisfies the range, and every per-file refusal with its reason.

- **Import: accept and serve.** The shell opens an `extension-import` tab — a `ui.shell` tab kind keyed by the group id, so a second press reveals it — showing the summary and *Accept*, which calls the bridge's `accept` for the group and lands on the kernel's confirmation page, *Establish an extension change?*, as any extension group does; *Reject* closes it through `reject`. A **new** extension is written into the state's `inactive` set by the import itself, beside the staging, so the moment the group is accepted it is established and off: nothing is built, the row appears under *Yours* struck through, and the tab's next step is *Switch on*, which is the activation toggle's route — the range check, the gate, `building` then `serving` — followed in the tab as the extension view follows it. An **update** of an extension the instance holds leaves its state alone; after acceptance head is past the pin and the tab offers *Serve now*, a promotion of head through the gate (the act the toggle performs, exposed as `POST /__kernel/extensions/promote` with the same refusals), or nothing, if the person prefers to pin later from the extension view. The tab ends on *serving `<id>` `<version>`* or on the gate's refusal in the kernel's words, the state written and the pin where it was, by `BO_0218`'s decision. `kernel extension import <file> [--truth]` shares the operation; `--truth` is the fresh-install case the seed hook already has.

- **Icons**, in the `BO_0222_008` table: `plus` for the header's create (the row's `plus` keeps its own name, *New change for `<id>`*), `upload-simple` for import, `download-simple` for export. Phosphor regular, unaltered, `aria-hidden` inside a named control.

- **What never travels.** Activation and pins (`kernel.extensionstate`), `ext.settings`, the connection store's values, provenance (who wrote what), proposal groups, and the lockfile. Declaration instances attached to a manifest by a non-`ext.*` type (`extension-model.md`, Declaration By Instance) are not in `TransferredMemberTypes` and do not travel here either — the same gap the release has, stated rather than closed.

### Why create is truth and not a proposal

- A proposal would send the person to a confirmation page asking *Establish an extension change?* for a name and a sentence they typed a second ago. The content is theirs, it runs nothing, it changes the served tree not at all, and it is the same act as switching an extension off — a kernel operation under the signed-in human. The seed's rule holds: one statement, no partial subtree.

- An import is different because its content is not the person's own words: it is code and vocabulary from a file, and the review path — a group, a confirmation, the gate — is what the graph has for exactly that.

### Why the zip carries the release's shapes

- The tree and the sidecar are already what every install applies and what every `kernel commit` reads, so the import is the seed hook's recipe over one directory, and the export is `checkout --members` cut to one id. A second format would need a second reader; this one has none.

- `documents.json` is the one addition, and it exists because `BO_0222` moved changes out of the tree.

### Out Of Scope

- A registry, a marketplace, a URL to install from, or signing and trust: an archive is bytes a person chose, and the kernel checks shape and hashes, not authorship.

- Importing or exporting more than one extension per file, and bundling dependencies: a dependency is imported first, and a missing one is named by the commit path.

- The Core and required extensions: they move with a release (`BO_0223`), and an import naming them is refused.

- Editing an extension's code in the browser, a proposal diff view in the shell, or any review surface beyond the kernel's confirmation page: the Scope Boundary's rule stands.

- Agent tools for export and import: an agent creates and evolves extensions through the proposal loop under `create-extension`, and the CLI verbs are for the operator.

- Exporting instance state: settings, secrets, accounts, activation, pins.

- Creating an extension with an entrypoint, a scaffold of views or a chosen prefix: the form takes a name and a purpose, and the first code is an agent's or the CLI's.

### Decided

Decided by the user on 2026-09-09, answering the five open points the first shape raised, each as recommended:

- **Create is truth, in one statement.** The kernel writes the manifest and `system.md` under the signed-in person with no confirmation round-trip. The confirmation would guard nothing: the write gate refuses `ext.*` because of code, and this is a name and a sentence. A staged group confirmed on the kernel's page was the alternative and was not chosen.

- **Import is the owner's alone.** It brings code and migrations from outside the instance, the class of act an update is, and `BO_0223` gates the update on the owner; the activation toggle stays every human's because it chooses among what the instance already holds.

- **Change documents travel.** `documents.json` carries the extension's change documents and the import lands them as documents of the extension, skipping a title it already has. Before `BO_0222` they were members and would have travelled as sources; the document form does not cost an extension its history.

- **An imported new extension arrives off.** Established and inactive on acceptance, nothing built until the owner presses *Switch on*, which runs the range check and the gate; an update of an already active extension offers *Serve now* instead. Active and served at once was the alternative and was not chosen.

- **The Core extensions export, with their licence.** Any extension exports; a `bundled` one carries `LICENSE-APACHE`. The import's refusal of the Core ids is what keeps a file from replacing a Core extension, and an author may fork the shell under a new id.
