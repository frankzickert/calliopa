# BO_0222_FEAT_extension-change-documents

Status: completed

It should be editable (by the user and the agents) like any other document, but it should have a status shown in the right panel when it is opened: idea, draft, ready, wip, completed, rejected — similar to those used in this repo. ## Where This Starts

- The Extensions section is a component body, not the uniform row (`src/components/library/extensions-section.tsx`, `BO_0201_005`, `BO_0202_003`): two groups, *Core* and *Yours*, each row the extension id, its version, the inactive strike-through, the pinned mark or the ahead dot, and a re-read control. A row opens the read-only owner document (`ui.shell:extension`, item `ext:<id>`). The section has no per-row control and no children; its only header control is the collapse toggle, because it declares no `createLabel` (`src/contract.ts`, `LibrarySection`). Nothing in the left panel is a tree.

- The Documents section is where creation lives today (`src/extensions/ui.shell/contributions.ts`): the header's `+` calls `POST /api/x/ui.shell/documents` with the title *Untitled document* and opens the answer as a `document` tab; `createDocument` (`src/server/documents/documents.ts`) mints the document and its first block in one `write` script. `listDocuments` answers every parentless `document` node sorted by title (`layout.md`, `CA_0011_002`), so whatever a change document is, the Documents section will list it too unless told otherwise.

- A document is a graph node of the `document` type `ui.shell` declares (`BO_0207_011`, `block-document-model.md`): `id` and `title` required, `intention` and `record` optional and unconstrained, `text` (roles `paragraph`, `h1`–`h3`, `quote`; runs with marks and a link) and `divider` its children. Widening a declaration with optional properties is non-breaking; a permitted set on a new optional property is enforced by CCGW's Validation on every write that names it (`property_value_not_permitted`, proven under `BO_0207_011`).

- The bridge's `write` verb (`ui-kernel.md`, `BO_0134_001`) lets the browser revise content nodes as the signed-in person, and refuses any target — a relation endpoint included — whose type is `ext.*` or that sits in an extension subtree through `partOf`. A document cannot be related to an extension's manifest from the shell, and an `ext.source` member cannot be written from the browser at all; a document can only *name* the extension.

- Agents reach documents through the kernel toolset (`ui-kernel.md`, `BO_0207_004`): `list_documents`, `read_document`, and `propose_document_changes` with replace, insert, remove and move — block gestures, staged into the run's group, never truth. There is no gesture for a document's own properties, so an agent cannot set a title or, tomorrow, a status; it proposes and the user accepts.

- The inspector renders what a view contributes in a fixed vocabulary (`src/components/shell/view-bridge.ts`): facts as `text`, `saveState`, `time`, `count`; actions as `button` and `toggle`. *The vocabulary grows by change when a view needs a shape it lacks. That cost is the point.* There is no choice-from-a-set control anywhere in the shell, and no icon: every glyph in the served shell is a text character (`+`, `↻`). The rule for icons is the user's from the old shell (`BO_0178`, `BO_0180`): Phosphor only, path data unaltered, never drawn by hand.

- An extension's changes today are files: `docs/changes/<id>.md` members with a `Status:` line, finished ones under `completed/`, written by the agent through the proposal loop and by nobody from the browser; the block editor cannot open them. The graph holds 44 of them at head: `ui.shell` 4 open and 33 completed, `settings` 4 completed, `calliopa-video` 2 open and 1 completed. The owner document renders them (`ui-shell.md`, `BO_0201_007`): the extension node's Changes section (status, id, title, intent; open first, then id descending) and a change node with the change's text and its tasks' states; the network builder (`src/lib/owner-docs/network.ts`) links every task to the change that enumerates it and the lines that carry it.

- The file form is a stated protocol in three places: `docs/process/change-process.md` in this repository (*a change process starts with a change document in `docs/changes/`*; *a change whose implementation lands in the graph carries its change document into the owning extension's own `docs/changes/`, same id, same `Status:`, same content*, `BO_0202_010`), the graph's `docs/system/system.md` fixed line (documentation lives as the extension's own `docs/` members, `docs/changes/` included), and the two skills that teach it — `calliopa-extension.create-extension`'s `docs` convention and `calliopa-base.working`'s `whereRequirementsLive` (`extension-model.md`, `BO_0201_001`). The protocol knows five statuses; `rejected` is a graph lifecycle word (`NodeRevision`, a proposal group's outcome) and new to change documents here.

- Section state is a record keyed `<ext>:<section>` in the workspace layout (`src/server/workspaces.ts`, `layout.md`): the collapsed state follows the workspace across reloads and devices. A section re-reads itself when a tab of its declared `kind` changes; the Extensions section declares none.

- A one-time transfer of content into the graph has a precedent: `kernel import-app-content` (`ui-kernel.md`, `BO_0207_005`) reads a source once and writes the instance's content as one accepted human-class mutation at one `dataRevision`, with a report the operator reads before the old form is dropped.

## Intent

* A change of an extension is a document in the graph — one form, whether the agent wrote it as a file yesterday or a person starts it from the left panel today. A person looking at an extension can start one in one press: a new document, opened in the editor, that is a change of that extension from the moment it exists. Writing in it, marking it, proposing changes to it from an agent run, deleting it, revealing its retired blocks — everything a document offers — works unchanged.

* The change carries a status from the repository's own vocabulary — `idea`, `draft`, `ready`, `wip`, `completed`, `rejected` — shown in the right panel while the document is open and changed there from a dropdown. The status is a fact of the document in the graph, so an agent reads it, and the left panel shows it.

* The left panel lists an extension's changes under the extension. What is finished stays out of the way: `completed` and `rejected` are hidden until asked for, and a filter control on the Extensions header reveals one toggle per status so a person chooses what to see.

* What a change *did* to an extension — the tasks transferred into its system topics — keeps living in those topics. Linking a change document to its tasks and topics in the graph is a later change; this one leaves the door open and closes nothing.

## The Shape

- **A change is a `document` with two more properties.** The `document` declaration (`ui.shell`'s `ext.blocktype` member, `BO_0207_011`) gains `change`, optional and unconstrained, carrying the id of the extension the document is a change of, and `status`, optional with the permitted set `idea`, `draft`, `ready`, `wip`, `completed`, `rejected`. A document carrying `change` is a change document; one without stays an ordinary document. No new node type, no relation: the editor, the assembler, the listing, the delete, the retired read, the proposals, the kernel's document tools and every test over `document` keep working, and the extension is named by its id because the write gate refuses a relation to its manifest and the id is what the section, the owner document and the kernel already key on. Validation refuses a seventh status at the graph, not in the shell's words. The revised declaration lands as a member of the same proposal through `kernel commit --members`, the way `BO_0207_011` staged it.

- **The existing members are converted once, `kernel import-changes`.** After `import-app-content`'s shape: the command reads every `docs/changes/**/*.md` member of every extension at head, converts each into a change document — the title from the file's `# ` heading (so `BO_0218_FEAT_extension-activation` stays the name a person and an agent know), `change` from the owning manifest through `partOf` (root-mapped members are `ui.shell`'s), `status` from the `Status:` line, the body as blocks: `##`/`###` headings as `h2`/`h3`, `>` as `quote`, a fenced code block as one `paragraph` whose single run keeps the lines with their newlines, every other line group as a `paragraph` **kept verbatim** — a live line's marker, state box and identifiers survive as text (`* `, `- [x] BO_0218_009 …`), so the parser's grammar still reads it should a later change want to; bold, italic, code and links become marks and run links — and writes them as one accepted human-class mutation under the operator's principal at one `dataRevision`, with a report per extension naming each file, its document id, its status and its block count. Idempotent: a member already imported (the report is kept beside the release pin as the app-content report is) is skipped on a re-run. The files are then retired from the tree as a proposal from a checkout with `docs/changes/` removed from every extension, accepted by the user from the CLI, so the conversion is two steps the operator reads between, as `BO_0207_017` was. A change whose file the network builder linked to tasks loses nothing: the tasks and their lines stay in the topics, and the builder stops yielding changes from members.

- **The protocol says documents.** The fixed line in the graph's `docs/system/system.md` and the two skills are revised: an extension's changes are `document` nodes carrying `change: <id>`, listed under the extension in the shell, created there or by an agent's tools, statuses as above; `docs/system/<area>/<topic>.md` members and the live-line protocol are unchanged. This repository's `docs/process/change-process.md` is rewritten the same way: this repository keeps its own `docs/changes/` files in git for the kernel and the distribution, and a change whose implementation lands in the graph carries its change document into the graph **as a document** of the owning extension — same title, same status, same content — staged by the agent through the document tools in the same run as the code, or written by the user, in place of `BO_0202_010`'s file copy. The `ui.shell.documents` skill member says where an extension's changes are found (`list_documents` filtered by `change`).

- **The `+` on the row.** Each extension row in the Extensions section carries a small icon button after the version and marks — Phosphor `plus`, regular weight — with the accessible name *New change for `<id>`*. Pressing it calls `POST /api/x/ui.shell/documents` with the title *Untitled change*, `change: <id>` and `status: idea`, and opens the answer as an ordinary `document` tab. `createDocument` takes the two optional properties and writes them in the same `CREATE`. An inactive extension keeps its `+`: a change to something switched off is a normal thing to write. The section body is `ui.shell`'s component, so the control is its own and not the header idiom's `createLabel`.

- **The Documents section lists no change documents.** `listDocuments` drops a document carrying `change` beside the ones an active `contains` points at, so a change appears once, under its extension. `list_documents` in the kernel toolset still answers every document, with `change` and `status` on each row, because an agent asked to work on an extension's change must find it.

- **Children under the extension.** The section's listing route (`GET /api/library/ui.shell/extensions`) answers, beside each extension, its change documents — id, title, status, last-changed time — read from CCGW as `listDocuments` reads, matched by `change`, never from the extension snapshot, which is code and pinned per head. Each extension row becomes a small tree: the row, then an indented list of its changes, each entry the status icon (below) with its accessible name, then the title, opening the document tab by its document identity, so a change already open is revealed rather than duplicated and the row reads current with the marker and `aria-current` like every entry. Order is the Documents rule, by title — which for the converted files is the id order the owner document used, since their titles begin with the id. A change of an extension the graph no longer holds is listed under a trailing group *Other* by the id it names, rather than vanishing. The section declares `kind: "document"` so a rename, a status change or a delete in the editor re-reads it, the same rule that keeps the Documents section current.

- **The filter.** The Extensions category header gains a second icon button beside the collapse toggle — Phosphor `funnel`, accessible name *Filter changes*, `aria-pressed` reflecting whether the row is shown. Pressing it shows or hides a row of six toggle icon buttons directly under the header, one per status in the vocabulary's order, each `aria-pressed` for whether changes of that status are listed, with the status word as its accessible name and title. The chosen set is stored in the workspace layout beside the section's collapsed state, under the section's `ui.shell:extensions` key, defaulted and back-filled like the other layout fields, so it follows the workspace across reloads and devices; a workspace that has never chosen shows `idea`, `draft`, `ready` and `wip` and hides `completed` and `rejected`. Whether the filter row is open is not stored: it is a gesture of the moment, and reopening the shell shows the header alone. When the set hides every change an extension has, the row shows no children and nothing says so; the funnel reads as active (a visible mark, not colour alone) whenever the set differs from the default, so a person wondering where a change went sees the filter before the list. An open tab of a hidden change stays open: the filter is the list's, not the workspace's.

- **The status in the inspector.** The block editor's inspector contribution, for a document carrying `change`, adds a `text` fact *Change of* naming the extension, and a status control. The action vocabulary gains its third kind, **`choice`**: an id, a label, the current value, the options each with a value and a label, and `run$(value)`. The shell renders a `choice` as a labelled native `select` in its own idiom, in the inspector and, should a view ever hand it to the dock, there too — one vocabulary, two surfaces, as the existing kinds. Choosing writes `status` on the document through the bridge's `write` verb as the signed-in person, one `SET` on the document node with the base revision compared first, so a stale editor answers a conflict and re-reads rather than overwriting; the inspector shows the new value when the write lands, and the section re-reads. Every transition is allowed from the dropdown: the protocol's rule that only the user promotes to `draft` and `ready` is honoured by *who* holds the dropdown — a person in the browser — not by refusing moves. The tasks a change transferred are not shown here; a later change links a change document to its tasks and topics in the graph and adds them as facts then.

- **Agents propose a status, they do not set one.** `propose_document_changes` gains a fifth gesture, `status`, naming the value, compiled into the run's proposal group as a `SET` on the document beside its block gestures; `read_document` answers `change` and `status` with the document. Accepting the proposal is what moves the status, so an agent claiming a change from `ready` to `wip`, or closing it as `completed`, is a proposal the user answers as any other, and an agent shaping an `idea` writes its blocks the way it does today. This is the protocol translated: the agent never establishes a status by itself. Creating a change is also an agent's gesture — `create_document` with `change` and `status: idea` — because the protocol now says an agent's change lands as a document, and a run that implements something must be able to write its change document without a person pressing `+` first; it stages, as every document tool does.

- **The owner document's Changes section reads the documents.** The extension node (`src/lib/owner-docs/render.ts`) lists the extension's change documents — status, title — each a link opening the document tab through `openTarget$`, open first then title descending, in place of the members it listed; the change node kind and `?path=` for a change go away with the files. Topics, questions and history are unchanged; the parser keeps reading `Status:` harmlessly, the builder keeps tasks linked to their lines and no longer to a change.

- **Icons.** The shell's first icons are one module, `src/components/shell/icons.tsx`, holding the Phosphor regular path data unaltered from `@phosphor-icons/core@2.1.1` (MIT), inlined rather than added to the lockfile as the old shell did (`BO_0178`), rendered `aria-hidden` at 16px inside a control whose accessible name is its label. The set: `plus` for the row's create control; `funnel` for the filter; and one per status — `lightbulb` for `idea`, `pencil-simple` for `draft`, `flag` for `ready`, `hammer` for `wip`, `check-circle` for `completed`, `x-circle` for `rejected`. The status icon is the same asset in the filter toggle, in the child row and beside the dropdown, so a status looks the same wherever it appears. Nothing is drawn by hand; an icon the family lacks is a reason to choose another Phosphor asset, not to approximate one.

- **The extension view stays read-only**, as `ui-shell.md`'s Scope Boundary fixes it: a change document opens in the block editor as a `document` tab, and nothing here edits code, reviews a proposal or promotes.

### Out Of Scope

- Linking a change document to the tasks and topics it transferred, and showing them in the inspector or the document. Decided by the user as the future: *at best, we link these in the graph*. This change keeps identifiers verbatim in the converted text so the link can be made later without re-reading anything.

- Block types the conversion would like — a code block, a list, a task line with a state — and any rendering of the live-line protocol inside the editor. Converted text is paragraphs; a richer document model is its own change.

- A status on ordinary documents, and a filter on the Documents section. `status` is declared on the type because the type is one, but the shell writes and shows it only for a document carrying `change`.

- Numbering. A change document has a title and an id; the repository's `BO_nnnn` sequence stays the git files' and the agent's habit, and nothing here mints one for a document.

- A dropdown anywhere but the inspector, and a status shown on the tab or in the editor's header. The inspector is where a document's own facts live (`document-panel.md`).

- This repository's own `docs/changes/` in git, which records the kernel's and the distribution's work and is not in the graph.

### Decided

Decided by the user on 2026-09-08, answering the open points the first shape raised:

- **Documents become the only form.** *The new documents should be the way to look at `docs/changes` members inside the graph.* The existing members are converted once and the file protocol is retired in the graph; a new change of any extension is a block document, whether a person or an agent starts it. Rendering members as read-only documents beside editable ones (two origins, one listing) and a document-as-view over a markdown member (a proposal per save) were the alternatives and were not chosen.

- **What a change transferred stays in the topics; linking is later.** *Inside the change tab there is everything that has been transferred from a change doc to the extension; at best, we link these in the graph for the future.* A change document's inspector shows its status and extension now; the change node with its tasks goes with the files.

- **A change is listed once, under its extension.** The Documents section never shows it; the kernel's `list_documents` answers every document so agents find them.

- **The default set shows `idea`, `draft`, `ready` and `wip`** and hides `completed` and `rejected`; an open tab of a hidden change stays open.
