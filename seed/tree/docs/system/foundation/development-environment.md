# Development Environment

## Development Environment

* Everything runs in containers, including the application. Editing application source reaches the running container without a restart or rebuild.

- Source reaches the container through Compose file syncing (`develop.watch` with `action: sync`) rather than a bind mount, so a daemon that cannot see the checkout still works.
- Vite watches by polling (`CHOKIDAR_USEPOLLING` and `server.watch.usePolling`) because synced writes do not reliably raise inotify events inside the container.
- Changing `package.json` or the lockfile rebuilds the image because a dependency change cannot be synced into a running container.
- Garage reads one configuration file and has no shell, so `garage.toml` is baked into `Dockerfile.garage` rather than mounted.
- `docker-compose.yml` defines the stack. `docker-compose.dev.yml` is the development override carrying sync rules and published ports.
- Environment variables use a `CALLIOPA_` prefix. `.env.dev.example` is committed; `.env.dev` is never committed.
- `pnpm run bootstrap` takes a fresh checkout to a working stack: it creates `.env.dev` from the example when absent, generates the secrets key when that file has none, starts Postgres and Garage, initializes the Garage cluster layout, creates the bucket and access key, writes those credentials into `.env.dev`, and applies migrations.
- Bootstrap is safe to re-run. Every step checks current state before acting, so a partially built stack is completed rather than duplicated or broken.
- `CALLIOPA_SECRETS_KEY` is retired with the shell's own secret store (`BO_0207_013`): the kernel's `kernel_secrets_key` takes its place and the application no longer requires the variable. Before it: `CALLIOPA_SECRETS_KEY` is generated once and never regenerated. Every secret [Settings](../../../src/extensions/settings/docs/system/secret-storage.md) stores is encrypted under it, so a re-run that minted a new one would make the stored secrets unreadable while reporting success.
- The `postgres` service runs `pgvector/pgvector:pg17-trixie`, because Honcho stores its vectors in Postgres. The extension has to arrive in the image: Postgres loads it from the server's own library directory, so the running image is what decides whether `create extension vector` can succeed (`CA_0022_001`).
- The `-trixie` variant is the one that may be used, and the plain `pgvector/pgvector:pg17` tag must not be. pgvector's default tag is built on Debian 12 while `postgres:17` is Debian 13, so adopting it moves an existing data directory backwards from glibc 2.41 to 2.36 and Postgres reports a collation version mismatch on the database. That is an index-correctness hazard rather than a cosmetic warning, because a text btree ordered under one collation is not guaranteed to answer correctly under another. The trixie variant shares the base `postgres:17` already had, so the collation version keeps agreeing (`CA_0022_001`).
- The swap was proven by hand on the real development volume, which is where the mismatch above was found: the stack came up on the new image without recreating `postgres_data`, every table's content and the whole migration ledger read back identical to the `postgres:17` baseline, the database's stored collation version still matched the one the operating system provides, and `create extension vector` succeeded (`CA_0022_001`).
- The `hermes` service runs the pinned agent image, mounts `hermes_data` at the Hermes home and `agent_config` for what the settings surface writes, and is published on 4503. Its healthcheck reads Hermes's own `/health` with `python3`, because that image carries no `curl` and because `/health` only answers once the entrypoint wrote its `.env` and `aiohttp` gave the API server an adapter — so the healthcheck is a real readiness probe rather than a liveness one (`CA_0022_002`).
- Its port is declared in the base file and stripped by the verification override, as every other service's is. The change document called it development-only, and this is the mechanism the repository already has for exactly that; `tests/behavior/compose-environment.test.ts` keeps the override honest by requiring every service in it to publish nothing (`CA_0022_002`).
- `CALLIOPA_HERMES_API_KEY` is a required Compose variable and `pnpm run bootstrap` generates 24 bytes as hex when it is absent, leaving an existing one alone: Hermes refuses a key shorter than 16 characters, and regenerating one would orphan a service already running against it. A checkout that predates the variable is completed by re-running bootstrap, which is what bootstrap being safe to re-run is for (`CA_0022_002`).
- `CALLIOPA_AGENT_TOOLS_TOKEN` is the agent's own `cak_` credential and is deliberately not generated: it is issued by `pnpm run client issue <name> --proposer` like any other machine caller's. Absent, the agent starts with no tools rather than failing to start, because an agent that cannot reach documents is still a working service to sign a subscription into (`CA_0022_002`).
- `honcho` and its `honcho-deriver` worker run the pinned `ghcr.io/plastic-labs/honcho:v3.1.0` against a `honcho` database in the shared Postgres, published on 4504. The image serves but does not migrate and refuses to start on an unmigrated database, so the service brings the schema to head before serving; the database itself is created by `pnpm run bootstrap`, because the service migrates but does not create (`CA_0022_003`).
- Both sit under a Compose profile, because Honcho refuses to start without an LLM key and a service that crash-loops is worse than one that is absent. `pnpm run dev` decides the profile from whether the `honcho` connection holds a key, reads it through the accessor every other server caller uses, and hands it to Compose in the environment of the process it spawns. It is never written to `.env.dev` (`CA_0022_003`).
- The application holds no control over the Docker daemon, so a key saved while the stack is up takes effect the next time `pnpm run dev` runs. That is the cost of the application not being able to restart its own services, and it is a once-per-machine event (`CA_0022_003`).
- `src/server/secrets.mjs` is ESM with a sibling `secrets.d.mts`, for the reason `api-clients.mjs` is: `pnpm run dev` reads the memory key under bare Node while the server is compiled TypeScript, and neither may hold a second copy of how a stored secret opens (`CA_0022_003`).
- The `memory service` gate proves the wiring and says what it does not prove. With no key stored the service is not in the stack at all, so a gate run never starts something the instance was not configured for. With a key stored through the store's own API it migrates its schema and serves, and the key reaches the container and neither a log line nor the environment file. That the key is one OpenAI would accept is not proven and could not be: Honcho asks nothing of it at startup, and the gate holds no account (`CA_0022_003`).
- `pnpm run dev` refuses when `.env.dev` is absent or missing a required variable. Otherwise it brings the stack up detached, reports one line per service, waits for every service to be running and healthy where a healthcheck exists, and only then attaches the watch loop. When a service does not come up, it prints logs and exits non-zero.

* Clearing development data never removes API clients or their credentials. An operator issues them deliberately and external callers hold tokens against them, so a cleared development database still authenticates the callers it authenticated before. Clearing is about content, not about access.
* An operation that clears development data reaches only the development stack's database. It must not be able to reach the verification stack or any other database.

- `pnpm run db:clear` empties the development database and leaves it migrated and immediately usable. It refuses an absent or incomplete `.env.dev`, brings Postgres up when it is down, and never asks before clearing, so another script or an agent can run it without a bypass flag and the refusal is the only guard.
- Clearing empties `workspace`, `process`, `publication`, `destination_binding`, `front_binding`, and the graph content tables; keeps `api_client`, `api_credential`, and `schema_migrations`; keeps the `calliopa` row in `graph_scope`; and returns `graph_data_revision.current` to `0`. `publication` is emptied by truncation rather than by deleting rows, because it is append-only and the database refuses to remove an entry; a development reset is a different act from rewriting history and says so by being wholesale. It does not touch `.env.dev`, Garage, or the Garage credentials.
- Every table is in exactly one class — cleared, preserved, or seeded — and `scripts/lib/db-clear.mjs` holds that classification alone. Deleting rows rather than dropping and re-migrating is what preserving API clients costs, and a table a later migration adds that no class claims fails the gate where it is introduced.

- A browser tab left open across a clear holds data revisions that no longer exist and is reloaded. Clearing is a development convenience, not a live-migration path, and does not need to survive an open session.
- The production stack is one of the databases clearing must not be able to reach. `scripts/db-clear.mjs` addresses `devCompose` alone and gains no target flag, environment override, or other way to be pointed elsewhere; reaching the development stack through that one helper is the whole of the guard, which is why the helper rather than a prompt is what keeps production safe.

## Implementation

- `docker-compose.yml` assembles the application, Postgres 17 as `pgvector/pgvector:pg17-trixie`, and a Garage v1.0.1 image carrying its baked configuration. It publishes only 4500–4502 with named data volumes and health-aware startup. `docker-compose.dev.yml` adds polling-based Compose sync for source/configuration and dependency-triggered image rebuilds; `.env.dev.example` defines the `CALLIOPA_` development contract (`CA_0002_003`).
- `migrations/0001_initial.sql` creates only the migration ledger. `pnpm run bootstrap` creates `.env.dev` when absent, starts Postgres and Garage, assigns the single-node Garage layout, creates `calliopa-assets` and `calliopa-app` credentials, writes them without exposing the secret, and runs each pending SQL migration transactionally. Re-running it preserves the layout, bucket and key and reports no pending migrations (`CA_0002_004`).
- `pnpm run dev` refuses an absent or incomplete `.env.dev` with bootstrap guidance, builds and starts the detached stack with `--wait`, reports every service state, prints logs and exits if any service is not ready, prints `http://100.114.122.91:4500`, and only then attaches Compose watch. The readiness parser and environment-file rules have Given/When/Then behavior coverage (`CA_0002_005`).
- Compose watch syncs changes under `src/` into the running application container and Vite's polling watcher serves them at `http://100.114.122.91:4500` within seconds without a container restart or image rebuild. A live edit-and-restore probe verified the path; no adjustment beyond `develop.watch`, `CHOKIDAR_USEPOLLING`, and Vite polling was required (`CA_0002_006`).
- `scripts/db-clear.mjs` carries `pnpm run db:clear`: it refuses through the shared environment rule, brings Postgres up, and runs `scripts/run-db-clear.mjs` in a one-off `app` container, which clears in one transaction. `scripts/lib/db-clear.mjs` holds the table classification and the delete order the foreign keys require, and `clearDatabase` leaves the transaction to its caller, so the same statements compose into the command and into a test that rolls them back. `resolveCaller` accepts a transaction handle beside the client, because resolving a caller only reads (`CA_0019_001`).
- Until `BO_0207_013`, `CALLIOPA_SECRETS_KEY` was a required application variable in `config/required-env.json`, is declared empty in `.env.dev.example`, and reaches the container through the Compose application environment, so `pnpm run dev` and `pnpm run db:clear` refuse a file without it through the rule they already share. `scripts/bootstrap.mjs` writes 32 bytes as hex into `.env.dev` when `findMissing` reports the variable empty or absent, which is the same rule the refusal is built on rather than a second reading of it. The verification stack mints its own per run in `scripts/lib/verify-stack.mjs`, beside the Garage credentials it already mints, so a gate run neither depends on a developer's key nor leaves one behind (`CA_0021_001`).
- `devEnvRefusal` in `scripts/lib/env-file.mjs` is the one environment-file rule `pnpm run dev` and `pnpm run db:clear` share, and `tests/behavior/env-file.test.mjs` covers an absent, an incomplete, and a complete file (`CA_0019_001`).
- `tests/integration/db-clear.test.ts` proves against real Postgres that clearing empties every content table, returns the data revision to `0`, keeps the seeded scope and the ledger, and leaves a preserved client's token authenticating. It clears inside a transaction it rolls back and then asserts the content is back, so the shared integration database keeps its rows (`CA_0019_001`). The same file reads the live table list from the catalog and fails when a table falls in no class or in more than one (`CA_0019_002`).
