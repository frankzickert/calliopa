# Verification

## Verification

* `pnpm run verify` is the authoritative change-completion gate.

- `pnpm run check` is the fast development check. It runs type checking, formatting validation, unit tests, and service-free behavior tests directly from the checkout with installed dependencies, explicitly reports every result, and exits non-zero if a check fails or cannot run. It does not install dependencies or start Docker, services, migrations, production builds, readiness probes, or browsers (`CA_0003_001`).
- `pnpm run verify` verifies a frozen dependency installation before invoking the complete fast check, then runs every applicable real-dependency integration test, migrations, the production build, the `/health` probe, Playwright browser scenarios, and the pinned Hermes image. Every gate is reported; failure or inability to run produces a non-zero exit (`CA_0003_002`).
- The completion gate runs against the production image in a uniquely named, isolated Compose project with no published ports, so it never collides with the development stack. Its teardown runs on success, failure, or termination and leaves nothing behind: `compose down` carries `--profile '*'`, so it reaches a service behind a profile as well as one in front of it, and `--rmi local`, so the images Compose built for the run go with it. The two images the gate builds under names of its own are removed by name, which `--rmi local` does not reach (`CA_0032_001`).
- A run killed before it reaches its teardown still leaves its containers, images and environment file. The file and the project share a token, so what any leftover belonged to is readable from its name.
- `pnpm run verify:clean` removes what earlier runs left, and reports what it removed. It reaches only this repo's verification runs, through the `VERIFY_PREFIX` every run name is already derived from rather than a second copy of the string: containers, volumes and networks by their Compose project label, images by repository name, and an `.env.verify-<token>` file. The `calliopa` development project, the production project, and other checkouts' projects on the same daemon are never matched (`CA_0032_002`).
- A verification project with a running container is named in the report and left alone, because a gate run takes minutes and several agents share the daemon. `--force` clears those too, for a run killed with something still up. A skipped run keeps its containers, volumes, network, images and environment file (`CA_0032_003`).
- `scripts/lib/verify-clean.mjs` chooses over listings and removes nothing, so what a cleanup would reach is provable without a daemon. `tests/behavior/verify-clean.test.mjs` covers the choice, which is the part that could destroy something: the development stack and a sibling checkout's runs are never selected, a working run keeps everything of its own, and `--force` selects it (`CA_0032_004`).
- `pnpm run verify` does not sweep leftovers itself. `verify:clean` is run deliberately, so a gate run never removes anything outside its own project.
- Tests use distinct unit, service-free behavior, real-dependency integration, and browser classes. Behavior scenarios use `Given`/`When`/`Then` naming. An integration suite is added only with a real case; a test that cannot reach its dependency fails rather than skips.
- Browser scenarios run in their own image, `Dockerfile.browser-tests`, joined to the verification stack network. Chromium reaches the application by a dotted network alias over plain HTTP.
- The whole `tests/` directory is copied into the browser image, so an image missing the suite cannot pass as an empty project.
- The first browser scenario proves the empty application serves a page and `/health` reports both dependencies reachable on desktop and mobile viewports.
- A behavior test asserts that the required-variable list, Compose application environment, and committed example environment agree, and that the verification stack publishes no ports.
- `pnpm run verify:publish` proves what needs a real destination, for the reason `verify:agent` proves what needs a real subscription: the verification stack has no channel credential and must not have one. It refuses on an unqualified machine rather than skipping, runs the `publish` vitest project against the development stack, and `tests/behavior/publish-gate.test.mjs` keeps it out of both gate lists so `pnpm run verify` can never reach it. [Publishing](../../../src/extensions/calliopa-video/docs/system/publishing/adapters.md) carries what it proves.
- The `hermes image` gate builds `Dockerfile.hermes` and exercises the pinned release against the running stack. It is the one gate that depends on an external distribution, so it is the one that will break on a pin bump; [Calliopa Agent](../agent/pinned-upstream-contract.md) carries what it proves and why each assertion is where it is. It starts no compose service and publishes no port, so the no-published-port rule stays true.
- Prettier formats the code. Markdown and `docs/` are excluded so automatic formatting cannot change commitment markers.

## Implementation

- `pnpm run verify` creates a uniquely named Compose project and environment file per run, publishes no ports, starts and initializes real Postgres and Garage, applies migrations, builds and serves the production image, and probes real readiness through the isolated network. It also gates frozen install, type checking, unit tests, and behavior tests, reports every gate explicitly, tears the run down as the Verification section describes, and leaves the development stack untouched (`CA_0002_007`).
- `tests/behavior/compose-environment.test.ts` mechanically keeps `config/required-env.json`, the base Compose application environment, `.env.dev.example`, and the no-published-port verification override aligned, so drift fails where it is introduced (`CA_0002_008`).
- `Dockerfile.browser-tests` contains the complete Playwright suite and Chromium runtime. Desktop and mobile projects run from the isolated verification network and prove that the empty home page renders accessibly while `/health` reports real Postgres and Garage readiness (`CA_0002_009`).
- Prettier formats repository code and configuration while `.prettierignore` protects Markdown and `docs/` commitment markers. The authoritative gate checks frozen dependencies, types, formatting, unit and behavior tests, real migrations and dependencies, the production build, readiness, and desktop/mobile browser scenarios; all foundation gates pass together (`CA_0002_010`).
- The `integration` vitest project runs `tests/integration/` against real Postgres. `pnpm run verify` builds the `Dockerfile` `base` stage as its own image and runs the suite in a container on the verification network, so the tests reach the unpublished database by service name and the stack still publishes nothing. The gate is reported between migrations and the production build, a database it cannot reach fails rather than skips, and `pnpm run check` stays service-free (`CA_0004_001`). Integration files share one database and one global data revision, so the project runs them one at a time in a single fork. The suite is handed the whole application environment the stack was started with, read from `requiredEnv.app` rather than a second list, because it exercises the same server modules the application does and those read one validated environment. Before that it received the database URL alone, and the first test to reach Garage failed on a missing variable — which reports a configuration gap as a broken test (`CA_0033_005`).
