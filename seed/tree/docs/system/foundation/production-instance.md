# Production Instance

## Production Stack

* A production instance of Calliopa runs on this machine beside the development stack, under its own Compose project with its own volumes, its own environment file, and its own secrets, answering at `http://100.114.122.91:4000`. It holds real production work; the development stack stays the place where content is created and cleared freely.
* Production runs the `production` image target. No Vite, no source syncing, no `develop.watch`: a code change reaches it only by rebuilding the image and recreating the application, which is a deliberate command and never a side effect of a development action.
* Production runs the full stack, mirroring development — `app`, `postgres`, `garage`, `hermes`, and `honcho` with its deriver behind the `memory` profile. Its agent, subscriptions, memory, and secrets are its own and are never shared with development's.
* No script in this repo may write or clear content in production. Content-writing scripts reach the development stack alone, by construction, and a behavior test proves no script can address the production project or its environment file.
* The production agent stages proposals and may not write truth. Its credential is issued with `--proposer`, so an agent run produces proposal groups a human answers per item rather than changes to production content.
* Deploying production does not gate on `pnpm run verify`. Running the quality gate before deploying is the operator's call.

- Issuing an API client is access, not content, and is deliberately allowed to reach production: the fixed line above already exempts clients and credentials from clearing, and production needs its own issued `cak_` credential for its agent. Structural and access-carrying operator commands get a production form; content-clearing ones do not.
- Production starts empty and nothing copies development content into it. The application is valid and renderable with an empty database, and every gate run already proves it.
- Every production service carries `restart: unless-stopped`, which covers a container crash and a Docker daemon restart while deliberately not restarting a stack an operator stopped on purpose.
- Surviving a host reboot needs the Docker daemon to come back, and on this machine it already does. `devstack-vscode-production` — the code-server container the work happens inside — is the only container on the daemon carrying a restart policy, and it returns after a reboot with nobody starting it. Production needs no mechanism that this machine has not already been running: no second daemon, no systemd distribution, no scheduled task.
- The reboot guarantee is proven by observing a reboot, not by reading the restart policy back. That observation is the operator's: an agent session runs inside the `devstack` container with the Docker socket mounted and no `/mnt/c`, so it can neither read nor change Docker Desktop's autostart setting, nor reboot the host, nor watch it come back. A test asserting the policy string would prove only that the string is present.
- Nothing here reserves machine resources or limits what may run beside production. Thirty-two cores and 31 GiB carry production, a development stack, and a verification run without contention worth designing around. Disk pressure is real and belongs to `pnpm run verify:clean`.
- The production project name is neither `calliopa`, which is the development stack, nor anything beginning with the `calliopa-verify` prefix, which `pnpm run verify:clean` selects on. Either collision would put production inside the blast radius of something built to destroy.
- Production runs unbacked until `CA_0035_BUILD_production-backups` lands. That is a stated decision, not an oversight.

- `production` names two unrelated things in this repo and the collision is accepted rather than renamed. Here it is the deployed instance: the `production` Dockerfile target, `docker-compose.prod.yml`, `pnpm run prod`, the `calliopa-prod` project. In [Episodes And Assets](../../../src/extensions/calliopa-video/docs/system/production/episodes-and-assets.md) it is the media work Calliopa exists to do: a production role, a production asset, `src/server/production/`. The convention that tells them apart is that the deployment sense is always spelled `prod` in a file, script, or project name, and the domain sense never is.

- `docker-compose.prod.yml` is the production override: `app` builds `target: production` and runs the standalone Node server, every service carries `restart: unless-stopped`, and there is no `develop` section. `.env.prod.example` is committed and `.env.prod` is not. The example carries ports 4000–4004 and leaves the Postgres password, database URL, Garage RPC secret, Garage admin token, secrets key, and Hermes key empty: development ships known values for several of those, and production mints its own instead (`CA_0034_001`).
- `scripts/lib/run.mjs` exports `PROD_ENV_FILE`, `PROD_PROJECT` (`calliopa-prod`), and `prodCompose` over the base plus production files, beside the existing `devCompose`. Those three names are the only way anything in this repo addresses production (`CA_0034_002`).
- `scripts/lib/bootstrap-stack.mjs` is the one bootstrap, taken over a `{ envFile, compose }` pair, and `pnpm run bootstrap` and `pnpm run bootstrap:prod` are that function and nothing else, so the two stacks cannot drift apart in what bootstrapping means. It generates every secret left empty, composes `CALLIOPA_DATABASE_URL` from the password it just wrote, and leaves an existing value alone in every case (`CA_0034_002`).
- `pnpm run prod` deploys: it refuses an absent or incomplete `.env.prod`, decides the `memory` profile from the stored Honcho key exactly as `pnpm run dev` does, builds and starts the stack detached with `--wait`, reports one line per service, prints the address, and exits without watching anything. `pnpm run prod:stop` brings the stack down keeping its volumes (`CA_0034_003`).
- `pnpm run migrate:prod` applies pending migrations to the production database, over a `scripts/lib/migrate-stack.mjs` the development form shares. `pnpm run client:prod` is `pnpm run client --prod` and administers API clients there. Both are structural or access-carrying and neither reaches content (`CA_0034_004`).
- `pnpm run client` passes `--build` to `docker compose run`, as `pnpm run db:clear` already did. Without it Compose builds only when the image is missing, so an operator would administer clients through the code as it stood at the last build. That was found by issuing production's credential against a stale image (`CA_0034_004`).
- `tests/behavior/stack-isolation.test.mjs` proves the isolation rule over the scripts themselves: no content-writing script names production by any handle, the clearing command addresses `devCompose` and carries no target flag, only the allowed scripts name production at all, and `PROD_PROJECT` is neither the development project read from `docker-compose.yml` nor anything under `VERIFY_PREFIX`. Adding `prodCompose` to `scripts/db-clear.mjs` fails two of them, which is what the test is for (`CA_0034_005`).
- `tests/behavior/compose-environment.test.ts` also holds production to the contract: `.env.prod.example` declares every required and optional variable, every production port is inside 4000–4020, differs from its development counterpart, and is distinct from the other production ports, and the override builds the `production` target, restarts every service, and carries no `develop` section (`CA_0034_006`).
- The production image carries the ESM server modules its operator entry points import. `scripts/` ships in that image and runs there under bare Node, but the production stage copies named paths rather than the checkout, so `src/server/*.mjs` was absent and both `pnpm run client:prod` and the memory-key probe inside `pnpm run prod` failed at import. `tests/behavior/production-image.test.mjs` reads the stage's `COPY` lines against every `../src/` import under `scripts/` and fails when one is not covered, because the alternative is finding out during an operator's first production command (`CA_0034_007`).
- Production was bootstrapped and deployed on 2026-09-04: it minted its own secrets, its agent's credential was issued against its own database as a proposer, all four services came up healthy, and `http://100.114.122.91:4000` serves the page while `/health` reports real Postgres and Garage reachability. Nothing was published in 4000–4020 before it, and the development stack kept answering on 4500 throughout with its own separate volumes (`CA_0034_007`).
- What the restart policy is proven to do stops short of a crash of the real application, and the reason is worth keeping. The four production containers carry `unless-stopped`, and this daemon honours it: a probe container that exits by itself was restarted four times before being removed. The running application cannot be crash-tested in place, because a container's PID 1 ignores every signal whose disposition is default, from inside its namespace and from an ancestor, and the one signal that does reach it — `SIGKILL` — is recorded by Docker as a manual stop, which deliberately suppresses the restart. So the guarantee rests on the policy being present, the daemon honouring it, and `devstack-vscode-production` returning across real reboots (`CA_0034_007`).
- Docker Desktop's autostart is on, confirmed by the operator, so the daemon returns after a reboot without anyone starting it (`CA_0034_008`). That is the last link the guarantee needed: the policy is on all four containers, this daemon honours it, the daemon comes back by itself, and `devstack-vscode-production` has been returning across real reboots on exactly that chain. Production itself has not yet been watched coming back — the machine's next reboot is when that is first seen, and a failure there is a finding to record rather than something to work around.
