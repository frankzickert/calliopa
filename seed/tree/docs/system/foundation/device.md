# Device

## Purpose

- The shell on the Android and iOS apps: the same tree at the same release pin, built for a
  WebView inside the native host, with its server half running in the page behind a port that the
  device cell answers. The cell, the host, the sandbox and the release are the fixed layer's
  (`calliopa-bootstrap`'s `docs/system/mobile.md`); this topic owns what the tree does so that every
  feature built for the web reaches the device with no device-specific code.
- This topic carries the shell's half of `BO_0319`, transferred 2026-10-01. The scaffold's changes
  take over its port and device-build lines under their own identifiers as each is transferred:
  `CA_0074` the port, transferred 2026-10-01; `CA_0075`, the extensions' server halves on the port
  and the rule, and `CA_0076`, the device build, both transferred 2026-10-01.

## Fixed

* No feature has device-specific UI code. A feature the device cannot run yet is shown
  unavailable, never re-implemented for it. User decision, 2026-09-30 (`BO_0319`).
* A capability without its key or without network stays visible, disabled, says why in words and
  offers to add the key. User decision, 2026-09-30.
* An extension proposal can be read on the device and is never previewed or promoted there.
* The instance's behavior does not change: `build` stays what the kernel runs, and the web adapter
  is today's routes.

## The Port

- `src/server/port/` is the one interface the server half reaches the world through (`Port`, `port.ts`): the environment the frame reads (`CALLIOPA_CCGW_URL`, `CALLIOPA_KERNEL_URL`, `CALLIOPA_KERNEL_SESSION`, `CALLIOPA_KERNEL_CALLBACK_SECRET`), the clock, record identifiers, constant-time comparison of secrets, scopes that carry a value through a call and everything it awaits, the agent configuration files, the graph gateway, the kernel, and outbound fetch. A scope is an interface of the port rather than `AsyncLocalStorage`, because a WebView has none; the request context and the branch and pin scopes are scopes of the port. `CA_0074_001`
- The port answers the graph gateway and the kernel by route, not by operation. `gateway(path, init)` reaches CCGW under `CALLIOPA_CCGW_URL`: `/v1/cypher/query`, `/v1/cypher/mutate`, `/v1/cypher/explain`, `/v1/head`, `/v1/schema` and `/v1/blobs/…`. `kernel(path, init)` reaches the kernel under `CALLIOPA_KERNEL_URL`: `/__kernel/…`, which serves sessions, acceptance, proposals, document tools, party records, state records, attachments and runs. The device cell answers the same routes behind the bridge (`calliopa-bootstrap`'s `BO_0319_053`), so no operation is described twice. Each call rejects when its address is not set, and never guesses one.
- The agent configuration files are named relative to the directory the application and the agent share: `read` answers null for a file it cannot read, `exists`, and `replace` writes a file whole beside it and renames it into place, making its directory first.
- The port says where the shell runs, `where`: `instance` from the Node adapter, `device` from the device adapter. What differs between the two is data a module reads by it — which parties a place lists (`settings`' `BO_0319_047`) — never a component of its own. `BO_0319_047`
- `#port` binds the adapter: `tsconfig.json` points it at `adapters/node-server/port.ts`, which `build`, the dev server and the suites resolve through `vite-tsconfig-paths`. The device build points it at its own (`CA_0076`). Nothing installs the port at start.
- `adapters/node-server/port.ts` answers the port on an instance with what the server half did before it: `process.env`, `node:crypto`, `AsyncLocalStorage`, `node:fs` under `CALLIOPA_AGENT_CONFIG_DIR` (default `/var/lib/calliopa/agent-config`, read by the adapter alone), and `fetch`. It reads every value when it is asked for rather than when it loads, so a suite that stubs the environment or `fetch` sees its own. `src/server/port/port.test.ts` holds the instance's answers to the port.
- The frame's own server modules reach Node, the environment and HTTP only through the port: `processes.ts`, `kernel-callback.ts`, `graph-gateway.ts`, `request-context.ts`, `workspaces.ts`, `registry.ts`, `ccgw/branch-scope.ts`, `ccgw/env.ts`, `agent/attachments.ts` and `agent/adapters.ts` under `src/server/`. The extensions' server halves still call what they called before, which the port leaves in place (`CA_0075_001`). `CA_0074_002`
- The frame's clients reach CCGW and the kernel only through the port: `ccgw/client.ts` (reads, the touched set, the reaching groups, the standing read, and the review verbs `write`, `stage`, `accept` and `reject`), `ccgw/blobs.ts`, `kernel/client.ts`, `kernel/extensions.ts`, `agent/bridge.ts` (the agent surface under `/__kernel/agent`, its event stream included), `session.ts`, `licence.ts` and `health.ts` under `src/server/` call `port.gateway` and `port.kernel` by route, and `src/routes/health/` probes `/healthz` and `/__kernel/agent/health` the same way (`reach(via, path)`); none calls `fetch` itself. A probe's failure names the route rather than the address. Verified 2026-10-02 by `typecheck` and by `check` failing on the same seven cases before the change and after it, the two others that failed once under load passing on their own. `CA_0074_003`
- Every extension's server half reaches Node, the environment and HTTP only through the port, as the frame's own modules do. The port carries what they needed: `randomBytes(size)` beside `uuid`, and `config(directory)`, the files of a directory shared with a service beside the application — `agent`, where the application and the agent meet, and `media`, where the media service's sign-in is handed over — whose locations the instance's adapter alone reads (`CALLIOPA_AGENT_CONFIG_DIR` and `CALLIOPA_MEDIA_CONFIG_DIR`, defaulting to `/var/lib/calliopa/agent-config` and `/var/lib/calliopa/media-config`). ## The Device Build

- The device build is `CA_0076`'s. It speaks the device cell's bridge as built (`calliopa-bootstrap`'s `docs/system/mobile.md`, *The Device Cell* and *The Native Host*): the `Cell` plugin's `call` takes one request — `protocol`, `method`, `path`, `header`, `body` or `bodyBase64` — and answers `protocol`, `status`, `header` and `body` or `bodyBase64`; a refusal by the routes is a response, and only the bridge's own error rejects. Bridge protocol 1.
- `adapters/device/port.ts` answers the port in a WebView. The graph gateway's and the kernel's routes are cell requests over the bridge (`Cell.call`), their paths unchanged and with no address: a request's headers travel as they are, a JSON body as JSON and any other as `bodyBase64`, and the cell's answer becomes the response an HTTP client would have read — a refusal by the routes a response, only the bridge's own error a rejection; an aborted caller stops waiting, since the bridge cannot take a call back. The two addresses read `cell:`, so the gateway reads as configured. The clock, record identifiers, random bytes and constant-time comparison are the platform's Web Crypto. A scope is a value set around a call and restored when it settles, held apart per request because the in-page server answers one request at a time; two runs of one scope racing inside one request are not carried apart. The configuration files are absent: `read` answers null, `exists` false, and a write is refused in words saying that sign-in to a subscription or a media service is an instance's and the app uses an API key. Outbound HTTP is Capacitor's native HTTP (`CapacitorHttp`, a text body; a binary request body is refused in words). `#host` is the native host's own definitions (`calliopa-bootstrap`'s `mobile/host/src/index.ts`: the `Cell` plugin, the page plugins and `CapacitorHttp`), so the page reaches the plugins through their one definition. `CA_0076_001`
