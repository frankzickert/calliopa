# Proposed Changes

## Proposed Changes To A Document

* A proposal group is staged against one document. A caller touching three documents stages three groups, because a group is against one document and cross-document atomicity is a promise nothing has asked for.
* An item is one of `replace`, `insert`, `remove`, or `move`, and each carries everything its operation needs.

- `replace` names a block and carries its proposed runs and role, staged as a candidate revision of that block. Accepting it establishes that revision, which is the same supersede an ordinary save performs.
- `insert` carries a new block's type, its content, and the position it takes as a sibling and a side, the shape `insertBlock` already accepts. Accepting it creates the block and the containment that places it as one item, which is why it cannot be half-accepted into a block no document contains.
- `remove` names a block and retires it on acceptance, closing containment and creating the `retired` relation in the same mutation, as retiring already does. It is recoverable from the retired blocks like every other retirement.
- `move` names a block and the position it would take. The key lives on the block, so a move is a revision of its content like any other and stages a candidate; accepting establishes it and containment is untouched.
- The order key is minted as an item is staged, against the document as it then stands, and each insert of a group counts the ones staged before it as siblings so two appends do not mint the same key. Minting at acceptance was the alternative and would have made the item's own content depend on when it was answered; a fractional key always sorts somewhere, so an item accepted after the document moved still lands where it said it would rather than nowhere.
- A stale item is one naming a block the document no longer contains. It is refused rather than applied to something else, because the block it was staged against is gone and a document that removed it is a conflict rather than a target.
- Containment validity holds after every acceptance order. Exactly one active containment parent per block is the invariant, and accepting an `insert` and a `move` against the same parent in either order leaves a valid document.
- Staging does not change the document and does not count as a change to it. A candidate revision is not part of the document until it is established, and a count that moved while nothing the reader can see moved would report a change they cannot find. Acceptance is what counts, as the write it performs.
- The ordered document read is unaffected by open items. It follows established truth, so a document with a group standing against it reads exactly as it did before the group was staged.

- `proposeDocumentChanges` in `src/server/documents/documents.ts` compiles the four kinds into one proposal-scoped mutation script and stages it through the kernel bridge's `stage` verb into a fresh CCGW group the shell names (`node:chg-<hex>`): a `replace` is a content `SET` on the block and lands as its candidate revision, a `move` the same on its order key, an `insert` a `CREATE` of the new block with the `RELATE` that places it — a relation anchored at the member's own candidate, which travels with that member at acceptance — and a `remove` a `CLOSE` of the containment, recorded as the group's close intent, with the `RELATE` of the `retired` relation. An item naming a block the document does not hold is refused as it is compiled rather than reaching the graph (`CA_0023_010`, `BO_0207_012`).
- `readDocumentProposals` derives the document's items from each open group's touched set and candidates, since a CCGW group names no document: a staged `CONTAINS` from the document to a node with no established truth is an `insert`, a staged `retired` from the document is a `remove`, and a candidate of a contained block that differs from its established content is a `move` when only the order key differs and a `replace` otherwise; a candidate equal to established content is the carry-forward anchor a staged relation hangs on and is not shown. A proposed block goes through `toBlock`, the same reader the document's own blocks go through, so a proposed block and a stored one cannot come to mean different things (`CA_0023_010`, `BO_0207_012`).
- An item's identity is the group, the kind and the members its decision covers, joined by `|`: one member for a replace, a move or an insert — the staged node — and two for a remove — the staged `retired` relation and the containment the close intent names, decided in that order so a block is never detached before it is recorded as retired. `answerDocumentProposal` issues one bridge `accept` or `reject` per member; a content member executes without a confirmation (`ui-kernel.md`, `BO_0207_001`), a member the kernel keeps behind its confirmation answers as refused rather than half-done, and CCGW's drift judgement on a rewritten block answers as a conflict against the item, with `override` the explicit accept-over. The group's state after the answer is read back so the caller learns it closed without asking (`CA_0023_010`, `BO_0207_012`).
- `GET /api/x/ui.shell/documents/[id]/proposals` reads them, and `propose` and `answerProposal` are commands on the existing command route. Proposing is a command like any other because an in-application proposer — an import, a bulk transform — reaches a document through the same transport its editor does (`CA_0023_011`). An agent proposes through the kernel toolset's document tools once `BO_0207_004` lands, staging into the run's own group.
- `tests/behavior/documents.test.ts` proves the lifecycle over the one graph: a staged group leaving the document and every revision exactly as they were, the items read back against their blocks with the proposed content, an insert accepted establishing the block with the containment that travels with it while the group stays open, and the replace rejected leaving the block as it was and closing the group (`BO_0207_012`). Before it, `tests/integration/block-documents.test.ts` and `tests/integration/document-api.test.ts` proved the shell's own lifecycle against real Postgres (`CA_0023_010`, `CA_0023_011`).

## Proposed Changes In Place

* The panel carries a `Show proposed changes` toggle. Turning it on shows the document's unanswered proposal items in place, each against the block it concerns.
* A proposed item is visibly not truth, visibly not the active block, and visibly not a retired block, and carries an accessible name saying what it proposes and by whom.
* A proposed item says who proposed it at a glance: the proposer's face on its left border and a ground and edge of the proposer's own, with the face's and the block's accessible names saying the same in words (`BO_0233`).
* An item is answered where it is read, by icons on its top edge: accept, reject, and — for a group of more than one — accept all.
* Editing a proposed item's text accepts it: once the reader's typing pauses, or they leave the text, the item is established and what they typed is made on top as the reader's own revision (`BO_0233`).
* Editing a proposed rewrite accepts it even when its block's words, role or place changed after it was staged, and makes what the reader typed on top: the reader's edit to the block since is replaced by the proposal's text and the typing, and the reader's standing stays theirs. Accepting such a rewrite from its ✓ or by *Accept all* is still refused in words, and so is a move, which takes no typing. User decision, 2026-09-11 (`CA_0042_001`).
* Moving a proposed item does not answer it: its new place is staged into its own group, and accepting it later lands it there (`BO_0233`).
* Accepting an item changes the document under the reader at once, because an accepted item is truth.

- The panel states how many items stand unanswered whether or not the toggle is on. A toggle that hid the fact that work was waiting would leave a reader with no way to learn it, and the count is a fact about the document like the change count beside it.
- The toggle is off by default and its state is the tab's, following the retired-blocks toggle exactly and for its reason: what it reveals is not the reading order, and the resting surface stays what the document says.
- A `replace` shows its proposed text beside the block's current text, because judging a rewrite means seeing it against what it replaces.
- An `insert` shows as a proposed block at the position it would take. A `remove` marks the block it would retire, which stays readable and editable meanwhile. A `move` marks the block where it now stands and says where accepting would put it, rather than drawing the block twice and asking the reader which one is real.
- The proposed treatment is distinct from the retired treatment and from the marked treatment [Command Mode](./command-mode.md#command-mode) uses, by more than colour, and it leaves no trace once nothing is proposed. Three treatments can share a surface only while a reader can tell at a glance which is which.
- Both toggles may be on at once. Retired blocks and proposed items interleave in the same reading order, each keeping its own treatment.
- A proposed item is not markable. Marking points at what the document says, and a proposal is not that yet. Until `BO_0233` it was not activatable either; a rewrite's and a new block's text now take the caret, and a change accepts them — the user's decision of 2026-09-10, that editing a proposal is answering it.
- While the reader types into a proposal nothing is accepted and nothing is handed over: the words show as typed, and the proposal keeps its face, its colour and the caret. Accepting turns the proposal into the block, with the block's look; when the first keystroke accepted, that happened under a typing hand, and the caret and the keystrokes typed meanwhile were lost (`BO_0233_014`). So the moment is the block editor's own save pause, or leaving the text: a reader still in it is given the block, activated where their caret is, before the proposal goes, and a reader who has left has what they typed written to the block without the caret being taken back. A new paragraph or a format is the block's to carry out, so it hands over at once. Answering a proposal from its icons while its typing waits keeps the typing if it accepts, and discards it if it rejects.
- A conflicted item says what moved and stays answerable, which is the per-item conflict [Graph Gateway](../content-store/proposals.md) reports. A stale item says its block is gone and offers `Reject` alone, so a group holding one can still close.
- CCGW judges a member's drift by revision: any revision of the block established after the group's base conflicts, including one that set only its standing. Accepting a rewrite or a move whose block moved only in its standing — its words, role and order at the base are what truth holds now — is done over the drift, and the reader's standing is written back afterwards, since a standing says nothing about the words. One whose words, role or place changed is refused in words (*made against an older version of the block … Reject it, or ask for it again*) rather than with the edit conflict's *reload*, which would change nothing — unless the reader typed into the rewrite, which accepts it over the drift (`CA_0042_002`). Found on `BO_0233`'s walk-through, when a pinned block's proposal could not be accepted (`BO_0233_011`).
- Answering an item is a saved operation and the undo keystroke does not reverse it, as it reverses no other saved structural operation. Rejecting is how a reader declines a change, and a rejected item is recoverable only as the record of what was asked for.
- Review happens in the document rather than in the inspector: [Workspace Shell](../workspace/layout.md) fixes what the shell renders from a view's contribution — a save state, a time, a count, a line of text, a button, and a toggle — and none of that expresses proposed text against current. Growing that vocabulary for one consumer would put a document's text in a drawer beside the document.
- A review tab of its own was rejected for the same reason: it judges a block's text away from the document that block lives in.
- A reader stages only a proposal's place. Until `BO_0233` the rule was *nothing here stages a proposal*; dragging a proposal, or moving it by the arrow keys, now stages its new order key into the group that holds it — a group an agent may have opened, which CCGW admits — and nothing else. The editor still answers what another caller staged, and a human editing a document still writes truth directly.

## Implementation

- The panel contributes the count of unanswered proposed changes as a fact and `Show proposed changes` as a toggle beside the retired one. The proposals are read whenever the document is, not only when the toggle is turned on, because the count is what tells a reader work is waiting while the items are hidden (`CA_0023_012`).
- `placeProposals` puts each item where it belongs: an item that would insert a block carries an order key and sorts among the blocks by the comparison siblings already sort by, and an item naming a block sits immediately after that block, because judging a rewrite means seeing it against what it would replace. An item whose block has gone since is drawn at the end rather than dropped, so a group the reader must answer never hides an item they cannot find. It is pure, so where an item lands is settled without a document (`CA_0023_012`).
- Until `BO_0233`, `.proposal-row` was solid where the retired row is dashed, took the accent edge where that one takes a muted one, and carried a standing label naming what was proposed and who staged it — *Proposed rewrite · staged by agent:hermes*. The label named the account every agent stages under (`BO_0206_008`), so a Claude run's rewrite read as Hermes's, and it was removed by the user's decision of 2026-09-10 (`CA_0023_012`).
- A proposed item is drawn as the block it would become (`ProposalBlock`, `src/components/views/proposals/proposal-block.tsx`): `.block-row`'s gutters, its role's element and typography, in its proposer's ground and edge. The proposer is read from the group's own `agent.run` provenance node — its `agent` and `executedBy` — and a group a person staged is the person's; an agent-stamped group with no provenance node says *an agent* (`readDocumentProposals`, `proposerOf` in `src/lib/proposals.ts`). The face, 24px, is centred on the left border and is the handle; the answers — Phosphor `check`, `x`, `checks` — ride the top edge, right-aligned. A rewrite sits right after the block it rewrites and a new block where it would land; a removal and a move frame the block that stands, which stays the editor's — a removal strikes its text through, and a move is marked where it stands with Phosphor `arrows-down-up`, where it would go said in its accessible name (decided 2026-09-10). Retired rows stay dashed and struck, so the three treatments stay apart by more than colour (`BO_0233_004`, `BO_0233_005`).
- The face sits at the vertical middle of the proposal's left border, and never higher than 2.35rem below the proposal's top (`.proposal-block__face`, `top: max(2.35rem, calc(50% - 14px))`). A removal or a move drops its own gutters, so the block it frames keeps its ⠿ handle and its standing glyph at the top of that same edge, reaching 2.13rem and 2.29rem down. A face pinned to the top covered them. With the floor, both stay in sight, and on a block of one line the face hangs past the lower border, about 0.6–0.8rem. Every kind places its face by the same rule. The grip comes later in the document at the same `z-index`, so on touch it keeps its presses over the face's enlarged target. Measured in Playwright on desktop and phone widths, over the editor's own markup, for a framed and an own-text proposal of one line and of several: no face meets any handle or standing glyph, its own block's or the next one's (`CA_0043_001`, user request 2026-09-11).
- Editing accepts through one path. A proposal's text cancels every input as it begins — synchronously, since a `$`-handler's `preventDefault()` runs after the browser has changed the text — and `heldEdit` says what it would have done; the item is accepted through `answerProposal`, the document re-read, the established block activated at the same offsets, and the held edit applied through the editor's own `editRuns$`, which saves it. An input that changes nothing (an undo, a delete at an edge) accepts nothing; a refused acceptance applies nothing and says why (`BO_0233_006`).
- An edit's acceptance says so. `answerProposal` carries `edited` from the command route through `answerDocumentProposal`, and an edited `replace` that CCGW answers as drifted is accepted over the drift (`override`) even when its words, role or place changed; the standing the block holds now is written back when it differs from the proposal's (`restoreStanding`), as for a standing-only drift (`blockDrift`). Without `edited`, and for a move, the `BO_0233_011` refusal stands. `tests/behavior/documents.test.ts` proves it over CCGW: a rewrite is staged, then the block's words are revised and its pin taken back; the plain accept is refused with `proposalStale`, the edited accept establishes the rewrite with the reader's standing, and an edited accept of a stale move is refused (`CA_0042_002`).
- `settleProposal$` is the one caller that accepts as an edit; the icons and *Accept all* answer through `answerProposal$` without it. `proposal-block.test.ts` proves that the settle path's answer carries `edited` and the icons' answers do not (`CA_0042_003`).
- Walked on the served build at pin 338 on 2026-09-11. The user typed into Claude Code's rewrite of a pinned block that they had revised after it was staged: the rewrite was accepted with the typing, and the block kept its pin (`CA_0042_004`).
- Moving uses the editor's own drag and drop marks, with `proposal:<itemId>` as the dragged item; a drop compiles into `placeProposal`, which stages `SET order` into the item's group — a staging into a group that already holds a candidate of the block builds on that candidate, so a rewrite keeps its words (proven over CCGW). Arrow presses on the face draw the new place at once and stage it once they pause for 600 ms, since the kernel refuses a block restaged within 250 ms (`BO_0233_007`).
- `Accept` and `Reject` sit on the item, and `Accept all` appears on a group of more than one. Accepting answers one item and then reads the document again, so what the reader sees is what the graph holds rather than what the surface predicted; `Accept all` runs the same per-item answer over the group in its own order, which is what makes it a shortcut rather than an operation with acceptance semantics of its own (`CA_0023_013`).
- `tests/browser/block-editor.spec.ts` proves the treatment on desktop and mobile against the real application: a staged group counted in the panel while the document still reads as truth, the toggle showing the change against the block it concerns and below it rather than over it, one item accepted leaving the block holding it and the rest of the group standing, one rejected leaving its block unchanged, a whole group accepted closing it and taking the treatment away, a retired block and a proposed change on screen together each saying in words which it is, and the axe scan clean with a proposal showing. The proposals are staged through the transport's own `propose` command, because no surface stages one: staging is what an untrusted writer does and this view only answers it (`CA_0023_012`, `CA_0023_013`).
