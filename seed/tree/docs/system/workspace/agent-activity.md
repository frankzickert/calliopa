# Agent Activity

## The Agent At Work In The Document

- Under `calliopa-bootstrap`'s `BO_0265`, set to draft by the user on 2026-09-18 and transferred here the same day, the person sees an agent's work in the document while it happens. The shell's part is to carry the run's activity to the view showing its document, and to draw one chip for each open run group, on the line under the view bar (`CA_0055`). The document's part is `documents`' [The Agent At Work](../../../src/extensions/documents/docs/system/documents/agent-at-work.md). The kernel's part is `calliopa-bootstrap`'s `docs/system/ui-kernel.md`, *The Agent At Work In The Document*, which adds the `document.activity` bridge event (`BO_0265_003`).
* A run's work on the document as a whole is shown on one line for the run, and that line stays as the run's summary when the run ends. The line is the run chip, under the view bar (`CA_0055`). While the run is going it says what the agent is doing on the document, and once it has ended it says what the run did, followed by *Reject all* and *Accept all* — drawn in full; from the second chip on, a chip that is not the expanded one says as much in a number and two signs (One Chip Open At A Time, `CA_0061_004`). User decision, 2026-09-18, narrowed 2026-09-22.
* *Reject all* and *Accept all* are offered only after the run has ended. User decision, 2026-09-18.
* There is one chip for each open run group on the document in the active tab, newest first. User decision, 2026-09-18.
* Each of the reader's own open proposals on the document has a chip of its own on the run chip line, beside the run chips. It reads *Proposal · yours* and the time its session started, and carries *Reject all* and *Accept all*. Pressing it shows or hides that proposal as a run chip's press does — expanding one chip collapses the rest, so one change is read at a time (One Chip Open At A Time, `CA_0061_004`); a pencil beside its words puts the tab to work in it, and one proposal at a time is worked in. User decision, 2026-09-18 (`CA_0057_001`), and in the walk the same day (`CA_0057_014`).
* A chip whose change is shown takes a tinted background, its proposer's ground, and the session the tab works in a stronger one, the accent. User decision in the walk, 2026-09-18 (`CA_0057_015`).
* The chips stand on a line of their own directly below the view bar and push the content down to make room for themselves. User decision, 2026-09-18 (`CA_0055`, replacing `BO_0265`'s place above the command field).
- The view reports its chips and the shell draws them, as the view reports its bar groups and the shell draws the bar (`CA_0053`).
- The contract carries the activity (`BO_0265_006`). `RunEvent` in `src/server/agent/run-events.ts` has `documentActivity`, carrying a `DocumentActivity`: `document`, `scope` (`document` or `blocks`), `action` (`read` or an item's kind), `blocks`, and — when there are — the `group` the run staged into, the `member` a staged item covers and the agent's `note`. `translateBridgeEvent` in `src/server/agent/bridge.ts` maps the bridge's `document.activity` onto it and answers nothing for one naming no document or action. `describeRunEvent` (`src/lib/runs.ts`) gives the console one line for it: *Read the document*, *Read 2 blocks*, *Proposed a rewrite*. `bridge.test.ts` proves both.
- The view hears the activity while the runs are going (`BO_0265_007`, `BO_0269_014`). The view bridge carries `activity: ViewActivity` beside `proposed`: `runs`, one `ViewRunActivity` per run the reader started and aimed at a document — its `itemId`, its `runId`, the `agent` the reader ran it on, whether it is still going, and its `documentActivity` events for that target in order — and a `seq` that rises when any of them changes. The shell fills it from the reads of `/api/runs/:id/events`. While one of the reader's runs is aimed at a document and has not been seen to end, those reads run on their own clock, every 750 ms (`ACTIVE_RUN_POLL_INTERVAL_MS` in `shell.tsx`), one pass at a time, so a mark lands within a second of the tool call; every other run's events ride the registry's 2 s poll as before.
- The run chips (`BO_0265_008`). A view reports its target's chips through `setRunChips$(itemId, chips)`, each a `RunChip`: its `key` (the group, or the run before it has staged), the `group`, the proposer's `face`, `tone` and `name`, one line of `text`, and whether its run has `ended`. The shell files them by target and draws the active tab's target's chips under the view bar (`RunChips`, `src/components/shell/run-chips.tsx`, `CA_0055_001`): the face and the text, which together are the chip's own toggle (`CA_0055_002`), and, once ended, *Reject all* and *Accept all*, each named *Reject all of <name>'s proposals*. A press writes `answerAll` (`itemId`, `group`, `answer`, `seq`), which the view reads and answers. Chips are filed by target rather than cleared on a tab switch, so a tab shows its own target's chips and one that reported none shows no line.

## Run Chips Under The View Bar

- Under `CA_0055`, set to draft by the user on 2026-09-18 and transferred here the same day, the run chips leave the command bar for a line directly below the view bar, and a chip's own press shows or hides its change's proposals. The editor's half is `documents`' [The Agent At Work](../../../src/extensions/documents/docs/system/documents/agent-at-work.md) (`CA_0055_005`–`CA_0055_008`). The decisions are the change document's: the chips push the content down, a chip reads as pressed while its change is shown, *Show proposed changes* sets every change and resets the chips, and the handle stops counting. They replace this topic's fixed lines placing the chips above the strip and counting them on the collapsed handle, which `CA_0055_001` and `CA_0055_003` rewrite.
- The chip line stands under the view bar (`CA_0055_001`). `shell.tsx` renders `RunChips` in `.workspace` right after `ViewBarPanel`, for the active tab's target (`chipsFor`, `src/lib/run-chips.ts`). `.run-chips` lies over the region's top edge at `top: var(--view-bar-height)`, opaque, as the bar does, and pushes the content down: `RunChips` measures its line (a `ResizeObserver`) and publishes its height as `--view-chips-height` on the region, and back to `0px` when it goes; the block editor's `--block-bar-height`, which its padding and scroll margins keep clear, is the bar's height plus it. With no chips there is no line. The render harness's DOM cannot parse a custom property, so the line is not measured there.
- A chip's own press shows or hides its change (`CA_0055_002`). `RunChip` carries `shown`, and the chip's face and text are one toggle button (`.run-chip__toggle`) named *Hide <name>'s proposals: <text>* or *Show …*, `aria-pressed` while shown and disabled for a run that has staged nothing. A press writes `toggleRun` on the view bridge (`itemId`, `key`, `seq`, `ViewToggleRun`), which the view answers; *Reject all* and *Accept all* are buttons of their own and toggle nothing. A hidden change's chip is dashed, its words muted.
- `run-chips.test.ts`, through `testing/run-chips-host.tsx`, proves the line right after the bar and absent without chips, the chips in order with the answers only once ended, a chip's press writing `toggleRun` and its answers writing `answerAll` alone, `aria-pressed` and the name following `shown`, a run that staged nothing not pressable, and no chip and no count in the command bar (`CA_0055_004`).

## Proposal Sessions As Chips

- Under `CA_0057`, set to draft by the user on 2026-09-18 and transferred here the same day, the run chip line also carries the reader's own open proposals on the document, one chip for each proposal session, and on a touch screen the chips lost their minimum height. The editor's half is `documents`' [Document Panel](../../../src/extensions/documents/docs/system/documents/document-panel.md), *The Proposal Toggle And Sessions*.
* On a touch screen the run chip has no minimum height: the line is as high as its words. User decision, 2026-09-18 (`CA_0057_002`).
- A session chip (`CA_0057_003`). `RunChip` carries `session: true` for the reader's own proposal session and `accepts: "others"` when someone else must accept it; the view gives its words (*Proposal · yours · 14:32*) and reports it `ended`, so `RunChips` draws its answers at once. Its toggle is named *Show <words>* or *Hide <words>* and writes `toggleRun` as a run chip's does; its pencil (`.run-chip__work`, `data-run-chip-work`, Phosphor `pencil-simple`), named *Work in <words>* or, pressed, *Stop working in <words>*, writes `toggleRun` with `work: true`; its answers are *Reject all of <words>* and *Accept all of <words>*; the view decides what each does. A chip with `working` carries `data-run-chip-working`, its pencil pressed and its toggle disabled, since that session is the document the tab reads (`CA_0057_014`). A shown chip (`data-run-chip-shown`) takes `--proposal-person`, `--proposal-codex`, `--proposal-claude` or `--proposal-hermes` by its tone as its background, and a working one the accent as its edge, an inner ring and a 22% accent ground (`CA_0057_015`). With `accepts: "others"` the chip draws *Someone else accepts it.* (`.run-chip__note`, `data-run-accepts-others`) in place of *Accept all*. `shell.css` gives the chips no `min-height` under `@media (pointer: coarse)` any more (`CA_0057_002`).
- `run-chips.test.ts` proves a session chip with its answers at once, its names, its press writing `toggleRun` and its pencil `toggleRun` with `work`, its *Accept all* `answerAll`, a working chip marked with its pencil pressed and its toggle disabled, the grounds of shown and working chips in `shell.css`, *Someone else accepts it.* in place of *Accept all* under `accepts: "others"`, and no rule in `shell.css` giving a chip a minimum height (`CA_0057_004`).

## One Chip Open At A Time

- Under `CA_0061`, set to draft by the user on 2026-09-22 and transferred here the same day, a line of several chips minimizes, and the chip the reader has open is the one whose change is drawn. The view's half is `documents`' [The Agent At Work](../../../src/extensions/documents/docs/system/documents/agent-at-work.md), *One Chip Open At A Time* (`CA_0061_007`–`CA_0061_012`).
* From the second chip on, a chip that is not the one being read stands minimized: the proposer's face, the number of changes it holds as a bare number, and its two answers as their signs alone. One chip on the line is drawn in full, as it is today. User decision, 2026-09-22.
* Pressing a chip's face expands it — its words and its labelled answers come back and its change is drawn in the document — and collapses every other chip, hiding its change. Pressing the expanded chip's face collapses it again, and the line may stand with nothing expanded and no change drawn. User decision, 2026-09-22.
* Only the expanded chip is highlighted. A collapsed chip carries no proposer's ground and does not read as pressed. User decision, 2026-09-22.
* *Show proposed changes* expands the newest chip and shows that change alone; turned off it collapses every chip and shows none. User decision, 2026-09-22, replacing `CA_0055_006`'s showing of every change at once on a line of several.
* A run that is still going is never minimized: it keeps its words, since it has no number to give yet, and its proposals keep appearing as it stages them. When it ends, its chip is the expanded one, and whatever was expanded collapses. User decision, 2026-09-22.
* A session chip minimizes as a run chip does and keeps its pencil. Where *Someone else accepts it.* stands, a minimized chip shows a warning sign in the accept's place, titled with those words. User decision, 2026-09-22.
- The minimized chip (`CA_0061_001`). `RunChips` (`src/components/shell/run-chips.tsx`) marks the line `data-run-chips-several` from the second chip on, and `shell.css` draws every chip inside such a line that is `ended` and not `shown` as its face, its number (`.run-chip__count`, `data-run-chip-count`) and its two answers' signs: the words (`.run-chip__text`) and the answers' labels go to `display: none` and the answers' padding tightens. A session chip keeps its pencil. Under `accepts: "others"` the `warning` sign (`.run-chip__note-sign`, `data-run-accepts-sign`), titled *Someone else accepts it.*, stands in the accept's place, and the note's own words are hidden to the eye alone rather than taken out. Nothing is left out of the chip and every accessible name is the one it carries drawn in full, so a minimized chip says no less to a screen reader.
- The count comes from the view (`CA_0061_002`). `RunChip` carries `count`, the open changes its group holds, which the view reports beside `text`; the shell draws it and never reads a number out of the words. A run that has staged nothing has none, and is never minimized because it is not `ended`.
- The highlight is the expanded chip's (`CA_0061_003`). The proposer's ground under `data-run-chip-shown` and the toggle's pressed state are what say a change is drawn, as they already did (`CA_0055_002`, `CA_0057_015`); on a line of several a collapsed chip is drawn as a hidden change's chip is — dashed, with its number muted beside its words — and the working session keeps its accent.
- The two fixed lines above this section were narrowed with it (`CA_0061_004`): an ended run's summary and a session chip's reading are what a chip drawn in full says, and a session chip's press no longer shows several proposals at once.
- Proven (`CA_0061_005`). `run-chips.test.ts`, through `testing/run-chips-host.tsx`: the line marked from the second chip and not before, the collapsed chip's number, its words and its answers' names unchanged by minimizing, a running chip neither ended nor numbered, the warning sign beside a session's kept pencil, and the rules in `shell.css` that hide the words, the labels and the note and show the number and the sign. Each was shown to fail with its code removed.
- The release note is in `calliopa-bootstrap`'s `docs/release-notes/unreleased.md` under *Changed* (`CA_0061_006`).

## The Chip Line Is One Row

- Under `CA_0062`, set to draft by the user on 2026-09-22 and transferred here the same day, the chip line becomes one row that scrolls, as the view bar became one under `CA_0060` ([Layout](./layout.md#the-view-bar)). No extension's half: what a view reports is unchanged.
* The line is one row whatever it carries. When the chips need more room than it has, the whole row scrolls sideways with nothing held at either edge, and the height it takes from the document stops depending on how many chips stand on it. User decision, 2026-09-22.
* An end with chips beyond it fades outwards, as the view bar's does: the line's own ground thinning out, answering no press and taking no room from the chips. User decision, 2026-09-22.
* A chip that becomes the expanded one without the reader pressing it — a run ending, the bar's toggle expanding the newest, a document opening with its proposals shown — is scrolled into view. A press the reader made moves the line no further, and nothing else scrolls it. User decision, 2026-09-22.
* The expanded chip takes at most the line's width and its words truncate; its answers and its pencil keep their size, since a control is not what gives way. User decision, 2026-09-22.
- One row that scrolls (`CA_0062_001`). `.run-chips` (`shell.css`) is `flex-wrap: nowrap` with `overflow-x: auto` and `overflow-y: hidden`, its chips centred and nothing held at an edge, as `.view-bar` is (`CA_0060_001`). The line is still measured and still publishes `--view-chips-height` (`CA_0055_001`), which now holds at one height however many chips stand on it, so the document is pushed down once and stays there.
- The ends fade (`CA_0062_002`). `RunChips` carries `data-more-start` and `data-more-end`, written from `moreBeyond(scrollLeft, scrollWidth, clientWidth)` on the line's own scroll and on the pass that publishes its height, so the one `ResizeObserver` answers both. `shell.css` draws each fade as a sticky `::before`/`::after` flex item held at its end of the scrollport, pulled back by `margin-inline: -1.5rem` so it takes no room from the chips, painted over them in `--panel-raised` thinning to `transparent` and switched by `opacity`; reduced motion drops the transition. The bar's rules, on the line's ground (`CA_0060_002`).
- `moreBeyond` is shared (`CA_0062_003`). It lives in `src/lib/scroll-edges.ts`, where the view bar and the chip line both read it, with its cases in `src/lib/scroll-edges.test.ts`; `view-bar.tsx` imports it from there and draws its fade as before.
- The expanded chip is brought into view (`CA_0062_004`). `RunChips` keeps what the line has shown and the key the reader last pressed: a chip that gains `shown` other than by that press — a run ending, the bar's toggle expanding the newest, a document opening with its proposals shown — is scrolled to with `scrollIntoView({ inline: "nearest", block: "nearest" })`, smoothly unless the reader asked for stillness. `block: "nearest"` keeps the page where it is, and a DOM without `scrollIntoView` is left alone.
- A wide chip gives way (`CA_0062_005`). `.run-chip` is `flex: 0 0 auto` with `max-width: 100%`, so a collapsed chip keeps its size and the expanded one is held to the line's width; what truncates there is `.run-chip__text`, by the ellipsis it already carries, while the face, the answers and the pencil keep theirs.
- Proven (`CA_0062_006`). `run-chips.test.ts`, through `testing/run-chips-host.tsx`: the one-row and fade rules in `shell.css` and the chip's own `flex` and `max-width`; neither end fading on a line whose chips fit; and a chip scrolled to when the host reports it shown, not when the reader pressed it — the host reports its own chips, since Qwik's harness refuses to render over its container twice. `src/lib/scroll-edges.test.ts` holds `moreBeyond`'s cases. Each was shown to fail with its code removed. The harness parses no custom property and measures no scroll, so the fade drawn and the scrolling are the walk's, as the line's height is (`CA_0055_001`).
- The release note is in `calliopa-bootstrap`'s `docs/release-notes/unreleased.md` under *Changed* (`CA_0062_007`).
- Walked on the served build at pin 1283 on 2026-09-22, and the user said it works (`CA_0062_008`): the chips stood on one row that scrolls, the document was pushed down by one height and stayed there as runs came and went, an end with chips beyond it faded, a chip that became the expanded one was brought into view, and an expanded chip's words gave way rather than the row.

## Execution

- Under `calliopa-bootstrap`'s `BO_0267`, promoted to draft by the user on 2026-09-18 and transferred here the same day, the inspector gains an *Execution* section listing the runs of the document in the active tab. It is drawn by the shell, which owns runs, beside what the view contributes; the view reports which block is selected, as it already does through `setSelection$`, and answers a run's change through `toggleRun` and `answerAll`, as the chips do.
* The *Execution* section lists every run of the document the person may see, newest first, archived runs included. User decision, 2026-09-18.
* With a block selected it shows two groups: *From this block*, the runs sent from it, then *Touching this block*, the runs that proposed changes to it or referenced it. With no block selected it shows every run. User decision, 2026-09-18.
* A run's entry shows the agent's face, the first line of its prompt and its state. Pressing the entry shows or hides that run's proposals in the document, as its chip's press does; *Reject all* and *Accept all* are its own buttons, offered once the run has ended, and *Cancel* while it runs. User decision, 2026-09-18.
- Which runs a person sees is `BO_0232`'s: their own, and every run for the owner. A block another person sent is still a prompt to everyone, since standing is graph truth, but its runs are listed only for that person and the owner.
- The section (`BO_0267_010`) is `ExecutionSection` in `src/components/shell/execution.tsx`, drawn in the inspector's content for a document tab after the view's contribution, under its own band and caret (`SectionHeader`, the layout's `ui.shell:execution` section), and not while a selected process holds the inspector. The shell reads `GET /api/runs?artifact=<id>` into its `execution` store when the active document changes, when a run it started opens or ends (`run.id`, `runProposed.seq`), and every `ACTIVE_RUN_POLL_INTERVAL_MS` while a listed run is running. An entry shows the face (`faceOf` of the run's agent), the first line of the command (`firstLineOf`), the state in words (`stateWords`: *running*, *ended*, *failed*, *cancelled*), and while the run's group stands open the view's chip line for it; the entry's body is a toggle writing `toggleRun` with the chip's key and reading as pressed while its change is shown, disabled with no open change; *Reject all* and *Accept all* write `answerAll` once the run has ended and its change is open, and *Cancel* posts the run's cancel while it runs. `executionGroups` (`src/lib/execution.ts`) splits the list by the tab's selection into *From this block* (`source`) and *Touching this block* (`touched`, or a reference to the block, the first group's runs excluded), each group omitted when empty and a line when both are; with no selection every run is listed. Proven by `src/lib/execution.test.ts` and, in the render harness, `src/components/shell/execution.test.ts` over `testing/execution-host.tsx`: the entries as read, both groups and the return to every run, the toggle writing its chip's key, a run with nothing open not pressable, the answers only once ended and the cancel only while running.

## Execution Is The One List

- Under `ui.shell`'s `CA_0058`, set to draft by the user on 2026-09-20 and implemented the same day, the console left the dock and *Execution* became the one list of processes in the right panel ([Commands And Runs](./commands-and-runs.md), *The Dock Went*; [Processes](./processes.md), *The Run List In The Panel*).
* *Execution* is the one list. On a document tab it keeps its groups — *From this block* and *Touching this block* — and carries the reader's other processes in a group of their own; on every other tab, and in the empty workspace, it lists those alone. No process is listed twice. User decision, 2026-09-20.
- The third group is named *Elsewhere* and holds what the first two do not: the reader's processes that are not runs of this document, a publishing run among them.
- The groups (`CA_0058_008`). `executionGroups` (`src/lib/execution.ts`) takes the reader's processes beside the document's runs and answers `elsewhere` with those no listed run reports — matched by a process's `runId`, so a run of this document is listed as a run and never again as a process, and a tab with no document lists its processes alone. `ExecutionProcess` is what an entry reads of a process (`executionProcess`): its id, title, state, step, the run it reports and whether an extension's trigger started it.
- The section is drawn on every tab (`CA_0058_005`, `CA_0058_010`). `ExecutionSection` (`src/components/shell/execution.tsx`) takes the active tab's document or `null`, the processes and the selected one; `shell.tsx` renders it in the inspector after the view's contribution, whatever the tab shows, and a selected process's detail takes the contribution's place above it rather than the list's, so the reader can move from one entry to the next. A run's entry keeps its toggle and gains a caret (`.execution__detail`, `data-execution-detail`) named *Details of “…”*, `aria-pressed` while that run's process is selected and disabled for a run no process of the reader's reports. A process entry carries the console's own hooks — `data-process-id`, `data-state`, the `sparkle` for a system run — and its press selects the process; it is a drag source as the console's row was, from `panel` now rather than `dock`. With nothing at all the section says *Nothing has run yet* on a tab with no document, and *No runs on this document yet* on one with.
- `execution.test.ts` and the harness over `testing/execution-host.tsx` prove it: the three groups with a process reporting a listed run left out, the processes alone on a tab with no document, the empty line, the caret selecting and letting go while the toggle writes nothing, and a process entry's press. The caret's case was shown to fail with the control taken out.
