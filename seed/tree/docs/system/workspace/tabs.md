# Tabs

## Tabs

* Tabs represent open working contexts, not routes alone. A tab can contain a script, scene, storyboard, media asset, timeline, or process result.
* Each tab retains its own selection, scroll position, drawer context, unsaved state, and running-process indicators.
* On mobile, swiping across the tab strip selects tabs; swiping inside the workspace stays available to the current tool.
* Open tabs and layout state persist per workspace record in the kernel's per-instance state record, keyed by the workspace identified by the URL. Tabs survive reloads and devices; ephemeral scroll position stays local.

- A tab is a tab shape seated on the header's bottom edge: rounded top corners, no bottom border, panel background, and a strip that aligns its tabs to that edge.
- The active tab is raised to the raised-panel surface and carries an inset accent bar along its top edge, so the active context is legible without colour alone.
- A tab title truncates with an ellipsis at a bounded width instead of stretching the strip.
- Unsaved state and process state are small round markers inside the tab, each with its own accessible name, not glyphs appended to the title.
- The tab close control is a transparent icon button that gains its surface on hover.
- The strip says which tab is active with a value on every tab — `data-active` is `true` or `false`, and `aria-current` is `page` or `false` — never with an attribute present on the active tab alone. An attribute written as absent is left behind on a reused element, so the tab that stopped being active went on saying it was, to a reader's assistive technology as much as to a scenario. `tests/browser/tabs.spec.ts` proves on both form factors that a selection leaves exactly one tab reading as active and every other tab saying it is not (`CA_0021_007`).
- URL state identifies the workspace and optionally the active item. Drawer states, dock position, and scroll are not encoded in the URL.
- A tab carries its item identity, its item kind, and the view type presenting them. [Workspace View Types](./view-types.md) owns the view contract, the built-in registry, and how a tab chooses, remembers, and mounts a view.
- `ui.shell:document` is a target kind — `document` as `ui.shell` contributes it, qualified by the extension id like every contributed kind (`BO_0202_004`) — presented by the block editor in [Block Editor View](../documents/block-editor.md). The library's `Documents` category offers a new document, which creates it in the graph and opens it in its own tab; the tab names the document, and the graph owns it. Renaming a document in its tab renames the tab and the library entry together, through `setTitle$` on the view bridge. That offer lives in the library category, not in the header.
- Settings is a tab, opened from a control in the header beside the theme toggle, the layout controls, and the process indicator. It is chrome belonging to the instance rather than to any document, which is what that row already holds, so it takes the same transparent icon-button idiom.
- `settings` is a target kind that resolves to nothing in the graph. Every other kind names content — `document` is answered by [Block Document Model](../documents/block-document-model.md) — and this is the first tab whose target is not content at all.
- The settings tab carries a synthetic instance-wide target instead of no target. A tab is found by its target, so opening settings twice reveals the open tab rather than opening a second one, and the reveal rule works unchanged rather than special-casing a tab that has nothing to be found by.
- The settings tab persists, restores, closes, and reorders like any other tab, because it is one. [Settings](../../../src/extensions/settings/docs/system/settings-surface.md) owns what it holds; the shell owns that it is a tab.
- The synthetic target is the instance, so every workspace's settings tab names the same one. Nothing in the graph answers it, and nothing needs to: `openTab` matches a tab by target identity, target kind, and view, and a target that resolves to no content matches exactly as well as one that does.
- The library does not list settings. The `Documents` category is a content tree, and an entry that is not a document would make the drawer mean two things.
- The library holds a second category, `Episodes`, listing the episodes [Episodes And Assets](../../../src/extensions/calliopa-video/docs/system/production/episodes-and-assets.md) answers and opening one in its own tab under the `episode` target kind. It offers a new episode the way `Documents` offers a new document, from the category rather than the header (`CA_0033_013`). The category is `calliopa-video`'s contributed section since `BO_0203`, keyed `calliopa-video:episodes`, and the kind is `calliopa-video:episode`; a tree without the extension has neither.
- The stored layout carries the sections' states as one record keyed `<ext>:<section>` (`Layout.sections`, `BO_0202_003`), replacing the five named fields it carried per category. A key absent reads expanded when the shell asks (`sectionState`), so a section added later arrives open in a workspace that predates it; a key whose extension is absent from the build is preserved untouched, so an extension removed and restored remembers its state; a layout stored with the named fields is rewritten to the keys on read — the one migration the change names — and stored so on its next save. `parseLayout` refuses a state outside the vocabulary rather than defaulting it (`CA_0033_013`, rewritten under `BO_0202_003`).
- Every library category is a contributed section: what the drawer holds is the registry's list, in contribution order, each with its title, its toggle, its optional create control and a body that is either the uniform row or the contributed component ([Contribution Contract](./contribution-contract.md), `BO_0202_003`). A tab's kind is qualified by the extension that contributes it, and a kind stored bare from before that rule is rewritten on read (`LEGACY_TAB_KINDS`); the frame's own kinds — the story-development placeholders and `process-result` — stay bare (`BO_0202_004`).

- The library holds two further categories. `Standing Assets` lists the assets no episode holds ([Episodes And Assets](../../../src/extensions/calliopa-video/docs/system/production/episodes-and-assets.md)); `Destinations` lists the destinations that have a front and opens one under the `front` target kind, whose identity is the channel ([Publishing](../../../src/extensions/calliopa-video/docs/system/publishing/homepage-front.md)). The two are not one list: one holds work and the other holds the places work goes (`CA_0038_008`). Both are `calliopa-video`'s contributed sections since `BO_0203`, keyed `calliopa-video:standing` and `calliopa-video:destinations`, and the front kind is `calliopa-video:front`.
- A destination with nothing written for its front is listed rather than hidden. Otherwise the first front could never be opened to be written (`CA_0038_008`).
- A standing asset is named and not opened, because no view presents an asset on its own and a control that opened nothing would say there is somewhere to go. The follow-up is `CA_0038_009` in [Episodes And Assets](../../../src/extensions/calliopa-video/docs/system/production/episode-view.md) (`CA_0038_008`).
- `Layout` carries a section state for each, and `parseLayout` defaults them through the rule it already applies to every category, so a workspace stored before they existed reads them back expanded (`CA_0038_008`).

- The shell header carries the active tab's save state in words — `Saving`, `Saved`, or `Unsaved` — beside the tab strip, so a reader learns whether their work is safe without a block being active. A tab whose view reports no save state, such as a placeholder, shows nothing there.
- The tab's round unsaved marker is that state projected rather than a second reading of it: anything but saved means the graph does not hold what was typed.
- A stored tab whose target no longer exists opens with a visible notice saying so and offers nothing to edit. The tab keeps its place, matching the view-fallback rule in [Workspace View Types](./view-types.md): the shell has one account of a target it cannot present, and a tab the reader left open never disappears without saying why.
- The round unsaved marker is the inactive-tab affordance only. The active tab's state is the header's words beside the tab strip, so a marker there would encode the same fact twice in one glance; on a tab the reader is not looking at, the marker is the only signal there is.
- [ ] CA_0012_007 Show the round unsaved marker on inactive tabs only. `shell.tsx` renders it for every tab with unsaved work today; the active tab drops it while the header keeps naming its state in words, and the marker's accessible name still says which tab has unsaved work. A scenario proves the marker appearing on a tab left unsaved, absent on that tab once it is active, and back when the reader switches away.


## Workspace Record

* There is one default workspace at `/`, created on first visit. A workspace list arrives with users or projects in a later change.
* A workspace record stores open tabs, active tab, and layout state.
- The stored layout carries the `Documents` category's collapsed state alongside the drawer states and the dock position. A record written before the category existed carries no section state and reads back expanded rather than being refused.

- The route group serves `/` for the default workspace and `/w/:id` for an identified workspace.
- The workspace API can create and read a non-default workspace so browser scenarios do not share mutable state.
- Tabs and layout are saved on every change. Scroll position stays browser-local.
- The record also stores the view last chosen for each target, keyed by item identity, so reopening a target answers with that view.

## Implementation

- Tabs have a typed context contract and pure open, select, close, reorder, and update operations. Selection, drawer context, and unsaved state are stored per tab, the process marker is projected per tab from the registry, and scroll is explicitly browser-local (`CA_0002_016`).
- Since `BO_0207_014` a workspace is one JSON record in the kernel's state record (`GET`/`PUT`/`DELETE /__kernel/state/workspaces/<id>`, `ui-kernel.md`, `BO_0207_002`), reached through `src/server/kernel/client.ts`: a tab switch is working state, never a data revision. The default workspace has the fixed identity `00000000-0000-4000-8000-000000000001`, so the first visit and every later one find the same record without a marker, and a workspace deleted in the shell is removed from the record. `migrations/0002_workspace.sql` and its table stay in the retired database, unread, until `BO_0207_005` carries the rows over. `src/server/workspaces.ts` validates tabs, active tab, and layout on the way in, creates the default workspace at first visit, and serves `/` and `/w/:id` from the same shell. `POST /api/workspaces` creates a further workspace, `GET`/`PUT /api/workspaces/:id` read and save it, and every tab or layout change saves immediately. Browser scenarios take their own workspace through `tests/browser/workspace.ts`, so state survives reload without leaking between parallel scenarios (`CA_0002_017`).
- The tab shape lives on the tab wrapper: rounded top corners, no bottom border, the `panel` surface, and a strip that seats its tabs on the header's bottom edge. The wrapper carries `data-active` for the raised surface and its inset accent bar, and the title truncates with an ellipsis inside a bounded tab width (`CA_0010_002`).
- Unsaved state and process state are round markers inside the tab named `Unsaved`, `Process running`, and `Process failed`, in place of the appended glyphs. Tab coverage asserts the unsaved marker by its accessible name (`CA_0010_003`).
- The header's save state is its own component reading the bridge's save store, for the reason the inspector contribution is one: re-rendering the shell would rebuild the mounted view, and for an editing surface that means rebuilding the element the caret is in. A view reports for the tab it is mounted on, and the report is ignored for a tab that has since closed; only a report for the active tab reaches the header (`CA_0012_004`).
- `targetGone$` on the view bridge is how a view says its target no longer exists. The shell closes every tab in this workspace showing it, saves, and re-reads the library; the view says the target is gone because only it knows what removed it, and the shell owns the tabs (`CA_0015_007`).
- A stored tab in another workspace naming a deleted document is discovered by the view failing its read: a rooted read of an archived document answers no result, and the block editor reports that as a deleted document rather than as an unreadable one. The tab keeps its place and offers nothing to edit (`CA_0015_007`).
- `settings` is a target kind in `src/lib/tabs.ts` and a view type in `src/lib/views.ts` presenting only that kind, so it is its default and its only compatible view and the workspace renders no `Open in <view>` group for it. `SETTINGS_TARGET` in `shell.tsx` is the synthetic instance-wide target identity, and the header's `Settings` control opens a tab against it in the chrome idiom the theme toggle and layout controls already use. The view mounts through `ViewHost` like every other, whose total component record is what made registering the kind without a component impossible (`CA_0021_005`).
- `tests/browser/settings.spec.ts` proves on desktop and mobile that the control opens a settings tab, that a second press reveals that tab rather than opening a second, that the tab survives a reload still showing settings, that it closes like any other tab, and that the axe scan stays clean (`CA_0021_005`).
