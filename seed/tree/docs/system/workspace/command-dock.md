# Command Dock

## Command Dock

* The dock renders the active view's contributed action. The view says what the action is and supplies its handler; the shell renders it in its own idiom, the way the inspector already renders a view's contributed actions.

- The action area is the start of the strip above the bar and rides with the composer: it is present at the dock's composer and console positions and absent at the collapsed handle (`CA_0039_001`). A view that contributes no action shows nothing there, as a placeholder view already shows nothing in the inspector.
- The action is the one place a view reaches into the dock. The handle, the composer, undo, and the console stay the shell's own, and a view never renders into them. A view may offer an undo for what it just did (`offerUndo$`, `BO_0227`); the shell renders it in its one undo line, as it renders a tab move's.
- A contributed action may read as pressed, so a view can say which of its own modes the surface is in rather than only offering a way in. The command mode in [Block Editor View](../documents/command-mode.md) is the first one that does.
- The contribution follows the active tab, as the inspector's does. A tab switch clears it, so the dock never offers an action belonging to a view the reader has left.
- The named-action vocabulary is the one the inspector already renders, defined in [Workspace View Types](./view-types.md). A second vocabulary for the same kind of thing would let one view's button and another's disagree about what a named action is.

* The dock handle's gesture applies one transition. A release that moved less than the swipe threshold is a tap, which closes an open dock and opens a closed one to the composer; a release at or beyond it is a swipe and moves the dock one position in its own direction. Which transition applies is decided by what the reader did, never by the order two handlers happen to run in.
* A release the handle saw no press for is never a swipe. What the handler records is that a press happened, not only where: a pointer's coordinate has no value that means "no press", so an initial one stands in for a measurement that never happened and reads as a swipe the length of the viewport.

- The first interaction is where the press record earns its place: until the handle's press handler is resolved a release can arrive with nothing recorded, and it is read as a tap rather than as a swipe the length of the viewport.
- Until `BO_0230` a tap cycled the dock forward — composer, console, collapsed — so from the composer the first tap opened the console and the dock grew; on a phone that read as the dock refusing to close, and the reader reported exactly that. A tap now closes an open dock and opens a closed one (`dockAfterTap`); the console is a swipe up from the composer or the header's console control (`BO_0230_002`).
- The release is where a pointer's gesture is decided, so a swipe is a gesture a touch makes. A mouse dragged off the handle releases somewhere else and the handle never hears it; a mouse taps, which is the same one transition.

* The command dock is the agent surface. The composer is the goal input, each request is a process record, and the process console lists runs. There is no message table and no new region.

- The shell consumes the normalized run event contract defined in [Calliopa Agent](../agent/run-lifecycle.md) and never depends on Hermes-native event JSON.
- One active run at a time. A second goal raised while a run is active is refused as busy rather than buffered, which is a constraint the agent's tool configuration forces rather than a choice the dock makes.
- Per-owner chat threads are not built. The dock the shell already has — goal input, live event stream, cancel, and a short list of recent runs with state — is the console, and a run is a process like any other.
- `POST /api/workspaces/:id/runs` starts an agent run for a goal. The run record opens before the agent is asked, so a goal the agent refuses still leaves something the reader can watch fail rather than a button that did nothing. The response carries the run and its process; the run is followed after the response is sent, because handing over a goal is quick and the run is not, and the shell learns how it is going by polling the registry rather than by holding a request open (`CA_0022_013`).
- `src/server/agent/hermes.ts` is the only place this application knows Hermes's HTTP shape, and `src/server/agent/conductor.ts` is the only place that drives a run. An agent that is unreachable, unconfigured, or refusing is an ordinary outcome carried back as words: a missing subscription is a state to report, never an exception to swallow (`CA_0022_013`).
- Following a run translates each event through the contract in [Calliopa Agent](../agent/run-lifecycle.md), records it for the console to read back, keeps the process step current, and moves both when a terminal event arrives. A stream that ends without saying how the run finished fails the run, because a run left `running` forever is worse than one that admits it lost track (`CA_0022_013`).
- `POST /api/runs/:id/cancel` asks the agent to stop and moves the registry either way, so a reader who pressed cancel is never left watching a run the agent never answered about. `GET /api/runs/:id/events` is what the console polls, and it answers the normalized contract's events rather than the agent's own JSON (`CA_0022_013`).
- The gate proves the whole path against the real agent: the application's own route opens a run, hands the goal to Hermes, follows the stream, and the process reaches the registry `failed` carrying the agent's own words about being unconfigured. The busy refusal is not asserted there — a run against an unconfigured agent ends in well under a second, so whether the slot is still held is a race rather than a property, and it is proven deterministically against real Postgres instead (`CA_0022_013`).
- A command issued while a document is open is aimed at it (`BO_0226`), and the strip right above the bar says so (`CA_0039_001`): the document's title, grayed, then a × that asks for words instead of a proposal. By default the run proposes into the document, staging what it writes for the reader to answer per item. After the × the strip reads *Answer in the console*: the run is asked for words and stages nothing, and the command still carries its references, so *what does #3 mean?* is answered in the console; the title, now a control named *Propose into «title»*, brings the proposal back. The choice is kept as `DeliveryChoice` keeps it: another document comes forward on propose, and the first one's dismissal is still there on return unless another document was dismissed since. The reader sets the delivery and the run obeys it: a run is never left to infer it from how the command was phrased, which is what the first run from an open document did, searching the web and answering in the console (`BO_0226_005`). Until `CA_0039` the choice was a *Result* select on its own row under the field.
- Which agent performs a command is the reader's choice, in a dropdown at the bar's left, vertically centred on the field (`AgentMenu`, `BO_0228`, placed by `CA_0039_002`): Codex, Claude Code and Hermes, each shown by its character's face — Codey, Clauderic, and for now the Fairytales barista robot — never a vendor's logo. Closed, it shows the chosen agent's face and a caret and is named *Agent: «name»*; open, it lists the three with their faces and names, Hermes's with its model. A native `select` cannot show a face, so it is the select-only combobox pattern: the arrows, `Home`, `End` and a letter move, `Enter` chooses, `Escape`, `Tab`, a press outside or the button again close with the choice unchanged. An agent that cannot run is listed dimmed with its reason as text under its name, `aria-disabled` rather than removed, and choosing it changes nothing. The choice is remembered for the instance (`PUT /api/agent/choice`, `agent-choice.json`), so every device opens on the same agent; when the remembered agent cannot run, it opens on the one the gateway is running and the notice line says so, and a command always names its agent. The faces' crops are recorded beside `AGENT_FACES` in `src/lib/agent-menu.ts`, and every decision the dropdown makes is a function there (`openingAgent`, `menuKey`, `pick`).
- `sendGoal$` reads the active tab, the delivery chosen for its document and the document's marks from their stores at the press — never from a captured closure, and never the tab's selection, which leaving the editor for the composer has already cleared — through `commandTarget` in `src/lib/command-target.ts`, and posts `artifact`, `delivery` and `references` beside the goal for a document tab and none of them otherwise. The route reads them back through `readCommandTarget` and refuses a shape the composer never sends by name — a delivery or references with no document, a document with no delivery, a reference list that is not one — rather than forwarding or guessing at it; the kernel's intake refuses an incoherent one too, and its `400` reaches the reader as a refusal rather than as the agent failing (`BO_0226_004`).
- When the run the composer started ends — completed, failed or cancelled, since a run that failed may already have staged — the shell tells the view showing its document once, through `proposed` on the view bridge, and the block editor reads its proposals again and opens them if any stand unanswered, so the reader sees the proposed change where it would land without reopening the tab (`BO_0226_007`).
- What a command carries from the open document is shown along the field's bottom edge as chips (`ReferenceChips`, `CA_0039_003`): one per reference in mark order — `#1`, `#3`, `#5` — then one per pinned block, carrying a pin and no number, since a pinned block is a standing and not a reference. A chip shows its number and says its words in its accessible name — *Reference 3: “…”*, *Pinned: “…”* (`chipName`, `pinnedChipName` in `src/lib/pointing.ts`); a stale passage's chip carries the warning icon and border and *stale* in its name. The chips are the view's report itself, the entries `commandTarget` builds the body from, so what they show and what is sent cannot differ; a pinned block is shown and never sent, since the kernel reads what is pinned from the graph at the run's start. They wrap onto a second line, and the row is absent when nothing is marked or pinned. A chip carries no × and no +: a reference is taken back where it was marked, in the document, which is still the list of what was marked; the chips are the command. Pressing one — click, tap, `Enter` or `Space` — asks the document's view to show its area through `reveal` on the view bridge ([Workspace View Types](./view-types.md)). This supersedes `BO_0226`'s *never an enumeration*, by the user's decision of 2026-09-10, as the disclosure it replaced did (`BO_0227_015`).
- Typing `#` in the field offers the document's references by number, narrowing as digits follow, as buttons in a list that opens above the field, since the field's bottom edge holds the chips (`CA_0039_002`), so pointer, touch and `Tab` reach them without a key handler racing the textarea's own `Enter`; choosing one writes `#<number>` where the reader was typing. A number typed creates nothing (`CommandField`, `src/lib/command-typeahead.ts`). The field takes the report itself, as the chips do: a component prop written as `object.field` is compiled through `_wrapProp`, which stays reactive only when the object is a store, and before anything is marked the report is the plain `NO_POINTING` — so both lists were taken once, empty, and kept. `composer-late-marks.test.ts` proves both through the shell's own JSX (`testing/composer-host.tsx`); a test building its elements with `jsx()` never meets the optimizer, which is how both froze while every such test passed.
- A command carrying a stale passage is refused at *Run*, naming it beside the control, as the composer's refusals are shown (`CA_0022_018`): its number may already be in the words, and sending it would name a reference with nothing behind it. So is a command whose words name `#n` that no mark stands under — a mark taken back after its number was written — naming the number and asking for it to be marked again or taken out of the words (`danglingNumbers`, `src/lib/command-typeahead.ts`).
- The strip is one thin line directly above the bar: the view's action at its start, then the title in `text-muted`, truncated with an ellipsis, with the full title in the strip's accessible name (*Command aimed at «title»*), and the × at its end, named for what it does. On a tab that is not a document there is no title and no ×, and the strip is absent when the view contributes no action either (`CA_0039_001`).
- The composer is one bar under the strip (`CA_0039_002`): the agent dropdown at the left, then the field, rounded, which grows with its text up to a bound and then scrolls (`fitField`), with a visually hidden *Command* label, since a placeholder is not a label. *Run* is a round button inside the field at its right end, the accent's ring around a play glyph, named *Run*, disabled while sending; an empty field still starts nothing. The notice line stays directly under the bar. The bar takes Calliopa's theme, not a mockup's palette: semantic tokens only, a fine border on `panel-raised` and no shadow. On a coarse pointer the dropdown, the ×, every chip and *Run* are at least 44px, and on a phone the bar spans the width and the strip's title gives way first.
- The undo line holds one thing: a tab move, carrying the tabs to restore, or a view's offer, carrying its own inverse. A new offer replaces what stood, and a tab switch clears a view's offer as it clears the view's dock action (`BO_0227_013`).
- The composer sends its text to the run route and clears on success. A refusal is shown beside the control that was pressed rather than on the message surface: a message takes the whole frame and demands an answer, and the reader who pressed `Run` needs a line saying why nothing happened, not a question (`CA_0022_018`).
- The run's normalized events show above the process list, read through the registry's own polling rather than a second transport, and the run is read once as soon as it opens so the console shows it without waiting a tick. Cancel is offered only while the run's process is still queued or running, so the control is never there for a run that has already ended (`CA_0022_018`).
- `tests/browser/agent-dock.spec.ts` runs serially and waits its turn for the agent, because the agent is one serialized resource and every scenario shares the single agent client: a scenario that assumed the slot was free was really asserting that no other scenario held it. Waiting is what a second reader would do, so the scenarios do it too (`CA_0022_018`).
- Those scenarios meet an agent with no subscription, which is the honest state of the stack: a goal opens a run the console lists, its activity reads back the start and then the failure in the agent's own words, the composer is cleared so the goal is not sent twice, no cancel is offered for a run that has ended, an empty composer starts nothing, and the axe scans stay clean with a run showing (`CA_0022_018`).

## Implementation

- The dock handle and the three dock positions apply on both form factors, so the desktop dock arrives at composer height and renders the console only in its console position. Desktop coverage cycles the handle through composer, console, and collapsed (`CA_0010_005`).
- `dockAfterRelease` in `src/lib/layout.ts` is the one reading of a release on the dock handle: a recorded press that travelled at least `DOCK_SWIPE_THRESHOLD` is a swipe, anything shorter is a tap, and a release with no press recorded is a tap. The threshold is one constant `dockAfterSwipe` asks as well, so the two readings cannot come apart. `shell.tsx` records the press in `mobile.dockPressY`, which is `null` rather than a coordinate when the handle saw none, and applies the single transition on `onPointerUp$` (`CA_0024_001`, `CA_0024_002`).
- The click a pointer leaves behind is left alone; the handle acts on a click only when it carries `detail` of `0`, which is what keyboard and assistive activation arrive as and what a pointer's own click never is. Two handlers acting on one interaction would apply two transitions, and which landed would be decided by whichever chunk resolved first (`CA_0024_002`).
- `src/lib/layout.test.ts` proves the classification where it lives: a press that barely moved is a tap, one past the threshold is a swipe in its own direction, and a release with no press is never a swipe. `tests/browser/layout.spec.ts` proves the gesture on both form factors — a release dispatched with no press cycles the dock forward, keyboard activation still cycles it, a swipe past the threshold moves one position each way, and two real taps move exactly one position each, which a click acting alongside the release would carry past (`CA_0024_003`). That browser suite went with the shell before `BO_0200`; the forward cycle it asserted of a tap is the rule `BO_0230_002` replaced, and `layout.test.ts` holds the new one.
- The dock is a layer above the document: `.dock` is positioned with a `z-index` of its own, above every layer a view draws in the flow and below the sheets, the messages and anything dragged. A dock taller than the room left to it takes the workspace's row down to nothing while the workspace's padding still spills over the dock's top edge, and the document's rows are positioned, so they painted over the handle and took the press — on a phone the reader could open the dock and never close it. On a phone the parts that grow — the console, the chips, the `#` offers — scroll inside themselves rather than growing the dock, which never clips, since the agent menu opens upward out of it; and the handle is a fingertip high across the dock's width. `tests/behavior/dock-layer.test.ts` holds the layering where no layout runs: no layer a view draws in the flow reaches the dock's (`BO_0230_003`).

- `ViewDock` on the view bridge carries the one action the active view contributes, and `CommandStrip` renders it at the start of the strip (`CA_0039_001`). Its own component for the reason `InspectorContribution` is one: a view changing what it offers re-renders the dock's action alone, and re-rendering the shell would rebuild the mounted view, which for an editing surface means rebuilding the element under the caret (`CA_0020_001`).
- `ViewAction` is the one named-action type, and both the inspector and the dock render it. One vocabulary with two renderers rather than one per surface, so a view's button in the dock and its button in the drawer cannot come to mean different things (`CA_0020_001`).
- `src/components/shell/composer.tsx` is the command bar over the shell's stores — `CommandStrip` (`command-strip.tsx`), `AgentMenu`, `CommandField` and `ReferenceChips` (`reference-chips.tsx`) — so the render harness mounts the wiring the shell mounts (`testing/composer-host.tsx`, which also shows what `commandTarget` would post and what `reveal` holds). `composer.test.ts` presses the strip, the bar and the chips, each case shown to fail when what it presses is taken out. Run's glyph, the pin and the stale chip's warning are Phosphor `play`, `push-pin` and `warning`, inlined into `icons.tsx` (`CA_0039_001`–`CA_0039_003`). On the served build at pin 275, on a desktop and on a phone, the reader found the references and a pin chip in the bar and pressed each to see its area in both modes, ran a command answered in the console after dismissing the strip and one proposed after bringing it back, toggled command mode from the strip, and closed and opened the dock by its handle on the phone (`CA_0039_007`).
- `.dock-actions` is hidden by the same rule that hides the composer at the collapsed handle. The action area rides with the composer because it is written into that rule rather than declaring positions of its own, which two lists of positions would eventually disagree about (`CA_0020_001`).
- The tab-switch task clears the dock's action along with the inspector contribution, the save state, and the message. All four belong to the view that wrote them, for the tab it was mounted on (`CA_0020_001`).
- A contributed toggle reads as pressed on screen, not only in its `aria-pressed`: at rest it has a border and an empty ring, pressed it takes the accent, a tinted ground and a filled ring (`.dock-actions button[aria-pressed]`). Until `BO_0227` it shared every dock button's transparent, borderless rest, so command mode could be on with nothing showing it — found when a reader, believing the mode was on, selected words and the block opened for editing.
