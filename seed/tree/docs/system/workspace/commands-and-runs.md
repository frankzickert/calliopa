# Commands And Runs

## Commands And Runs

* A command is written in a block of a document and sent from that block ([Command Mode](../../../src/extensions/documents/docs/system/documents/command-mode.md#blocks-as-commands), user decision 2026-09-18), and there is no command surface anywhere else (user decision, 2026-09-20). Each request is a process record, and the right panel lists the runs. There is no message table and no new region.

- The shell consumes the normalized run event contract defined in [Calliopa Agent](../agent/run-lifecycle.md) and never depends on Hermes-native event JSON.
- Runs go side by side: a command is sent while other runs of the reader's, of other people's, or of an extension's trigger are going, and none is refused as busy or queued (`calliopa-bootstrap`'s `BO_0269`, [Run Lifecycle](../agent/run-lifecycle.md)).
- Per-owner chat threads are not built. What the shell has — a block that is the command, a live event stream, cancel, and the reader's runs with their state — is the whole of it, and a run is a process like any other ([Processes](./processes.md), [Agent Activity](./agent-activity.md)).
- `POST /api/workspaces/:id/runs` starts an agent run for a goal. The run record opens before the agent is asked, so a goal the agent refuses still leaves something the reader can watch fail rather than a button that did nothing. The response carries the run and its process; the run is followed after the response is sent, because handing over a goal is quick and the run is not, and the shell learns how it is going by polling the registry rather than by holding a request open (`CA_0022_013`).
- `src/server/agent/hermes.ts` is the only place this application knows Hermes's HTTP shape, and `src/server/agent/conductor.ts` is the only place that drives a run. An agent that is unreachable, unconfigured, or refusing is an ordinary outcome carried back as words: a missing subscription is a state to report, never an exception to swallow (`CA_0022_013`).
- Following a run translates each event through the contract in [Calliopa Agent](../agent/run-lifecycle.md), records it for the console to read back, keeps the process step current, and moves both when a terminal event arrives. A stream that ends without saying how the run finished fails the run, because a run left `running` forever is worse than one that admits it lost track (`CA_0022_013`).
- `POST /api/runs/:id/cancel` asks the agent to stop and moves the registry either way, so a reader who pressed cancel is never left watching a run the agent never answered about. `GET /api/runs/:id/events` is what the console polls, and it answers the normalized contract's events rather than the agent's own JSON (`CA_0022_013`).
- The gate proves the whole path against the real agent: the application's own route opens a run, hands the goal to Hermes, follows the stream, and the process reaches the registry `failed` carrying the agent's own words about being unconfigured. The busy refusal is not asserted there — a run against an unconfigured agent ends in well under a second, so whether the slot is still held is a race rather than a property, and it is proven deterministically against real Postgres instead (`CA_0022_013`).
- A command to a document is written in one of its blocks and sent from its command control (`BO_0267`): it proposes into the document, names the block and the revision sent, and carries the marks made from that block, so *what does #3 mean?* is answered as a proposed block after the prompt. *Answer in the console* retired with it (`BO_0267_009`): the kernel refuses the `answer` delivery by name. The reader still sets where the work goes and the run obeys it, never inferring it from how the command was phrased, which is what the first run from an open document did, searching the web and answering in the console (`BO_0226_005`).
- Which agent performs a command is the reader's choice, in a dropdown at the start of a block's command control (`AgentMenu`, `BO_0228`, reached through `bridge.agents`, `BO_0267_008`): Codex, Claude Code and Hermes, each shown by its character's face — Codey, Clauderic, and for now the Fairytales barista robot — never a vendor's logo. Closed, it shows the chosen agent's face and a caret and is named *Agent: «name»*; open, it lists the three with their faces and names, Hermes's with its model. A native `select` cannot show a face, so it is the select-only combobox pattern: the arrows, `Home`, `End` and a letter move, `Enter` chooses, `Escape`, `Tab`, a press outside or the button again close with the choice unchanged. An agent that cannot run is listed dimmed with its reason as text under its name, `aria-disabled` rather than removed, and choosing it changes nothing. The choice is remembered for the instance (`PUT /api/agent/choice`, `agent-choice.json`), so every device opens on the same agent; when the remembered agent cannot run, it opens on the one the gateway is running and the notice beside the control says so, and a command always names its agent. The faces' crops are recorded beside `AGENT_FACES` in `src/lib/agent-menu.ts`, and every decision the dropdown makes is a function there (`openingAgent`, `menuKey`, `pick`).
- `sendCommand$` on the view bridge sends a block's command (`BO_0267_008`, `CA_0058_002`): it copies the marks the view last reported for the document (`setPointing$`) at the press, refuses a stale passage and a `#n` no mark stands under, and posts `blockCommand` — `artifact`, `delivery: "propose"`, `references` and `source` (the block and the revision sent) — with the chosen agent, the tab's branch and the block's attachments, and no goal, since the kernel reads the words from the revision. It goes through `startRun$`, which follows the started run. The route reads the target back through `readCommandTarget`, which knows that one shape and refuses every other by name — a body naming no document, one with no source, a reference list that is not one, a source missing its block or revision, `delivery: "answer"`, and the `delivery: "start"` the kernel still takes — and refuses a goal beside it, since the words are the block's; the kernel's intake refuses an incoherent one too, and its `400` reaches the reader as a refusal rather than as the agent failing (`BO_0226_004`, `BO_0267_009`). A process opened for a block's command is named by the first line of the words the kernel read (`firstLine`, `conductor.ts`).
- When a run the reader started ends — completed, failed or cancelled, since a run that failed may already have staged — the shell tells the view showing its document once, through `proposed` on the view bridge, and the block editor reads its proposals again and opens them if any stand unanswered, so the reader sees the proposed change where it would land without reopening the tab (`BO_0226_007`).
- What a block's command carries is shown as chips on its command control's line (`ReferenceChips`, `CA_0039_003`, moved there by `BO_0267_012`): one per reference in mark order — `#1`, `#3`, `#5` — then one per fixated block, carrying a pin glyph and no number, since a fixated block is a standing and not a reference. A chip shows its number and says its words in its accessible name — *Reference 3: “…”*, *Fixated: “…”* (`chipName`, `fixatedChipName` in `src/lib/command-target.ts`; the contract's `Pointing.fixated` and `FixatedBlock` follow the state's name, `BO_0272_015`); a stale passage's chip carries the warning icon and border and *stale* in its name. The chips are the view's report itself, the entries `sendCommand$` builds the body from, so what they show and what is sent cannot differ; a fixated block is shown and never sent, since the kernel reads what is fixated from the graph at the run's start. They wrap onto a second line, and the row is absent when nothing is marked or fixated. A chip carries no × and no +: a reference is taken back where it was marked, in the document, which is still the list of what was marked; the chips are the command. Pressing one — click, tap, `Enter` or `Space` — asks the document's view to show its area through `reveal` on the view bridge ([Workspace View Types](./view-types.md)). This supersedes `BO_0226`'s *never an enumeration*, by the user's decision of 2026-09-10, as the disclosure it replaced did (`BO_0227_015`).
- Typing `#` in the block being edited offers its prompt's references by number, narrowing as digits follow, as buttons in a list that opens above the command control; choosing one writes `#<number>` where the caret stood, through the editor's own edit (`BO_0267_013`). A number typed creates nothing (`pendingReference`, `referenceMatches` in `src/lib/command-typeahead.ts`). A block with nothing marked offers nothing.
- A command carrying a stale passage is refused at *Send*, naming it beside the control, as every refusal is shown beside the control that was pressed (`CA_0022_018`): its number may already be in the words, and sending it would name a reference with nothing behind it. So is a command whose words name `#n` that no mark stands under — a mark taken back after its number was written — naming the number and asking for it to be marked again or taken out of the words (`danglingNumbers`, `src/lib/command-typeahead.ts`, checked by `sendCommand$`).
- A run's normalized events stand in its detail in the right panel, read through the registry's own polling rather than a second transport ([Processes](./processes.md), `CA_0058_006`). Cancel is offered only while the run's process is still queued or running, so the control is never there for a run that has already ended (`CA_0022_018`).

## Implementation

- `ViewAction` is the one named-action type, and both the inspector and the bar render it. One vocabulary rather than one per surface, so a view's button in the bar and its button in the drawer cannot come to mean different things (`CA_0020_001`).
- `ReferenceChips` (`reference-chips.tsx`) and the paperclip (`command-attachments.tsx`) are the shell's own components, drawn by a block's command control since `BO_0267_012` and `CA_0058_002`; `reference-chips.test.ts` and `command-attachments.test.ts` press them in the render harness, the second over `testing/attachments-host.tsx`, each case shown to fail when what it presses is taken out. The pin and the stale chip's warning are Phosphor `push-pin` and `warning`, inlined into `icons.tsx` (`CA_0039_003`).
- The tab-switch task clears the inspector contribution, the bar, the save state and the message. Each belongs to the view that wrote it, for the tab it was mounted on (`CA_0020_001`).

## Command File Attachments

- Under `BO_0229`, promoted to draft by the user on 2026-09-10, transferred into this repository's docs the same day and re-transferred here on 2026-09-16 after the split of `ui.shell` into the frame, `documents` and `calliopa-refine` (`BO_0253`): the command bar attaches files to a command, and the run reads them. The kernel's half — the image, the upload and extraction route, the intake and the record, `read_attachment` and the facts measured at the transfer — is `calliopa-bootstrap`'s `docs/system/ui-kernel.md`, *Command File Attachments* (`BO_0229_001`–`BO_0229_006`). The process detail is [Processes](./processes.md) (`BO_0229_011`). Decided 2026-09-10: any file, up to 10 MB per file and 10 per command; contents for text, PDF, images and Office documents; kept with the run, in Garage; access follows the run, which is instance-wide today, with per-person scoping left to `BO_0232`; no process results.
- Attachments are the frame's: they belong to a command and its run, not to a document, so `ui.shell` declares the `attachment` type and nothing of this change is `documents`' or `calliopa-refine`'s. A command aimed at nothing may carry files, and the frame stays total without either extension.
* What a command carries is shown on its control's line, and each attachment can be taken off: a file the reader cannot see there never reaches a run.
* A file refused — over the bound, past the tenth, or failed to upload — is refused in words beside the paperclip, never dropped silently.
- The `attachment` type (`BO_0229_007`) is `ui.shell`'s `ext.blocktype` member, staged with the change through `kernel commit --members`: required `id`, `filename`, `mediaType`, `size` (bytes), `file` (a blob reference) and `textStatus` (`text`, `extracted`, `empty`, `image`, `none`), optional `text` (the extracted text's blob reference). A blob reference is top-level, where CCGW's validation looks for one, so writing the node references its bytes and Garage keeps them past the staging TTL. Nothing contains an attachment and it contains nothing. The kernel's fixture `internal/kernel/serve/testdata/ui-shell-vocabulary.json` holds the same member.
- The upload route (`BO_0229_008`, `src/routes/api/attachments/index.ts` over `uploadAttachment` in `src/server/agent/attachments.ts`): `POST /api/attachments` takes the file as the body with its name in `X-Calliopa-Filename`, percent-encoded as `encodeURIComponent` writes it — a header carries ASCII alone, and the kernel decodes it — refuses a missing or malformed name and a `Content-Length` or body past 10 MB (`413`) before the kernel is asked, and hands the bytes to the kernel's `POST /__kernel/attachments` with the session's cookie forwarded. It answers the kernel's descriptor `{hash, size, mediaType, filename, text, textStatus}`, or the kernel's refusal in its words with its status. Nothing is written to the graph.
- The run route writes the attachments and names them (`BO_0229_009`). `POST /api/workspaces/:id/runs` takes `attachments`, the descriptors the upload answered; `readAttachments` in `src/lib/command-target.ts` refuses by name a value that is not a list, more than ten, and a descriptor with no well-formed hash, size, media type, name or text status, or a `text` without its hash and size. Before `conductRun`, `writeAttachments` writes one `attachment` node per descriptor through the kernel's `write` verb as the signed-in person — a fresh UUID, both blob references, `status: "established"` as a document's creation writes it (without it the verb takes the node but it is nobody's truth, and the run's read at its pin found nothing: the first walk, 2026-09-16), the rationale *attachment «name» sent with a command* — and `startBridgeRun` posts the node ids as `attachments`; a command with none sends no field. A write refused `dangling_blob_reference` — the upload outlived the staging TTL while the bar held it — answers `400` *«name» is no longer stored: it was attached too long ago. Attach it again.*; nodes written before it stay, recording what was sent.
- The paperclip and the attachment chips (`BO_0229_010`, `src/components/shell/command-attachments.tsx` over `src/lib/attachments.ts`). *Attach files* sits on a block's command control, after the agent dropdown: a round control around a visually hidden native `input type="file" multiple` (`data-attach-input`), disabled while a command is sent, with Phosphor's `paperclip`. Choosing files calls `attachFiles`: a file over 10 MB or past the tenth — a refused chip still counts until it is taken off — is refused beside the paperclip in words (`data-attach-refusal`) without an upload; every other file becomes a chip at once and uploads through `uploadFile`, its chip reading *uploading*, then its size once *ready*, or *refused* with a warning glyph and the refusal in its name. The chips sit on the control's line before the reference chips (`data-attachments`, `data-attachment-chip`, `data-attachment-state`), each with a `×` named *Remove «name»*; a chip taken off while it uploads is not brought back by the answer. The control's own store holds the chips. *Send* is refused while a file uploads, naming it (*Wait for «name» to finish uploading.*), as every refusal is shown beside the control that was pressed (`CA_0022_018`); it posts the ready descriptors, read at the press, and clears the chips when the run starts, while a refused run keeps them. On a coarse pointer the paperclip and each `×` are 44px.

## Blocks As Commands

- Under `calliopa-bootstrap`'s `BO_0267`, promoted to draft by the user on 2026-09-18 and transferred here the same day, a block of a document is the command: the person writes it, points from it and sends it from a control on the block, and the dock stops being where a command to a document is written. The editor's half is `documents`' [Command Mode](../../../src/extensions/documents/docs/system/documents/command-mode.md#blocks-as-commands) (`BO_0267_012`–`BO_0267_019`); the kernel's half is `calliopa-bootstrap`'s `ui-kernel.md`, Blocks As Commands (`BO_0267_001`–`BO_0267_006`); the *Execution* section is [Agent Activity](./agent-activity.md#execution) (`BO_0267_010`).

* Every command aimed at a document proposes into it; *Answer in the console* is gone, and a question's answer is a proposed block after the prompt. User decision, 2026-09-18.
- The field left document tabs under `BO_0267_007` and the rest of the shell under `CA_0058_002`: no `Composer`, no strip, no command field, and no agent dropdown, paperclip or chips of the bar's own — a block's command control carries the ones a command needs. `ViewDock`, `bridge.dock`, the strip's action area, the × with its `DeliveryChoice` and `ActionControl`'s dock surface went with `BO_0267_007`; `CommandField`, `CommandStrip` and `Composer` with `CA_0058_002`.

## The Dock Went

- Under `CA_0058`, set to draft by the user on 2026-09-20 and implemented the same day, the command dock was removed and a run is followed in the right panel. ## The Agent List Fits The Screen

- Under `calliopa-bootstrap`'s `BO_0273`, the agent list opens where there is room for it and
  scrolls inside that room (`BO_0273_036`). It opened upward always, which was right in the
  composer at the foot of the page and wrong on a block: a chip near the top of a document pushed
  the list off the screen, and the senders beside the agents made the list long enough for that to
  happen on most blocks.
* A menu that cannot be seen does not exist. The list opens on whichever side of its button has
  more room, is never taller than that room, and scrolls rather than growing past it. User
  decision, 2026-09-22.
- The rule is pure (`roomFor` in `src/lib/agent-menu.ts`), so it is proven without a browser and
  the component only applies what it answers: the side with more room, a height that is what that
  side has with a floor so a cramped chip still shows something to scroll, and the side of the
  button it hangs from — left unless that would cross the right edge. `agent-menu.tsx` measures
  when the list opens, after a frame so there is a width and a height to measure, and falls back
  to a task where there are no animation frames.
- `shell.css` carries the rest: `max-height` from what was measured, capped at `60vh`,
  `overflow-y: auto`, and `overscroll-behavior: contain` so scrolling the list does not scroll the
  document behind it. `data-side="below"` flips it under the button and `data-from="right"` hangs
  it from the right.
- Proven in `src/lib/agent-menu-room.test.ts`: upward from a chip low on the page, downward from
  one near the top, never more room than the side has, the floor for a chip with almost none, and
  the flip to the right edge. The side rule was shown to bite by fixing it to *above*.
