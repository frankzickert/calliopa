# Tool Access

## What The Agent Reaches

- Since `BO_0207_015` the agent reaches Calliopa's content through the kernel toolset alone (`calliopa-kernel`, `hermes.md`): the statement tools over CCGW and the document tools — `list_documents`, `read_document`, `propose_document_changes` — bound per run to the agent principal, the pin and the run's group (`ui-kernel.md`, `BO_0207_004`). The shell's own tool surface and the `cak_` client it authenticated are retired; there is no `pnpm run client` any more, and the kernel toolset's bearer is generated by the stack's bootstrap.
- Documents and blocks ([Block Document Model](../documents/block-document-model.md)) are Calliopa's only domain content, so that is the whole of what the document tools offer; the statement tools reach the rest of the graph unfenced, as `hermes.md` records.
- The `ui.shell.documents` skill teaches the five work item kinds of `propose_document_changes` — `kind`, `claim`, `relate`, `reason`, `derive` — with an example of each (`relateTwoClaims`, `addAClaim`, `setAKind`, `reviseAReason`, `sayWhatABlockRestsOn`) and the rules the base skill carries too (`calliopa-base.working`, `ui-kernel.md` `BO_0244_005`): a relation is proposed with a reason naming the condition that connects its ends, with origin `inferred` or `derived` since a run never declares, and a claim is drafted before a relation is anchored on a block that asserts none, which the relate item does when its end names a block with the claim's words. What `read_document` answers — each block's `blockKind`, claims, provenance and `derivedFrom`, and the document's relations with both ends — is the kernel's (`BO_0244_001`). Both skills are revised through `kernel commit --members` (`BO_0244_011`).
- Since `BO_0249` the same skill teaches the `phase` item and carries the commit convention — a command that commits (*yes, this is the decision*, *treat this as the requirement*) is answered by exactly one `phase` item with a sentence of consequences as the rationale, never by a block or a write. It lives here beside `calliopa-refine.conventions` (`BO_0249_012`) because a person's run reads the base extension's skills and those of the extension declaring the document's intention, and a document without an intention reads no refine skill: found live on 2026-09-15, when the first commit command on such a document was answered by a decision block (`arun-9c86fedc90a75871`). *This* in a commit command is the document: a marked or referenced block says where the decision is stated, and the run may mark it `decision` in the same proposal, but the phase item is the answer — two runs with a marked block answered by a kind item alone before the convention said so (`arun-e59402106762828f`, `arun-b00cb016f8e98bf1`).
- A Claude run holds the kernel toolset and web search and web fetch, and nothing else: `--tools WebSearch,WebFetch` leaves every other built-in tool off — no terminal, no file tools — and `--permission-mode dontAsk` fails a call outside the allowed set rather than waiting for an approval nobody can give. The web tools match Codex's `web_search` (decided 2026-09-10). The runner writes the toolset into a per-run MCP config naming the bearer's variable, never its value (`BO_0228_001`).
- The `codex` runtime brings Codex's own tool surface, so the kernel toolset is registered in Codex's MCP config as well, with the bearer read from the environment at call time rather than written into the file.

* Hermes 0.19.0's MCP configuration is global. There is no per-run or per-session tool-server scoping, and the release's MCP client carries only the tool name and arguments on a call — no session identity and no per-call metadata.

- That constraint decides the architecture rather than a detail: any per-run binding lives inside Calliopa's own tool server, and runs are serialized to one active run at a time. The widening path, if concurrent runs ever matter, is Hermes profiles pointing at per-profile tool endpoints. Not built here.

- The entrypoint registers the toolset with both runtimes on every start. Hermes's `mcp_servers` entry carries the endpoint with the bearer literal in its `Authorization` header, because the release interpolates nothing in that file; Codex's `config.toml` carries the endpoint and `bearer_token_env_var` naming the variable, never the value (`CA_0022_009`).
- The asymmetry is forced, not chosen: inspection of the pinned release found no environment expansion on the way to the MCP header, so a header there has to be a literal. What follows is that Hermes's generated configuration is a secret-bearing file, and it is treated as one — written under a restrictive umask, mode `600`, on the volume and never in the image (`CA_0022_009`).
- The bearer is exported into the gateway's environment so Codex can read it at call time, which puts it in `/proc/1/environ` for anything running as the same user inside the container. That is the cost of Codex's own indirection and it is accepted rather than unnoticed: the container is the outer boundary, and the alternative is the value in a file Codex owns (`CA_0022_009`).
- The gate asserts both registrations, that the Codex file never contains the secret, and that all three generated files are readable only by their owner (`CA_0022_009`).
- `calliopa-refine` is a bundled extension of the graph (`BO_0245_012`, `ui-kernel.md` `BO_0245_007`): its manifest and docs live under `src/extensions/calliopa-refine/` — `docs/system/system.md`, with the `RF` prefix for its change documents, describes the `refine` intention, the judgement record (`judgement` node, `judges` edge, written as truth by the kernel's `record_judgement` tool under the `system` identity class, only by a system run or a merged run) and each skill's rules with the material's examples — and its members, the intention, the `judgement` and `judges` types and the skills `calliopa-refine.conventions` and `refine.derive`, were staged through `kernel commit --members` with it on 2026-09-14. A run under `refine` holds the kernel toolset as every run does; the judgement tool is the one tool the kernel binds only to its own runs.
- `refine.relate` joined the extension's members and its docs on 2026-09-14 (`BO_0247_008`; `src/extensions/calliopa-refine/docs/system/system.md`, the *refine.relate* subsection): the rules of `ui-kernel.md` `BO_0247_001` with the material's cache example, its refusal of generic relatedness and the sharpening that waits on `BO_0248`, and the `relate` and `claim` item shapes of `ui.shell.documents` as its examples.
- `refine.classify` and `refine.pressure` joined the extension's members and its docs on 2026-09-14 (`BO_0248_014`; `src/extensions/calliopa-refine/docs/system/system.md`, the two subsections under *Skills*): the rules of `ui-kernel.md` `BO_0248_001` and `BO_0248_002` with the material's scenarios 3A–3D, the six conditions of §36, the three registers of §55 and the audit example of §40 verbatim; the `judgement` member gained `target`, `resolves` and `resolved` with the resolution rule in its semantics.
- The commit convention of `calliopa-refine` — a commit command answered by proposing the root's `phase` item, never by a write — is `src/extensions/calliopa-refine/docs/system/system.md`, The Commit Convention (`BO_0249_012`).
