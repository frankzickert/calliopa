# Run Lifecycle

## Run Lifecycle

* An agent write is proposal-only. A run stages into a proposal group and a human accepts it; nothing the agent produces becomes truth on its own. This is enforced at the gateway boundary by the caller's identity class, not by the agent's good behavior.
* Runs go side by side, with no limit: one person's several runs, several people's runs, a system run beside a command, and two runs in one document, each staging its own group. Nothing is refused as busy and nothing is queued (`calliopa-bootstrap`'s `BO_0269`, user decision 2026-09-19). Since `BO_0207_015` the run is the kernel's: the shell hands a goal to the kernel's agent bridge and follows it there.
* A run nothing is following is failed rather than left holding the slot. The bound is the run's own age, read by whoever next looks at the agent's slot, so an application that stayed up while the process following a run died recovers the same way one that restarted does, and a crash needs no startup path of its own.
* An abandoned run reaches `failed` carrying an error saying that the application stopped following the run and that the agent may have finished the work. The process state set [Workspace Shell](../workspace/processes.md) fixes is preserved; abandonment is told in the error the console already shows, not in a sixth state word.

- The agent's client is propose-only. A run opens one proposal group per document it touches, stages into it incrementally, and closes naming the groups. A run never reports acceptance, because it cannot cause one.
- Every tool call is bound to the run it names inside the tool server, reads included: the agent container names the kernel's run id on each call — the `X-Calliopa-Run` header, or the MCP request's `_meta` for Hermes's own loop — never the model, and a call naming no active run is refused (`calliopa-bootstrap`'s `BO_0269_001`). A document tool's reads and stagings are reported as that run's activity in the document — the whole document read, the blocks a `read_blocks` names, each item staged against its block — so the person sees them at the blocks while the run is going (`calliopa-bootstrap`'s `BO_0265_003`, [Agent Activity](../workspace/agent-activity.md)).
- Run provenance lands with the group: the goal, the pin the run read at, the runtime and model used, and a reference to the run. The graph already carries provenance for an externally originated write, so this is a use of the existing mechanism.
- A run is a process record, so a cancelled or failed run leaves the registry's own failed state attached to the affected item, as [Workspace Shell](../workspace/processes.md) already specifies.
- The abandonment bound is derived from the follower's own ceiling rather than from how long work takes. `readAgentRunEvents` aborts the whole read at 600 seconds and `ask` buffers the stream to its end, so a followed run cannot outlive that, and the run's row is untouched between its move to `running` and its terminal move. A bound above the ceiling can therefore only ever move a run that is already dead.
- The bound is 15 minutes: the ceiling plus enough margin that a slow start or a loaded machine cannot trip a run that is still being followed.
- A run's refusal is answered in the kernel's words. No run is refused as busy (`calliopa-bootstrap`'s `BO_0269_002`); the kernel's `409` is an intention whose extension is switched off, which `conductRun` answers as reason `conflict` and the run route as `409` (`BO_0264_006`).
- Adoption is not built. An abandoned run is failed, and the proposal group it had already staged survives and is still there to accept, so what a run produced reaches the reader without following the run again.

- Since `BO_0207_015` a run is the kernel agent bridge's (`ui-kernel.md`, `BO_0089_012`): `POST /api/workspaces/:id/runs` hands the goal to `POST /__kernel/agent/runs`, which binds the agent principal, the identity class, the pin and the run's proposal group server-side and starts Hermes with the kernel toolset — the document tools included (`BO_0207_004`); the bridge's refusal is answered in its own words. A goal the bridge takes gets a process in the registry naming the run (`runId` on the process record), followed after the response is sent: `followRun` in `src/server/agent/conductor.ts` reads the bridge's event stream and moves the process — the step while it works, `completed`, `failed` or `cancelled` when it ends, and `failed` with a reason when the stream closes without saying. `src/server/agent/bridge.ts` is the shell's whole knowledge of the bridge: start, read, cancel, and the stream read frame by frame with the bridge's vocabulary mapped onto the console's contract.
- `src/server/agent/run-events.ts` is the normalized run event contract the console reads: run started, assistant delta, tool started, tool completed, document activity (`BO_0265_006`), run completed, run failed, run cancelled — each end carrying `document` when the run was started from a command and created one (`BO_0251_007`). The bridge's `proposal.staged` is reported as the agent saying which group it staged into. The Hermes-shaped translator that lived here went with the shell's own conductor; the bridge normalizes, and the shell never sees Hermes-native JSON.
- `GET /api/runs/:id/events` is what the console polls: the bridge answers its buffered history first, and the poll leaves once the stream goes quiet. `POST /api/runs/:id/cancel` asks the bridge to stop the run and moves its process either way.
- The run table, the client record the run belonged to (`api_client`), the shell's Hermes client and its MCP and JSON API surfaces are retired; the tables stay unread in the retired database until `BO_0207_009`. Runs go side by side in the bridge, and a process a run left behind is the registry's failed process as before.
- `src/server/agent/proposed.ts` answers what a run proposed from the bridge's own record of the run: its group's touched set names the blocks it staged, each is placed by its containment or by the containment the group stages, and the count of unanswered items per document is the document's own reading of the group, so the process detail and the editor cannot disagree.
- `src/server/agent/bridge.test.ts` proves the mapping of every bridge event type onto the contract, that an unknown type is reported as nothing, and that the stream parses frame by frame with a non-JSON frame kept rather than dropped; the transport is proven where a kernel with an agent bridge runs.

## System Runs

* A system run is a run an extension's trigger started, under that extension's intention, after a change it cares about settles — `calliopa-refine`'s under `refine` today — and a person's command never absorbs one (`BO_0245`; `BO_0264`, user decision 2026-09-18; the kernel half in `ui-kernel.md`, Extension-Triggered Runs). It is attributable and quiet: its record says it was the kernel's, what triggered it and what it concluded, it is a process like any run, and it raises no notice of its own.

- The shell follows a system run as it follows a person's (`BO_0245_009`, `BO_0264_017`): `src/server/agent/bridge.ts` maps the record's `trigger`, `extension`, `subject`, `since`, `artifact` and `conclusion` (`triggerOf`, `conclusionOf`, which reads an older record's `judgement` words where no conclusion is set), and `listProcesses` (`src/server/processes.ts`) syncs the bridge's system runs (`listBridgeRuns`) into process records under the `system` workspace (`SYSTEM_WORKSPACE`, `src/lib/process.ts`) — titled by the run's goal, which is the triggering extension's own words, the document it proposes into as the affected item named by the extension listing documents (`itemLabel`), `triggeredBy` naming the extension and the revision, the state following the run's, the conclusion as `concluded` — and lists them in every workspace, so a system run that started while no tab was open still appears; `POST /api/runs/:id/cancel` cancels it as any run. A system run is never created from the composer, so the dock does not open for it and the busy refusal a person's command may meet stays as it is; any run whose record carries a conclusion gets it on its process when it ends (`conductor.ts`). A system run's end reaches the open view as every process's does ([Processes](../workspace/processes.md), `CA_0063_002`): a process that has ended for a document, not already known when the page loaded and not a run this session follows, raises the view's `proposed` signal for that document (`endedForDocuments`, `runProposed` in `shell.tsx`), so its candidates appear without a reload as a person's run's proposals do.
- Verified 2026-09-18 on the tree (`BO_0264_017`): `tsc --noEmit` clean and the unit project green; the process detail's trigger and conclusion are read in the walk (`calliopa-refine` `BO_0264_019`).

## Concurrent And Faster Runs

- Under `calliopa-bootstrap`'s `BO_0269`, set to draft by the user on 2026-09-19 and transferred here the same day: several runs go at once, and every command is sent *Fast* or *Thorough*. The kernel's half and the decisions are `calliopa-bootstrap`'s `docs/system/ui-kernel.md`, *Concurrent And Faster Runs* (`BO_0269_001`–`BO_0269_006`), the agent container's `hermes.md` (`BO_0269_007`–`BO_0269_013`); the editor's half is `documents`' [The Agent At Work](../../../src/extensions/documents/docs/system/documents/agent-at-work.md), *Several Runs At Once*.
* Every command carries a speed, *Fast* or *Thorough*, for every agent: Fast is preselected, the person's last choice is remembered for that person, and Thorough is what a run did before. User decision, 2026-09-19.
* If Hermes stays much slower than the other agents for upstream reasons, the agent menu names it the slower agent; it stays on offer. User decision, 2026-09-19.
- The shell follows every run it started (`BO_0269_014`). `shell.tsx`'s `run` store keeps `followed`, one `FollowedRun` per run the session started (`src/lib/followed-runs.ts`: its document, its agent, its events, and whether its end was told and its started document opened), and the poll reads each run not seen to end — on the 750 ms clock while one of them is aimed at a document, on the registry's 2 s poll otherwise. The view bridge's `activity` is `{ runs, seq }`, one `ViewRunActivity` per followed run aimed at a document (`activitiesOf`), `seq` rising when any changes (`sameActivities`), so a view hears two runs on one document. A run's end is told once through `proposed`, one run per read since the signal carries one document, and a started document opens once. The console shows the last run started, and *Cancel run* cancels it; the *Execution* section cancels any. The composer and a block's command send while runs go: `sending` holds only for the press's own request.
- The speed (`BO_0269_015`). `SpeedToggle` (`src/components/shell/speed-toggle.tsx`) stands after `AgentMenu` in the composer and in a block's command control: one button showing the speed it holds — Phosphor `lightning` for *Fast*, at the accent, `hourglass-medium` for *Thorough* — named *Speed: Fast* or *Speed: Thorough*, titled with what a press does, and switching on a press. The speed is the run store's `speed`, handed to a view with `agents` and chosen through `chooseSpeed$`; `GET /api/agent/runtimes` answers the signed-in person's last speed from the kernel (`rememberedSpeed`, `GET /__kernel/agent/config`), fast when none, and `loadAgents` opens on it. Every run the shell starts carries `speed`, through the run route, `conductRun` and `startBridgeRun`; the kernel remembers it for the person when the run starts.
- Tests on the tree (`BO_0269_017`): `src/lib/followed-runs.test.ts` — two runs followed until each ends, their activities in their own documents in the order they started, each end told once on its own run; `agent-at-work.test.ts` in `documents` for two runs in one document; `composer.test.ts` and `command-control.test.ts` for the speed after the agent, Fast until pressed; `bridge.test.ts` for the speed in the intake's body and none without a choice; `per-person.test.ts` for the kernel's `409` answered as `conflict`. `tsc --noEmit` clean and the unit project green (1009 tests).
- Hermes is not named the slower agent (`BO_0269_016`): measured on the instance after the change, it took 15–38 s where Codex took 20–37 s (`calliopa-bootstrap`'s `hermes.md`, *Concurrent And Faster Runs*).
