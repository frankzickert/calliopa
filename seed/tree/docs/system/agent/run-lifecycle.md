# Run Lifecycle

## Run Lifecycle

* An agent write is proposal-only. A run stages into a proposal group and a human accepts it; nothing the agent produces becomes truth on its own. This is enforced at the gateway boundary by the caller's identity class, not by the agent's good behavior.
* One active run at a time. A second goal while a run is active is refused as busy, not buffered, which the global MCP configuration above forces anyway. Since `BO_0207_015` the run is the kernel's: the shell hands a goal to the kernel's agent bridge and follows it there.
* A run nothing is following is failed rather than left holding the slot. The bound is the run's own age, read by whoever next looks at the agent's slot, so an application that stayed up while the process following a run died recovers the same way one that restarted does, and a crash needs no startup path of its own.
* An abandoned run reaches `failed` carrying an error saying that the application stopped following the run and that the agent may have finished the work. The process state set [Workspace Shell](../workspace/processes.md) fixes is preserved; abandonment is told in the error the console already shows, not in a sixth state word.
* The busy refusal says what holds the slot: whether the run belongs to this workspace or another one, its goal, how long it has been running, and its id. It is the only thing a reader outside the run's own workspace ever sees of it, so it must not report an agent at work when nothing is following the run. A run another person holds is named as *another person's run* with how long it has been running, and never by its goal or id, since a person's run is theirs and the owner's alone (`BO_0232_007`, user decision 2026-09-16).

- The agent's client is propose-only. A run opens one proposal group per document it touches, stages into it incrementally, and closes naming the groups. A run never reports acceptance, because it cannot cause one.
- A staging tool call is bound to the caller's one active run inside the tool server, and a staging call with no active run is refused. Reads are not bound: nothing about reading a document needs attributing, and refusing reads would make an unwired agent indistinguishable from a broken one.
- Run provenance lands with the group: the goal, the pin the run read at, the runtime and model used, and a reference to the run. The graph already carries provenance for an externally originated write, so this is a use of the existing mechanism.
- A run is a process record, so a cancelled or failed run leaves the registry's own failed state attached to the affected item, as [Workspace Shell](../workspace/processes.md) already specifies.
- The abandonment bound is derived from the follower's own ceiling rather than from how long work takes. `readAgentRunEvents` aborts the whole read at 600 seconds and `ask` buffers the stream to its end, so a followed run cannot outlive that, and the run's row is untouched between its move to `running` and its terminal move. A bound above the ceiling can therefore only ever move a run that is already dead.
- The bound is 15 minutes: the ceiling plus enough margin that a slow start or a loaded machine cannot trip a run that is still being followed.
- The refusal carries the run's id because that is the handle `POST /api/runs/:id/cancel` takes, and a reader outside the run's own workspace is offered no cancel control. It says whether the holder is here or elsewhere rather than naming the workspace, because a workspace record has no name to say: it stores tabs and layout, not a label, and a uuid names nothing a reader recognises.
- Adoption is not built. An abandoned run is failed, and the proposal group it had already staged survives and is still there to accept, so what a run produced reaches the reader without following the run again.

- Since `BO_0207_015` a run is the kernel agent bridge's (`ui-kernel.md`, `BO_0089_012`): `POST /api/workspaces/:id/runs` hands the goal to `POST /__kernel/agent/runs`, which binds the agent principal, the identity class, the pin and the run's proposal group server-side and starts Hermes with the kernel toolset — the document tools included (`BO_0207_004`); the bridge's refusal is answered in its own words, busy as 409. A goal the bridge takes gets a process in the registry naming the run (`runId` on the process record), followed after the response is sent: `followRun` in `src/server/agent/conductor.ts` reads the bridge's event stream and moves the process — the step while it works, `completed`, `failed` or `cancelled` when it ends, and `failed` with a reason when the stream closes without saying. `src/server/agent/bridge.ts` is the shell's whole knowledge of the bridge: start, read, cancel, and the stream read frame by frame with the bridge's vocabulary mapped onto the console's contract.
- `src/server/agent/run-events.ts` is the normalized run event contract the console reads: run started, assistant delta, tool started, tool completed, run completed, run failed, run cancelled — each end carrying `document` when the run was started from a command and created one (`BO_0251_007`). The bridge's `proposal.staged` is reported as the agent saying which group it staged into. The Hermes-shaped translator that lived here went with the shell's own conductor; the bridge normalizes, and the shell never sees Hermes-native JSON.
- `GET /api/runs/:id/events` is what the console polls: the bridge answers its buffered history first, and the poll leaves once the stream goes quiet. `POST /api/runs/:id/cancel` asks the bridge to stop the run and moves its process either way.
- The run table, the client record the run belonged to (`api_client`), the shell's Hermes client and its MCP and JSON API surfaces are retired; the tables stay unread in the retired database until `BO_0207_009`. The slot, the abandonment bound and the busy refusal are the bridge's now, and a process a run left behind is the registry's failed process as before.
- `src/server/agent/proposed.ts` answers what a run proposed from the bridge's own record of the run: its group's touched set names the blocks it staged, each is placed by its containment or by the containment the group stages, and the count of unanswered items per document is the document's own reading of the group, so the process detail and the editor cannot disagree.
- `src/server/agent/bridge.test.ts` proves the mapping of every bridge event type onto the contract, that an unknown type is reported as nothing, and that the stream parses frame by frame with a non-JSON frame kept rather than dropped; the transport is proven where a kernel with an agent bridge runs.

## System Runs

* A system run is the kernel's own run under the `refine` intention, scheduled after a change to a document settles and folded into a person's command for the same document where it can be (`BO_0245`; the kernel half in `ui-kernel.md`, System Runs). It is attributable and quiet: its record says it was the kernel's, what triggered it and what it concluded, it is a process like any run, and it raises no notice of its own.

- The shell follows a system run as it follows a person's (`BO_0245_009`): `src/server/agent/bridge.ts` maps the record's `trigger`, `refined`, `refinedFrom`, `refinedAt` and `judgement` (`triggerOf`, `judgementWords`), and `listProcesses` (`src/server/processes.ts`) syncs the bridge's system runs (`listBridgeRuns`) into process records under the `system` workspace (`SYSTEM_WORKSPACE`, `src/lib/process.ts`) — title *Refine: <document title>*, the document as the affected item, the state following the run's, the judgement's words as `concluded` — and lists them in every workspace, so a system run that started while no tab was open still appears; `POST /api/runs/:id/cancel` cancels it as any run. A system run is never created from the composer, so the dock does not open for it and the busy refusal a person's command may meet stays as it is; a person's run that carried a refinement gets `trigger`, `refined` and `concluded` on its process when it ends (`conductor.ts`). A system run's end reaches the open view through the process poll: a system process that has ended for a document, and was not already known when the page loaded, raises the view's `proposed` signal for that document (`runProposed` in `shell.tsx`), so the derived candidates appear without a reload as a person's run's proposals do. The shell's server forwards the kernel's refinement route as `GET`/`PUT /api/agent/refinement` (`src/routes/api/agent/refinement/`, `parseRefinement` in `src/lib/refinement.ts`).
