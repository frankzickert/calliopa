# UI Kernel

## Purpose

- The UI kernel is the fixed trust anchor of the graph-hosted extensible UI: the part that exists outside the graph to turn graph content into a running process. It is a bootloader (CCGW client, materializer, toolchain harness) and a CLI, with no opinions about what the UI is — a generic "run graph pin N" machine whose source lives in this repository and ships as compiled images.
- This document carries the toolchain-harness work transferred from change `BO_0092`, the materializer-checkout work transferred from change `BO_0093`, the materializer-commit work transferred from change `BO_0094`, the boot/CLI orchestration transferred from change `BO_0095`, and the kernel-gated acceptance work transferred from change `BO_0103`.
- The toolchain harness runs install, build, dev, and serve against a given working tree with pnpm under Node. Which working tree it runs against is someone else's concern — the harness is fully implementable and testable against fixture trees on disk.
- The materializer's read half produces that working tree: `kernel checkout` projects the extension namespace at a projection spec into a directory, with a lockfile mapping every file back to the graph. It is read-only end to end — it never writes to the graph.
- The materializer's write half closes the loop: `kernel status`/`diff` compare the working tree against the lockfile, and `kernel commit` packages the difference into one atomic change through CCGW with human provenance — landing as accepted truth or as a proposal, at the human's choice. This is the single write path humans use for extension content; Hermes produces the same change shape through its own proposal-only identity (`BO_0089`).
- Boot orchestration composes the parts into `kernel serve`: dev mode runs checkout → watch → the toolchain dev server behind a kernel proxy that renders the non-forgeable preview banner; prod mode materializes the promoted release pin, builds, and serves, rebooting on promotion. The CLI verbs (`proposal …`, `pin`, `rollback`) are the permanent recovery path — the serial console for when an accepted change breaks the shell that would otherwise review the fix — exercised routinely, not only in emergencies.

## Fixed Constraints

* The kernel follows the repo's `cmd/<binary>` + `internal/<component>` convention: one `cmd/kernel` binary with `internal/kernel/toolchain`, `internal/kernel/materializer`, and `internal/kernel/ccgwclient` behind it. Package-boundary verification keeps the kernel out of `internal/ccgw` and every cell-internal package.
* The package manager is pnpm. The harness invokes `pnpm install --frozen-lockfile`, `pnpm run build`, `pnpm run dev`, and `pnpm run serve` — so a conventions-following tree must carry `pnpm-lock.yaml` and define `build`, `dev`, and `serve` scripts in its root `package.json`. `serve` runs the built output and binds to the port the kernel supplies through the environment, so the tree decides its own output shape (SSR or static) and the kernel keeps no opinion about it. This is the fixed kernel's only assumption about tree content; the contract joins the tree conventions recorded with `BO_0086`'s transfer.
* The kernel container image carries Node (pinned LTS), pnpm (pinned version), and the kernel binary — nothing else. Vite and the Qwik optimizer are deliberately not baked in; they arrive from the tree's own lockfile at install time, per the derived-`node_modules` decision in `BO_0082`.
* The health signal is the toolchain package's Go API, consumed in-process by boot orchestration (`BO_0095`): `install` and `build` are synchronous — success, or an error carrying the exit code and captured output; `dev` and `serve` are lifecycle-managed — readiness derived from the dev server's listening signal (dev) or from the process answering an HTTP request on the kernel-supplied port (serve), the bound address exposed to the caller, stop via context cancellation, and failure-after-start delivered as an exit notification.
* Verification follows the no-mock rule: real fixture trees, real pnpm runs. Hermetic means lockfile-determined results, not no-network — a warm pnpm content-addressable store runs offline, a cold store falls back to the registry.
* The projection spec is `(pin, optional single proposal overlay)`: the pin is a fixed `dataRevision` — immutable forever, the prod shape — or the symbolic established head, re-resolved as truth advances, which is `BO_0082`'s dev mode.
* Overlays come from at most one proposal, and only one authored by the session's own Hermes instance or by the operating human themselves — both are the operator's own code, which is what the restriction protects (`BO_0082`'s dev-mode trust posture).
* Human work is never destroyed silently: a re-projection never overwrites or deletes a file that no longer matches its lockfile entry, and never touches a file the lockfile does not know. `--force` is the deliberate reset.
* Both commit modes produce the same change shape — a `BO_0084` proposal group — the difference being only whether acceptance is implicit in the write. Truth mode is not a second write path; it is the proposal path with the acceptance folded into the same transaction (`BO_0082`'s uniform-change-shape decision).
* Staleness is judged per touched Block, never by head movement alone — the global `dataRevision` sequence advances on unrelated writes, so "head moved" is not a conflict. A commit is stale exactly when a Block it touches has established revisions newer than the lockfile baseline.
* The release pin lives in the graph: a kernel-owned `kernel.releasepin` Block written through CCGW as a human-provenance truth write. Pin history is revision history — `rollback` is re-pinning to a prior value — and the shell can render the current pin. The kernel additionally caches the last successfully built-and-served pin on its data volume, so the fallback path never depends on a graph read.
* The preview *state* is non-forgeable: kernel-held, driven only by the kernel's own preview control, and rendered as the banner by the kernel proxy outside the Vite pipeline — `vite.config` is graph content, so nothing graph-supplied can forge its acceptance state (`BO_0082`'s safety invariant). The injected banner node itself is same-document and therefore scriptable — a script can hide it, not falsify the state — which is why nothing load-bearing depends on the banner's visibility: while any overlay is active, acceptance is refused outright (`BO_0103_005`).

## Scope Boundary

- The toolchain-harness work has no CCGW client, no materializer, and no graph access of any kind.
- The checkout work is read-only end to end; the graph writes belong to the commit work. The shared-CCGW additions are two: the head route (checkout) and the truth-mode named operation (commit).
- The commit work creates changes but never reviews or accepts them: the review verbs are the CLI's (`BO_0095`) and the shell's (`BO_0098`). No merge or rebase machinery — a stale truth commit is resolved by re-checkout, not by merging. No rename detection — a renamed file is a removal plus an addition, and the new Block starts its own revision history; path-preserving continuity, if ever wanted, is a follow-up.
- The boot/CLI work completes the porcelain: `kernel serve`, `proposal …`, `pin`, `rollback`. It ships no shell content — serve works against any conventions-following tree, and an empty or root-less tree gets the built-in fallback scaffold.
- The agent-bridge work transferred from `BO_0089` (tasks `BO_0089_012`–`BO_0089_015` below) is the kernel half of the [Hermes Agent Service](./hermes.md): the bridge endpoints, the run-scoped workspace tools, the commit extensions, and the CLI intake verb, verified together with their Hermes counterparts.

## Toolchain Harness

- `cmd/kernel` is the kernel binary. Its verbs are `kernel toolchain install|build|dev --tree <dir>`, logging goes to stderr, and the exit discipline is 0 on success, 1 on command failure, 2 on usage errors. `BO_0092_001`
- `internal/kernel/toolchain` `Install` runs `pnpm install --frozen-lockfile` against the given tree — same lockfile, same result. Failure returns a `CommandError` carrying the exit code and the captured combined output. `BO_0092_002`
- `Build` runs `pnpm run build` against the given tree synchronously with the same success/`CommandError` contract. `BO_0092_003`
- `Build` runs the tree's `typecheck` script after `pnpm run build` succeeds, under the same `CommandError` contract, so a tree that bundles but does not type-check fails the same way a broken build does. Both callers inherit it — `internal/kernel/serve/prod.go` (the promotion gate) and `internal/kernel/agenttools/workspace.go` (the agent workspace, where the defects that motivated this were written) — and there is no path that promotes around it. **The order is load-bearing, not stylistic:** `src/registry.gen.tsx` is generated by the registry plugin during the build and is absent from a freshly materialized tree, so a typecheck run first fails with `TS2307` on `frame.tsx` and a cascade of spurious `TS7006`. Measured cost is 814ms against a 4557ms build. `kernel commit` is unaffected by construction — it does not call `Build`. **A tree declaring no `typecheck` script is not gated and says so** — `toolchain: tree declares no typecheck script — this build is NOT type-gated` on the same stream the promotion is read from. Tolerating the absence is deliberate: the tree owns its scripts and a plain-JavaScript tree has nothing to check, which the `minimal-tree` fixture is. Requiring it was rejected because every tree in existence lacked it, making the change a flag day; announcing it is what keeps a lost gate from being a silent one. `BO_0131_001`
- `StartDev` runs `pnpm run dev` as a lifecycle-managed process group: it returns once the dev server reports the address it listens on (the ANSI-stripped `Local:` listening signal), exposes that URL to the caller, stops the whole group on context cancellation (SIGTERM, SIGKILL after a 5-second grace), and delivers a self-exit through `Done`/`Err` as a `CommandError` exit notification. A stop caused by cancellation is not an error. `BO_0092_004`
- `infra/kernel/Dockerfile` builds the kernel image: Node 22.22.2 (pinned LTS), pnpm 11.9.0, and the kernel binary. Vite and the Qwik optimizer are absent from the image and resolve from a tree's own lockfile at install time, verified by an in-container install and build of the fixture tree. `BO_0092_005`
- Harness verification runs real pnpm against copies of `internal/kernel/toolchain/testdata/minimal-tree` — install, frozen-lockfile drift refusal, build, broken-source build failure, dev serve-then-cancel, and missing-dev-script start failure — resolving from pnpm's content-addressable store. `BO_0092_006`
- `internal/architecture/kernel_package_boundary_test.go` enforces the package boundary: kernel source imports no cell-internal package.
- Dependency build-script approvals are tree content, not kernel configuration: pnpm 11 runs a dependency's install scripts only when the tree approves it via `allowBuilds` in its own `pnpm-workspace.yaml` (the fixture tree approves `esbuild`); an unapproved build script fails the install. pnpm 11 no longer reads the `pnpm` field in `package.json`.

## Materializer Checkout

- `kernel checkout --tree <dir> --ccgw <url> [--pin head|N] [--proposal <id>] [--principal <name>] [--hermes-principal <name>] [--force] [--watch] [--interval <duration>]` projects the extension namespace per the [Extension Model](./extension-model.md) conventions: each `ext.source` Block to `src/extensions/<extId>/<path>` — root-mapped Blocks to the working-tree root — manifests to `manifest.json`, and UI contributions to one file each under `contributions/`. Exit discipline extends the kernel's: 0 clean, 1 failure, 2 usage, 3 completed with skipped-file conflicts, which are listed on stderr. `BO_0093_003` `BO_0093_005`
- The head route: `GET /v1/head` returns the current head `dataRevision` from the global sequence without advancing it (see [CCGW](./ccgw.md)). CCGW takes the pin as request input but never reports what head was, so without the route a head checkout could neither record its lockfile baseline nor project consistently. Checkout resolves a head pin by probing the route once per pass and pinning every projection query of that pass at the result — one consistent snapshot. `BO_0093_002`
- `internal/kernel/ccgwclient` is the kernel's CCGW client — the query envelope with the `dataRevision` pin and `proposalOverlay` fields, the head probe, and since the commit half the write side too: `Mutate` submits a mutation script under the human identity class, reporting the allocated `dataRevision` and structured refusals a caller can react to by code — carrying its own wire types so kernel source imports no cell-internal package. `BO_0093_001` `BO_0094_003`
- The lockfile is kernel-owned, `graph.lock.json` at the working-tree root, rewritten as part of every re-projection pass and read back through `materializer.LoadLockfile` (the commit half's baseline reader). Tree level it records the resolved baseline — the concrete `dataRevision` the pin resolved to, plus the overlay proposal if any — which is `BO_0094`'s input for refusing commits against a stale baseline. File level it records one entry per projected file: `(blockId, revision, proposalId?)` plus the file's content hash — the graph route-back for stack traces, citations, and diffs, and the local-modification detector. A file entry carries the overlay exactly when its projected revision is the overlay's staged candidate. `BO_0093_004`
- Dirty-tree rules, enforced by every re-projection pass (checkout into a non-empty tree, overlay swap, watch): a projected file whose content still matches its lockfile hash is freely updated or deleted; a file absent from the lockfile (`node_modules`, build output, new human files) is never touched — including a foreign file already sitting at a projected path, which is skipped and surfaced; a file that no longer matches is locally modified — skipped, surfaced as a conflict, and the pass continues, with the prior lockfile entry kept so the modification retains its recorded baseline. `--force` restores clobber for deliberate resets. Human work is never destroyed silently. `BO_0093_005`
- Overlay rules: exactly one proposal, carried by the `proposalOverlay` envelope field, refused unless the group is open and its provenance names the session's own Hermes instance (`--hermes-principal`) or the operating human (`--principal`). Pass mechanics are the "atomic swap": passes are serialized, each computes its full target from its one pinned snapshot, then applies per-file atomic writes (temp file + rename; adds and updates before deletes, emptied directories pruned) — no pass mixes two specs, no reader ever sees a torn file, and a watching Vite sees a burst of renames sourced from a single consistent snapshot. `BO_0093_006`
- Watch mode (`--watch`) polls the head route at the configured interval and re-projects when head moves past the last observed revision. Every write — truth or proposal staging alike — allocates from the same global `dataRevision` sequence, so one monotonic comparison covers both triggers: the established head advancing (when the spec pins head) and the overlaid proposal gaining a new revision. An unrelated-domain write costs one wasted pass, which the lockfile diff makes cheap; a fixed pin with no overlay makes watch a no-op. Namespace-scoped change detection and a subscription surface are follow-ups. `BO_0093_007`
- Verification runs against a real CCGW instance — the real service over real stores behind a real HTTP server, reached by the kernel client exactly as production reaches it — with a seeded fixture extension namespace: fixed-pin and head checkout, moved-truth pinning, overlay materialization, swap-back, and authorship refusal, every dirty-tree rule, blob-reference surfacing, and watch re-projection on head advance. The package-boundary verification exempts `_test.go` files: the boundary protects the shipped binary's only doorway, and the in-process service is test-only scaffolding outside the kernel build graph. `BO_0093_009`
- A blob-referenced `ext.source` (`_kind: "blob"` in place of text code) materializes through CCGW's blob route (`ccgwclient.FetchBlob`): the bytes are fetched and verified locally against the reference hash before anything lands on disk — the transport is trusted for delivery, never for integrity — and the reference hash is recorded on the file's lockfile entry (`blob`, which for content-addressed bytes coincides with the entry's content hash). A dangling reference or a hash mismatch is a per-file conflict and the pass continues, per the dirty-tree posture. Verified in `internal/kernel/materializer/blob_roundtrip_test.go` (real CCGW service over a real Garage-backed store, byte-identical round trip including a staged overlay), the dangling-reference conflict in `materializer_test.go`, and the mismatch defense in `blob_verify_test.go`. `BO_0093_008`

## Materializer Commit

- `kernel status --tree <dir>` and `kernel diff --tree <dir>` compare the working tree against `graph.lock.json` locally — no graph round-trip: changed, added, and removed files, with hashes, sizes, and media types (`diff` the full detail, `status` the summary). Files outside the extension namespace and the lockfile — `node_modules`, build output, dot-prefixed names — are foreign, exactly as the dirty-tree rules treat them. Exit 0 when clean, 3 when dirty. `BO_0094_001`
- `kernel commit --tree <dir> --ccgw <url> -m <rationale> --principal <name> [--truth] [--map-root <extId>] [--identity human|agent]` packages the full diff as one mutation script in one request — never trickled per file, in either mode (`internal/kernel/materializer/commit.go`): `BO_0094_003`
- `--map-root` also widens added-file discovery beyond the tree root's immediate files: root-mapped Blocks materialize to nested paths (`src/root.tsx`, `src/routes/…`), so a commit mapping root files walks the whole tree outside the extension namespace, with derived directories (`node_modules`, `dist`, `server`) and dot-entries staying foreign. Without the flag, discovery keeps `BO_0094_001`'s scope, so ordinary `status`/`diff` never surface nested foreign files. Amends `BO_0094_001`/`BO_0094_003`, surfaced by the import. `BO_0099_007`
  - changed `ext.source` files become one `SET` per Block (code and hash), folding into one new revision;
  - changed manifest and contribution files — derived JSON — are parsed back into content properties, cleared keys expressed as null assignments so the whole edit folds into one revision; changing a Block's `id` is refused — ids are identity, not content;
  - added files become new Blocks with `partOf` membership, the owning extension attributed from the `src/extensions/<extId>/<path>` convention; a new extension arrives by adding its `manifest.json` and members in the same commit, and the subtree projects on the next checkout;
  - removed files become the group's removal intents (archive-node plus close of the member's `partOf` relation) per `BO_0084`;
  - one pinned read of the namespace at the lockfile baseline supplies old content, manifest nodes, and relation ids — reads, so atomicity is untouched.
- Proposal mode (the default) stages the script into a fresh group whose recorded `baseDataRevision` is the lockfile baseline (the envelope `dataRevision`, `docs/system/ccgw.md` §2). Staging never locks: a stale baseline stages anyway and the conflict is reported at acceptance, never auto-resolved. `BO_0094_004`
- The reported conflict is real and fires: `BO_0160`'s first group based at 2540, `BO_0180` established a newer `artifact.components/reading.tsx` while it was being built, and acceptance refused it whole with `mutation_resolution_failed … conflicts with truth that moved past its base revision 2540`, naming the collided node. The repair is re-checkout rather than merge in the graph — project both upstream revisions, three-way merge locally, reject the stale group, re-baseline, restage — and it is cheap exactly when the two changes touch different parts of the file, which two surface changes against one component usually do.
- [ ] BO_0160_008 **A second collision on the same file was *not* refused, and the two outcomes have to be reconciled.** Hours after the above, `BO_0189` established `artifact.components/reading.tsx` and `reading.css` at 2980 from a pre-`BO_0160` base, replacing the versions `BO_0160` had established at 2911 and leaving head unbuildable — `write.ts` at 2911 takes `Run[]` where the restored `reading.tsx` passes strings, five `TS2345` errors under the tree's own `typecheck`, so the promotion gate (`BO_0131_001`) would have refused head and neither change could ship. Establish whether that acceptance carried the doorway's `override` (`BO_0113_007`, which surfaces drift and accepts over it) or whether the check did not see the collision, and record the answer here. **The two answers call for different work**: the first is a question about how loudly an override states what it is discarding, the second is a defect in the one guarantee that makes concurrent surface work safe. Until it is answered, a long-running change against a shared file should re-read head before accepting.
- An overlaid tree stages into its overlay group instead of opening a second one: successive commits revise the same open proposal, the lockfile keeps the overlay, and acceptance establishes the final staged state as one unit. A truth commit from an overlaid tree stays refused — `COMMIT PROPOSAL` requires a fresh group; an existing group is `ACCEPT PROPOSAL`'s job. `BO_0089_013`
- `--identity agent` declares the agent identity class for a Hermes-run commit under the agent principal — the same script shape and atomicity, with CCGW's identity policy (not kernel code) making the change proposal-only: an agent-class truth commit is refused wholly by CCGW and writes nothing. `BO_0089_013`
- Truth mode appends `COMMIT PROPOSAL` (`docs/system/ccgw.md` §6.5a): the same staged group accepted in the same transaction, human identity only, refused with `stale_baseline_conflict` when a touched Block's established truth moved past the baseline — the kernel maps the collided ids back to paths in its failure message. There is no later review step to catch it; re-checkout and retry. `BO_0094_002` `BO_0094_004`
- Per-file refusals never silently commit and never abort the rest: a new root file without `--map-root` — no extension is attributable from its path, and root mapping is policy-gated — an id change, binary content in a derived JSON file, or a JSON file differing only in formatting is listed with its reason, the commit proceeds with the remainder, and the exit is 3. A commit whose every difference was refused, a clean tree, or an overlaid tree (the overlay proposal owns those changes) is refused whole. `BO_0094_005`
- A successful commit rewrites the lockfile so the tree is immediately clean: truth mode re-baselines at the mutation response's `resolvedDataRevision`; proposal mode keeps the checkout pin, sets the tree-level overlay to the new group, and points file entries at the staged candidate revisions. `BO_0094_006`
- Commit verification runs against the same real CCGW instance as checkout — real service, real stores, real HTTP, no mocks (`internal/kernel/materializer/commit_test.go`): proposal and truth commits of changed, added, and removed files, the stale-baseline truth refusal and proposal acceptance-time conflict, the new-root-file refusal and `--map-root`, new-extension projection, and the per-mode re-baseline leaving a clean `status` — including a byte-identical re-checkout after a truth commit. `BO_0094_008` The `BO_0089_013` behaviors verify there too: successive commits into an overlaid group with acceptance establishing both, the overlaid-truth refusal, agent-identity staging under the agent principal with established truth untouched, and the CCGW-refused agent truth commit writing nothing.

## Boot And CLI

- `kernel serve --mode dev|prod --ccgw <url> [--tree <dir>] [--port 8090] [--data <dir>] [--principal <name>] [--hermes-principal <name>] [--proposal <id>] [--interval <duration>]` composes the kernel parts into the running system (`internal/kernel/serve`). The kernel owns the public port in both modes: it proxies to the tree's dev or serve process, which binds to a kernel-supplied internal port — which is what lets the fallback scaffold, promotion swaps, and last-known-good restarts happen without the public address ever changing. Kernel-owned endpoints live under the reserved `/__kernel/` prefix on that listener, apart from anything the tree can route: `GET /__kernel/healthz` reports the kernel's state — mode, state, pin, overlay — and answers from the first moment, including no-pin; the container health signal probes it. `BO_0095_001`
- Dev mode: checkout at the established head plus the optional selected overlay, materializer watch, and the toolchain dev server behind the kernel proxy. The proxy injects the non-forgeable "previewing proposal P" banner into every HTML response — asking the backend for identity encoding so no compression hides the injection point — and exposes the preview control: `POST /__kernel/preview {"proposal": …}` swaps the overlay in one serialized pass, `DELETE` drops it, and the banner follows the same state, so the swap and the banner cannot disagree. `BO_0098`'s preview action integrates against this surface; overlay authorship rules are the materializer's (`BO_0093`), and a refused swap leaves the current spec untouched. A failed dev cycle reports its error through the scaffold and retries on a timer — a fix can come from a graph write or a local edit. `BO_0095_002`
- The toolchain's `StartServe` runs `pnpm run serve` as a lifecycle-managed process group with the kernel-supplied port as `PORT` in the environment, under the same contract as dev: readiness — an HTTP answer on that port, whatever the status — exposed address, stop via context cancellation, failure-after-start as a `CommandError` exit notification. `BO_0095_004`
- Prod mode: materialize the promoted release pin (forced — the prod tree is kernel-owned, with derived artifacts outside the lockfile untouched), install, build, and run the tree's `serve` script. Promotion detection reuses the watch mechanics: poll the release pin, notice it moved, re-materialize → build → swap the proxied backend. Reboot on promotion is this swap — the kernel process itself stays up. A pin is attempted once; a failed pin is not retried until the release pin moves again. `BO_0095_005`
- Build-before-promote: `kernel pin --to N|head` materializes and builds the candidate pin in a throwaway staging tree, and only a successful build advances the release pin — cheap because builds are hermetic against the lockfile. A candidate that does not build never becomes the promoted state. `BO_0095_006`
- The promotion gate's serve probe: after the staging build, `kernel pin` starts the built tree's `serve` script on an ephemeral port under a deliberately constrained Node heap (`NODE_OPTIONS=--max-old-space-size=128`) and renders the root 50 times; the process must survive and keep answering — any HTTP status is an answer, matching the readiness contract, because the probe watches for a process that dies or stops responding, not content correctness. A candidate that cannot serve never becomes the promoted state, which also closes the empty-cache outage path: refused at the gate, there is nothing to fall back from. A probe failure refuses the promotion in the `BO_0127_002` failure shape — the failed step with its exit code plus the last output line — and a failed render waits a grace period for the process's own exit notification, so an OOM death surfaces its real exit code and output rather than the connection error the death caused (`toolchain.ProbeServe`, wired in `cmd/kernel/pin.go`'s `gateCandidate`). The tunables (50 renders, 128 MB heap, 5s per render) are chosen so the pin-145 failure class — whole-namespace content pulled per render, fatal within the first dozens of SSR renders — dies inside the probe while a healthy tree passes in seconds, and a hung server fails at its first stalled render rather than stalling the promotion. The probe lives in the promotion gate only: `kernel rollback` keeps skipping the gate (its target passed it once, and the serve loop's fallback still guards the floor), and the prod serve loop's deploy path is unchanged — deploying is itself the probe there, with last-known-good as containment. `BO_0132_001`
- Serve-probe verification (`cmd/kernel/pin_test.go`, beside the build-gate coverage): a candidate that builds cleanly but retains JS heap on every render — `internal/kernel/toolchain/testdata/leaky-tree`, a real Node server that OOMs under the constrained heap around render 15 while surviving far past the probe under a default heap — is refused without moving the pin, with the refusal carrying the serve process's own exit code and last output line, not a generic probe error. The healthy path is the existing promote-and-rollback round-trip, whose promotions now pass through the probe with the gate still completing in seconds. `BO_0132_002`
- The probe names itself: `ProbeServe` adds `CALLIOPA_SERVE_PROBE=1` to the candidate's serve environment beside the constrained heap, and the kernel's own serve never sets it. A tree whose `serve` entry does work against live state — the graph-hosted shell applies its own schema migrations before it listens — declines that work under the gate, so a refused candidate leaves the database it would have served untouched. `BO_0200_002`
- `last-known-good`: the last successfully built-and-served pin is cached on the kernel data volume (`last-known-good.json`). On build failure, served-process exit, or post-start HTTP probe failure, serve re-materializes that pin and restarts, reporting the fallback state with the failed pin's error — no graph read on the fallback path, so a broken promotion cannot strand the kernel behind an unreachable CCGW. A rootless pin is a content state and gets the scaffold, not the fallback. `BO_0095_007`
- The built-in fallback scaffold is what serve renders whenever no pinned tree is servable — no release pin yet, no root-providing extension, or no pin that builds: a dependency-free kernel-owned status page naming the state and the next step, so a fresh install shows a working floor instead of a refused connection. The no-pin state — a fresh install before any release pin exists — is a defined healthy state, reported through the container health signal; the distribution stack relies on it (`docs/system/distribution.md`). `BO_0095_008`
- The release pin is the kernel-owned `kernel.releasepin` singleton (registered beside the `ext.*` vocabulary in the bootstrap schema), truth-written through CCGW with human provenance by `kernel pin` and `kernel rollback` (`internal/kernel/releasepin`). Pin history is its revision history: rollback reads the value before the current revision through a pinned read just below its stamp and re-pins it — `--to N` overrides, and rollback deliberately skips the build gate, since its target passed the gate once and the serve loop's fallback still guards the floor. `BO_0095_003`
- CLI review verbs over CCGW, human identity: `kernel proposal list` (open groups, `--all` for terminal ones), `kernel proposal diff` — both sides projected in memory at one head pin, established against overlaid, printed as a unified diff — and `kernel proposal accept|reject`, invoking `BO_0084`'s atomic operations with the rationale recorded. These are the permanent recovery path, exercised routinely. `BO_0095_009`
- `mutation_resolution_failed: proposal … is not open` is what the *second* acceptance of a group answers, and during `BO_0163` on 2026-08-14 it was reached five times because two acceptance paths were open at once — the CLI and the shell's proposal review surface. Four times the CLI carried the losing attempt and printed the refusal to stderr while the group was already `accepted` under the human principal (at 4015, 4039, 4155 and 4206); once the CLI won, printed `accepted`, and the review surface showed the refusal instead. The refusal is correct in each case and nothing was lost: acceptance is atomic, the loser commits nothing, and each group carries exactly one revision. It is worth knowing that the message names a state, not a failure to act — an operator reading it on the recovery path may otherwise re-run, roll back, or hand-edit content that is already established.
