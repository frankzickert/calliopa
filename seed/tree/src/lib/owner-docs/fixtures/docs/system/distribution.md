# Calliopa Distribution

## Purpose

- Two stacks exist in the target architecture. The private dogfood stack is this repository's `docker-compose.yml`. The public distribution stack is what a user runs after the one-script install; it lives in the public `calliopa` repository and is authored entirely from this repository.
- This document covers the distribution scaffold — the source area, the publish step, the distribution compose stack, the install script, and the actor-facing docs skeleton — and the release pipeline (`BO_0090`) that fills the scaffold with pinned images, exported `bundled` extension snapshots, and seed content.

## Authoring And Publish Posture

- The distribution source area in this repository is the single place the public repo's content is written; the publish step is the only writer of `calliopa` and pushes the area verbatim. Release content (`BO_0090`) flows through the same area, so every release is also committed history here.
- No agent ever works in the `calliopa` repository directly; all work happens from `calliopa-bootstrap`.
- The public repo carries no internal details: no change process, change documents, live-line protocol, or internal system docs.
- Hermes is a first-class, always-on member of the distribution stack — not profile-gated as in the dogfood stack — and keeps the dogfood posture otherwise: CCGW-only access, no database credentials.
- On an empty graph the kernel's no-release-pin state is a defined healthy state: the bootloader starts, finds no pin, idles cleanly serving its built-in fallback scaffold, and reports that state as healthy. The behavior itself is kernel boot work (`BO_0095`); the distribution stack relies on it.

## The Scaffold

- The distribution source area is `distribution/`, holding the authored content of the public `calliopa` repository: `docker-compose.yml`, `.env.example`, `install.sh`, `README.md`, and the actor-facing `docs/` folder. `BO_0101_001`
- `scripts/publish-distribution.sh` (`make publish-distribution`) publishes the area to the repository named by `CALLIOPA_DISTRIBUTION_REMOTE` (branch `CALLIOPA_DISTRIBUTION_BRANCH`, default `main`): it replaces the clone's entire content with the area's current state and commits, so the published repo is always verbatim the committed area; an unchanged area is a no-op. `BO_0101_002`
- The distribution compose stack (project name `calliopa`) defines `bootstrap`, `postgres`, `migrate`, `app`, `garage`, `garage-init`, `backup`, `hermes`, and `kernel`, mirroring the dogfood service shapes with `image:` references instead of `build:` contexts. Images are parameterized by the `CALLIOPA_*_IMAGE` pins in `.env`, defaulting to the locally built dogfood tags until the first release (`BO_0090_001`) rewrites them to pushed GHCR references; `bootstrap`, `migrate`, and `app` share the one cell image. `BO_0101_003`
- `install.sh` self-downloads when run outside a checkout (clones `CALLIOPA_REPO_URL` into `CALLIOPA_HOME`, default `~/calliopa`, and re-executes), creates `.env` from `.env.example` on first run and adds only missing keys on re-run, takes the model-routing API key from the environment or an interactive prompt as the only human-supplied secret, pulls pinned images while tolerating not-yet-published local tags, and runs the bootstrap one-shot for idempotent secret generation and volume preparation. `BO_0101_004`
- The pre-seeding hook runs `seed/run.sh` with the stack's base URL when a release ships a seed bundle, bringing the cell up first so seeding goes through CCGW under the installer's identity; a missing bundle is skipped. Bundle content (the `ext.*` meta-schema, `calliopa-extension`, and `bundled` extensions) arrives with `BO_0090` releases. `BO_0101_005`
- `distribution/docs/` holds the actor-facing skeleton — `install.md`, `update.md`, `backup-restore.md`, `cli-recovery.md`, `bundled-extensions.md`, `extending.md` — with only user- and agent-facing content; sections grow with the features they document. `BO_0101_006`
- Scaffold verification performed: the compose definition validates against `.env.example`; the publish step round-trips to a bare repository byte-identically and no-ops on re-run; the install script, run from a clean copy of the published content, creates and repairs `.env`, tolerates unpublished image tags, and runs the bootstrap one-shot idempotently.
- The scaffold is published: the public `calliopa` repository's `main` branch carries the distribution area's content, written by the publish step and verified byte-identical to the source area. `BO_0101_002`
- The kernel service entry is aligned with the real kernel: it runs `serve --mode prod --port 8090` (the image's entrypoint is the kernel binary), reads `CALLIOPA_CCGW_URL` and `CALLIOPA_KERNEL_DATA` — the variables the binary actually consumes — keeps its last-known-good cache on the `kernel-data` volume, and healthchecks `GET /__kernel/healthz` through node, since the slim kernel image carries no wget. The dogfood compose gained the matching profile-gated `kernel` service, whose build produces the `calliopa-bootstrap-kernel` tag the distribution pins by default. `BO_0095_011`
- Distribution verification performed: from a clean copy of the distribution area, install and `up` brought the stack to healthy against locally built images — postgres, garage, app, backup, and the kernel, whose container healthcheck passed with `/__kernel/healthz` reporting `{"mode":"prod","state":"no-pin"}` and the public port serving the fallback scaffold ("No release pin yet") on the empty graph. Hermes was the one exception; its defect is recorded below. `BO_0095_012`
- The distribution stack publishes no CCGW port to the host: the `app` service carries no `ports` entry, so browser and host traffic reach only the kernel — the public port and the confirmation origin (8090/8091) — while the kernel reaches CCGW on the compose network. `internal/architecture/distribution_exposure_boundary_test.go` pins this file's published ports the way the dogfood exposure test pins the dogfood file's, so the closure cannot silently reopen. `docs/cli-recovery.md` records the in-stack CLI invocation (`docker compose exec kernel …`) — CLI parity survives the closure — and `install.sh` applies a release's seed bundle from inside the stack for the same reason. `BO_0103_007`

## Release Pipeline

- Releases flow one way, private to public, through the distribution area: the release script builds and pushes images, exports `bundled` extension snapshots, and writes pinned image references, exported source, and the seed bundle into `distribution/`. It never pushes to `calliopa` itself: the publish step (`BO_0101_002`) remains the only writer and stays a separate, explicit step, so every release is committed history here and passes a human checkpoint — review of the release diff — before anything goes public.
- GHCR is the only registry; no package registry exists. Bundled extensions ship as source in `calliopa` and build at materialize time.
- The export is a snapshot at the accepted pin, never history: the private dogfood instance remains the history of record, and the public repository's git history accumulates release-to-release diffs.

- `scripts/release-distribution.sh` (`make release-distribution`; `CALLIOPA_RELEASE_VERSION`, `CALLIOPA_RELEASE_REGISTRY`, `CALLIOPA_CCGW_URL`; `--no-push` for dry runs) fills the area with one release. It refuses to run without an accepted release pin — a release ships accepted truth only. It builds every locally built distribution image — cell, postgres, garage, garage-init, backup, hermes, kernel — pushes them to GHCR as `<registry>/calliopa-<name>:<version>`, and updates the `CALLIOPA_*_IMAGE` pins in `distribution/.env.example` to the pushed references. `BO_0089` reshaped the hermes entry (the pinned upstream Hermes Agent runtime; the worker image is retired, `BO_0104`); the release publishes whatever locally built set the compose then pins. `BO_0090_001`
- The export is a `kernel checkout` snapshot of the extension namespace at the accepted pin, written to `distribution/seed/tree/` with the lockfile kept as provenance. The guard keeps only extensions whose manifest is explicitly `category: bundled` — the default is `individual` (`extension-model.md`), so nothing private leaks by omission — prunes dropped subtrees from the shipped lockfile, and refuses the release outright when any root-mapped file belongs to a non-bundled extension or to more than one extension. `BO_0090_002`
- The export was, until `BO_0196`, the materializer's projection and nothing more, so it carried only what materializes — `ext.source`, `ext.manifest`, `ext.uicontribution` — and a bundled extension shipped as code without its vocabulary, skills, or declarations. Release `0.0.1` shipped `calliopa-extension` as `manifest.json` alone, its `create-extension` skill absent, and the end-to-end release verification did not see it because a dropped member kind is invisible to a build-and-serve check. The members sidecar closed this, and release `0.0.2` is the first export in which an extension's vocabulary leaves this graph at all. The lesson outlasts the defect: a release verification that reads the served page cannot see what the transfer dropped, which is why `BO_0196_005` reads the *installed* side.
- The install applied a release once and never again until `BO_0197`: the pre-seed hook skipped the whole extension import once its marker manifest was established, so a release delivered new images and no new graph content, and an install held the extension source and definitions it received the day it was created. The hook now runs on every invocation and lets the commit diff decide, so a release reaches a populated graph as a staged proposal.
- The seed bundle is `distribution/seed/`: `run.sh` (the `BO_0101_005` hook entrypoint, from `scripts/seed-run.sh`), a node CCGW helper, the meta-schema install profile emitted by `seed -emit` as check-then-create request payloads from the same definitions the dogfood seed writes (equivalence pinned by `internal/extensions/emit_test.go`), and `bundle.json` (version, pin, map-root owner, marker manifest, extension list). At install the hook applies the meta-schema idempotently, then imports the bundled extensions — `calliopa-extension` included, at the accepted pin like every other — as one atomic truth commit through `kernel commit` under the installer's principal (`CALLIOPA_PRINCIPAL`, default `installer`): a checkout of the fresh graph's (empty) extension namespace establishes the commit baseline and the exported files land over it as additions, the same shape as the original shell import. The hook then promotes the imported truth as the instance's first release pin — build-before-promote applies — so the kernel serves the shell right after `up` instead of idling on the fallback scaffold. A re-run skips the import once the marker manifest is established and leaves an existing pin alone. `BO_0090_003`

- Release verification performed 2026-07-31 at release 0.0.1 (dogfood pin 62), end to end: the release script filled the area, the publish step pushed it to the public `calliopa` repository, and the published content was verified byte-identical to the committed area. From a clean copy on fresh volumes, install and `up` pulled the GHCR-pinned images, generated secrets, applied migrations, applied the meta-schema install profile through the gateway, imported `calliopa-extension` and `ui.shell` as one atomic truth commit, and promoted the imported truth as the instance's first release pin; every service reached healthy — hermes included — and the kernel built and serves the shell in prod mode (`{"mode":"prod","state":"serving"}`). - A release carries a bundled extension's non-materializing members beside its materialized tree, in a `members.json` sidecar: `ext.blocktype`, `ext.relationtype`, `ext.skill`, `ext.intention` and `ext.migration`, each recorded with its extension, Block identity, kind and public content. `kernel checkout --members <file>` writes the sidecar from the same pinned snapshot as the projection, and `kernel commit --members <file>` folds it into the **same change set** as the tree — one mutation, one `dataRevision` — so an extension's sources and its vocabulary arrive together or not at all. A member the target graph does not hold is created and attached to its manifest by `partOf`; one it already holds is revised through the same property diff a changed content file takes, which is why the sidecar is not a check-then-create pass: create-if-absent can deliver a definition but never correct one. A member whose extension has no manifest in the graph or in the same commit is refused rather than attached to a guess, and a Block whose kind differs from the graph's is refused as an identity change. Both flags are opt-in and the working tree's contract is unchanged — only the release export and the install pre-seed pass them. `BO_0196_001`
- `ext.settings` is excluded from the transfer by construction: the sidecar reader refuses it as an untransferable kind. Settings are per-instance runtime state, and the shell's settings surface creates a Block on first write, so absence is the correct state for a fresh install to arrive in. `BO_0196_001`

- The pre-seed hook's commit posture follows what the graph already holds. A fresh install — no bundled extension present — commits accepted truth as before, because nothing exists to overwrite and the shell must serve straight after `up`. An update stages a **proposal** instead: the graph holds content this instance's own human accepted, and `distribution/docs/extending.md` promises them that nothing lands without their review. `kernel commit` already defaults to a proposal and takes `--truth` as an opt-in, so the posture is a flag rather than machinery. The consequence is stated plainly in `distribution/docs/update.md`: when `install.sh` finishes, an update is waiting for review, not applied. `BO_0197_001`
- The marker guard is gone. The hook runs the import on every invocation and lets the commit diff decide whether anything is left to do: an up-to-date install produces an empty change set, and `kernel commit` reports nothing to commit and exits 0 — a clean tree is a success, not a failure, the same posture `kernel status` already takes. The marker manifest is still read, but only to choose the posture above, never to skip the work. A version-recording marker was rejected: it answers a question the diff answers, and drifts from the graph the moment anyone edits a bundled extension. `BO_0197_002`
- A release is authoritative for what it ships, so a dropped file, member, or whole extension reaches an install as a deletion rather than lingering. On the tree side the hook clears every **bundled** extension subtree from the baseline checkout before the overlay, along with the root-mapped files the lockfile records: whatever the release still carries comes straight back as an ordinary diff, and whatever it dropped is absent and becomes a removal. The clearing is keyed on the manifest's `category`, not on the release's list, which is precisely what leaves an instance's `individual` extensions untouched. On the members side the sidecar carries an `extensions` list naming what it speaks for; within those extensions a transferred member the graph holds and the sidecar omits is retired with its `partOf` edge, and outside them nothing is touched. A sidecar that names no extensions adds and revises but never removes, which is the posture a release predating the field keeps. `BO_0197_003`
- Pin promotion is the fresh install's alone. A first install promotes the imported truth so the kernel serves the shell immediately, and build-before-promote (`BO_0131_001`) means a release that does not build leaves the pin unset and the kernel on its documented fallback scaffold. An update promotes nothing: its content is a proposal, and the instance keeps serving its current pin until a human accepts and promotes it. That ordering is what makes a bad release unable to take a running instance down — the failure mode the fresh-install path has nothing to protect against and an update very much does. `BO_0197_004`
- `distribution/docs/update.md` states what an update moves and what rolls back. Images and graph content version independently: the documented rollback — check out the previous release state, re-run the two commands — moves images only, and the doc now says so rather than implying it covers everything. Graph content rolls back on its own terms, through revisions and the release pin, which is the promise `extending.md` already makes. The same section states that an update arrives as a proposal and that a release never touches extensions the instance created itself. `BO_0197_005`

- An update **includes** the revert of a bundled file the install modified locally, staged in the proposal like any other change and unlabelled — decided 2026-08-24 (`BO_0197_006`). Include beats exclude because a silent fork is the worse failure: excluding leaves that install diverged from every future release with no signal it happened. The posture is honest about its limit rather than overclaiming — the proposal makes the change *reviewable*, not the collision *legible*. An install records nothing about which release it applied (the version reaches only log lines and the commit rationale, `scripts/seed-run.sh`), so the staged diff reads the same whether the release changed a file or the operator did, and the reviewer is not told which of their own edits they would be reverting. Pinned by `TestCommitGivenALocallyModifiedBundledFileThenTheUpdateStagesTheRevert`, which asserts the operator's content stays established while the release's content is staged beside it: the behaviour was incidental to the commit diff before it was decided, and the test is what makes it specified. `BO_0197_006`
