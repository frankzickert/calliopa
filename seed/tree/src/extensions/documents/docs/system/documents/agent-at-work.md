# The Agent At Work

## The Agent At Work In The Document

- Under `calliopa-bootstrap`'s `BO_0265`, set to draft by the user on 2026-09-18 and transferred here the same day, the person sees at the blocks what an agent does to the document while it does it. The editor draws the marks, shows the run's proposals as they are staged, and reports the run chips. `ui.shell` carries the activity and draws the chips ([Agent Activity](../../../../../../docs/system/workspace/agent-activity.md)). The kernel reports the activity (`calliopa-bootstrap`'s `docs/system/ui-kernel.md`, *The Agent At Work In The Document*).
* Whenever the agent reads a block by name or proposes against it, the agent's icon stands on that block's bottom border, left-aligned and inset, followed by one line saying what the agent does with the block. A read's mark fades three seconds after the last read of that block. A proposal's mark stays, and the proposal's decisions stand in the same line after the words. User decision, 2026-09-18.
* The line's words are derived from the operation, and the agent's own short note replaces them when there is one. User decision, 2026-09-18.
* The mark replaces the proposer's face on the left border and the answers on the top edge, for every proposed item: every agent run's, whether older or new, a person's branch, and a system run's derived candidates. *Accept all* leaves the item for the run chip. Read marks are shown for command runs only. User decision, 2026-09-18.
* A command run's items appear at their targets as the run stages them, without *Show proposed changes*, and stay shown after it ends until they are answered. They can be answered while the run is still going. User decision, 2026-09-18.
- Nothing moves the reader. No mark or staged item scrolls the document.
- The derived words: *Reading* for a read, *Proposes a rewrite* for `replace`, *Proposes a new block* for `insert`, *Proposes removal* for `remove`, *Proposes a move* for `move`, and the work kinds named as their item is named today (*Possible relation*).
- The chip on a proposed item (`BO_0265_010`, `DO_0004_003`). `ProposalBlock` (`src/extensions/documents/views/proposals/proposal-block.tsx`) draws one chip as its last child, `.proposal-block__mark`, half over the bottom border and inset by the gutter's width: the face (`.proposal-block__face`, the runtime's portrait at 18px for an agent, `user` for a person's branch, `sparkle` for the system), the words (`.proposal-block__words`), then accept and reject and, for a move, the `arrows-down-up` sign. A work item and a derived candidate take the same chip; a derived candidate's words are its derived name, and its *Fixate this framing* and *Discard* stand in the chip in place of answers (`.proposal-block__chip-use`, `data-derived-use`). The face stays the handle — drag, arrow keys — and nothing stands on the left border or the top edge ([Proposed Changes](./proposed-changes.md#proposed-changes-in-place)). `proposal-block.test.ts` proves the chip's order and words for every kind and that no *Accept all* is drawn on an item.
- The line's words (`BO_0265_011`). `itemWords` (`src/extensions/documents/lib/agent-at-work.ts`) answers the note the run's staging of the item reported, matched by the member the item covers, while that activity is held; otherwise the note the group's `agent.run` node records (`notes`, keyed by member), which `readDocumentProposals` sets on the item as `note`; otherwise the derived words (`markWords`). A reload shows the recorded note.
- The run's items appear as they are staged (`BO_0265_012`). The editor tracks `bridge.activity` for its document. It keeps each of the reader's runs there (`state.runActivities`, `BO_0269_018`), adds the group each stages into to `state.liveGroups`, and on any run's staging reads the proposals again through `reloadProposals$`, whose own read counter drops a read another overtook, so the editor never waits on a read. `shownProposalsOf` shows a live group's items whatever the toggle holds, while the run goes and after, until they are answered; the toggle keeps its meaning for every other group. An item answered during the run leaves the list at once and stays answered.
- The read marks (`BO_0265_013`). A `read` activity of scope `blocks` marks each named block the editor draws: `readMarks` keeps each until three seconds after its last read (`READ_MARK_MS`), and `BlockRow` draws `AgentReadMark` — the face of the agent whose run read the block, which the mark keeps (`ReadMark.agent`, `BO_0269_018`), and the words, *Reading* or the read's note — over the row's bottom border, `aria-hidden`, keyed by when it goes so a new read draws it anew. A timer drops it when its time has passed. It fades in the last fifth by a CSS animation, which reduced motion turns off. A whole-document read marks no block.
- The run chips and answering a whole run (`BO_0265_014`). `runChipsOf` builds one chip for each open group reaching the document whose `agent.run` node `readDocumentProposals` reads (`run: { runId, stagedAt }`), a command run's or a system run's, newest first by `stagedAt`, and puts each of the reader's running runs first, newest first, before it has staged too: *Starting*, *Reading the document*, then *Proposing changes*. An ended chip counts the group's unanswered items by kind (*3 rewrites, 1 insert*). A person's branch has no chip. The editor reports the chips through `setRunChips$` whenever what they say changes, and answers `answerAll` for its document through `answerGroup$`, the per-item `answerProposal$` over the group in its order.
- Marking a framed proposal follows the mark (`BO_0265_015`). The face that marks a removal or a move in command mode (`BO_0263_005`) is the one in the bottom-border line, with the same name and pressed state ([Command Mode](./command-mode.md#marking-every-drawn-row)).
- `agent-at-work.test.ts` (`lib` and `views/proposals`) proves the words, the read marks' three seconds and their restart, the chips in order with the running one first, items appearing on staging without the toggle while older groups stay behind it, and a chip's *Reject all* rejecting its group alone; each behaviour was shown to fail with its code removed.
- [ ] With the answers off a proposal's top edge, a proposal's ↑↓ arrows on a phone may stand at the right end of its top border as every row's do: `block-editor.css`'s `.proposal-block > .block-grip--end.block-grip--idle` override under `max-width: 640px` put them beside the handle only because the answers rode the top edge at the right (`BO_0263_014`). Drop the override and its comment, and measure at 360 and 390 CSS px that the arrows meet neither the handle nor the text.
- Walked on the served build at pin 148 on 2026-09-18, with the kernel rebuilt and hermes restarted, and the user said it works (`BO_0265_016`): a command run from an open document in command mode marked the blocks it read, its proposals appeared while it ran, and its chip offered *Reject all* and *Accept all* once it had ended. The walk showed a rewrite drawn as a block of its own after the one it rewrites, which `CA_0055` changed.

## Proposals In Place

- Under `CA_0055`, set to draft by the user on 2026-09-18 and transferred here the same day, a shown rewrite takes the place of the block it rewrites, and each change's proposals are shown or hidden from its run chip. The shell's half is `ui.shell`'s [Agent Activity](../../../../../../docs/system/workspace/agent-activity.md) (`CA_0055_001`–`CA_0055_004`).
- A shown rewrite replaces its block (`CA_0055_005`). `placeProposals` (`views/reading-order.ts`) draws a shown `replace` item as a row that `replaces` its block's entry — taking its position (`positionOf`), its key and its drop target — and leaves the block's own row out, so only the proposed version is drawn; with its change hidden the block is drawn as it stands. A block a removal or a move frames keeps its row with the rewrite after it, and so does the block being edited (`keep`, the editor's active block), which must not leave under the caret. A system run's derived rewrite stands beside the framing it challenges rather than in its place (`BO_0246_006`). With two rewrites of one block, the first takes its place. The rewrite keeps its mark line, its editing and its drag.
- Each change is shown or hidden on its own (`CA_0055_006`). Beside `proposalsOpen` the editor keeps `shownGroups` and `hiddenGroups`: `groupShown` (`lib/agent-at-work.ts`) shows a group while *Show proposed changes* is on unless a chip hid it, and while it is off only if a chip showed it; `toggledGroup` flips a group against the toggle for a chip's `toggleRun`, and the toggle clears both sets. The reader's live run's group joins `shownGroups` when it first stages, once, so hiding it from its chip holds while it stages more. When a followed run ends the editor no longer turns the toggle on, which would undo what the chips set; a run it did not follow still does. On a line of two or more chips this is narrowed to one change at a time (One Chip Open At A Time, `CA_0061_008`–`CA_0061_010`). A derived candidate shows as before, and a started document shows everything. The state is the tab's and is not kept across a reload. The chips carry `shown`.
- Proven in the render harness (`CA_0055_007`): `views/reading-order.test.ts` — a rewrite in its block's place with its position, key and drop placement; the framed, edited and derived exceptions; two rewrites of one block. `views/proposals/agent-at-work.test.ts` — with the toggle on, the rewrite in place and the block's row absent; the live run's chip hiding its change and giving the block back while the other stays; the toggle hiding every change and resetting the chips; a chip then showing its own alone; the chips' `shown` following. `proposal-block.test.ts` draws the rewrite in its block's place. Each was shown to fail with its code removed. A read mark's drop keeps waking until every mark has gone, since a timer may wake a little early — the flake that found it.
- Walked on the served build at pin 202 on 2026-09-18, and the user said it works (`CA_0055_008`): a run's rewrite stood in its block's place, its chip under the view bar pushed the document down, a press on the chip brought the original back and a second showed the proposal again, and the bar's toggle set every run.

## The Proposal Chip

- Under `DO_0004`, set to draft by the user on 2026-09-18 and transferred here the same day, a proposal's line on its bottom border becomes one chip that shows only when the reader turns to the proposal. What "desktop" means and the press rules are [Block Editor View](./block-editor.md#one-click-on-a-desktop).
* A proposed block's proposer, words and answers stand in one chip of equal-size controls, as the command control does ([Command Mode](./command-mode.md), `BO_0267_027`): one border around them, every control 24px on every device, no touch minimum. User decision, 2026-09-18.
* At rest a proposed block shows only its proposer's ground and edge; the whole chip — face, words and answers — is hidden. It shows on a desktop while the pointer is over the proposal or it holds keyboard focus, and on a phone once a first tap has focused it. The block's accessible name still says who proposed it and what it does. User decision, 2026-09-18.
* A proposed block reserves the room its chip takes below its border, held whether or not the chip is shown, so the chip never covers the block below and nothing moves when it appears. The rule for every bordered row is [Block Editor View](./block-editor.md#a-marked-block-is-a-card). User decision, 2026-09-21, replacing the ordinary-block spacing of 2026-09-18 (`DO_0008_009`).

- The chip hidden at rest (`DO_0004_004`): `.proposal-block__mark` is `visibility: hidden`, shown under `(hover: hover) and (pointer: fine)` while the proposal is hovered or holds the focus, and under `(hover: none), (pointer: coarse)` while it holds the focus. The proposal is focusable (`tabIndex -1`, and `0` for a claim, a kind or a state, which hold nothing focusable of their own), so a tap focuses it and shows the chip and its grip (`BO_0263_014`). `ProposalBlock` keeps a `Reach` store — `hover` from `hoverPointer()` (`lib/pointer.ts`), following the query's changes, and `engaged` from its `focusin` and `focusout` — and a rewrite's or a new block's text takes the caret (`contenteditable`) on a hovering pointer, or once the proposal is engaged: on a phone the first tap focuses, the second places the caret, and editing still accepts by the `BO_0233` rule. - The room the chip takes (`DO_0008_009`, replacing `DO_0004_005`'s spacing): `.proposal-block` has no block padding and the chip is out of the flow, so showing it moves nothing — and the row keeps `--row-overhang`, half the 28px chip plus half a card's label, so the chip never reaches the block below and a proposal and a card meeting never abut. The element that carries it is the row the document's flow holds (`DO_0009_001`): a proposal the editor gave a place is drawn in a `.drop-slot`, whose drop mark keeps the two margins from collapsing, so the slot keeps the room and the proposal inside it keeps none. The gaps are measured in one place, [Block Editor View](./block-editor.md#a-marked-block-is-a-card).

The `documents` unit suite passes (113 files, 985 tests over the tree), the tree typechecks and both bundles build.

## Several Runs At Once

- Under `calliopa-bootstrap`'s `BO_0269`, set to draft by the user on 2026-09-19 and transferred here the same day, several runs may work in one document at once, each staging its own group. The shell's half and the decisions are `ui.shell`'s [Run Lifecycle](../../../../../../docs/system/agent/run-lifecycle.md), *Concurrent And Faster Runs*.
* Two runs in one document are shown together: each run's marks carry its own agent's face, each run has its own chip, and its items appear as it stages them. When accepting one run's items makes the other's stale, the existing stale-proposal handling applies and the person decides. User decision, 2026-09-19.
- The editor follows every running run on its document (`BO_0269_018`): `state.runActivities` holds each from the bridge's list, each run's new events are read against what the view held of it, its reads mark with its own agent, its group joins `state.liveGroups`, and `runChipsOf` takes the list, giving each running run its own chip. A block's command control sends while runs go and draws the speed after the agent (`BO_0269_015`). `agent-at-work.test.ts` proves two runs' marks with their own faces and their own chips, and one run's end leaving the other's marks and chip; `lib/agent-at-work.test.ts` two running chips beside an ended group.
- Walked on the served build on 2026-09-19 at pin 441, with the kernel and agent images rebuilt and Claude Code on Opus, and the user said it all works (`BO_0269_019`): commands on different agents went at once in one document, each with its own chip and marks, and one run's items were answered while the other's stood.

## A Refined Proposal

The rule and the rest of this extension's half are [Proposed Changes](./proposed-changes.md#a-run-works-with-what-is-already-proposed) (`BO_0271_009`–`BO_0271_012`).
* A refined proposal is the refiner's work with its origin kept: the chip carries the refining run's face and words and says it refines an earlier proposal, naming its proposer. The reader answers the words in front of them and can still see where they came from. User decision, 2026-09-20.

Proven in `proposal-block.test.ts` (the refined rewrite's tone, face, words and names beside an unrefined item of the same group) and `lib/agent-at-work.test.ts` (the words with and without the group's proposer and with a note, and the refiner from provenance, from a live run's activity, and none); each was shown to fail with its code removed.

## One Chip Open At A Time

- Under `ui.shell`'s `CA_0061`, set to draft by the user on 2026-09-22 and transferred here the same day, the chip line minimizes from the second chip on and one change is read at a time. The decisions and the shell's half are `ui.shell`'s [Agent Activity](../../../../../../docs/system/workspace/agent-activity.md), *One Chip Open At A Time* (`CA_0061_001`–`CA_0061_006`); this half is what the view reports and what it shows.
- The count the chips report (`CA_0061_007`). `runChipsOf` (`lib/agent-at-work.ts`) gives an ended group's chip `count`, its unanswered items — the number `summaryWords` counts in words, so *3 rewrites, 1 insert* is `4` — and a running run's chip none. `sessionChipsOf` (`lib/branch.ts`) takes the counts the editor builds from the proposals it holds (`openCounts`, `views/block-editor.tsx`) and gives each session chip its branch group's.
- One change at a time (`CA_0061_008`). `toggledGroup` (`lib/agent-at-work.ts`) takes the `ChipLine` the press lands on — every group with a chip, newest first, and `liveGroupsOf`'s groups of the runs still going — and on a line of two or more answers `shownAlone`: the pressed group shown and every other hidden, or, when it was the shown one, none shown at all. A run still staging keeps its items through another chip's expansion, since its items appear as it stages them (`BO_0265_012`), and is hidden only by its own chip's press. On a line of one the press is the flip it always was (`CA_0055_006`). The editor builds the line from the chips it reports (`chipsOf`, `chipLineOf`) and passes it at every press, a run chip's and a session chip's alike.
- The toggle expands the newest (`CA_0061_009`). `toggleProposals$` clears what the chips set as before and then, on a line of several, shows the newest chip's group alone — the first group `chipsOf` reports; turned off it shows none. Proposals arriving from a run the view did not follow open the same way, one change at a time, where they opened every change. `keepOneExpanded` holds the line to one as the changes arrive, since a tab restored with its proposals shown turns the toggle on before it has read them and would otherwise draw every change (the walk of 2026-09-22 found it): it keeps the newest shown change, leaves a line already holding to one alone, and never takes away a run still staging or the session the tab works in. A started document still shows its run's proposal whatever the toggle holds (`BO_0251_010`), and a derived candidate shows as before.
- An ending run takes the expansion (`CA_0061_010`). When a run the view followed goes from running to ended, the editor shows its group alone and hides every other, so the items it has just staged stay on the page and the reader answers the run they watched. It replaces `CA_0055_006`'s leaving the chips as they stood on a followed run's end.
- Proven (`CA_0061_011`). `lib/agent-at-work.test.ts`: the count on an ended chip and none on a running one; a line of one flipping its own group; a line of several showing one and hiding the rest, and collapsing to none; a live group surviving another chip's expansion and still hidden by its own press; `shownAlone` and `liveGroupsOf`. In the render harness, `views/proposals/agent-at-work.test.ts`: the toggle showing the newest change alone, a chip's press moving the expansion and giving the rewritten block back, its own press leaving nothing drawn, a run's items standing while another change is expanded, its end taking the expansion, a change landing while another stands shown leaving the newest expanded alone, and the counts the chips carry; `views/branch/branch.test.ts`: two sessions and a run, each press moving the expansion. Each was shown to fail with its code removed.
- Walked on the served build at pin 1283 on 2026-09-22, and the user said it works (`CA_0061_012`): several chips stood minimized with the newest expanded when the document opened, a press on a face drew that run's changes and collapsed the rest, a second press left the document with none, the bar's toggle expanded the newest, a run still going kept its words and took the expansion when it ended, and the reader's own proposal chip minimized with its pencil. The walk of the morning found the open path — a restored tab turns the toggle on before it has read its proposals — which `keepOneExpanded` answers.

## A Proposed Picture, And A Send That Is Not A Run

- Under `calliopa-bootstrap`'s `BO_0273`, two things broke the first time a block was sent to a
  model, and both were the senders change reaching further than it looked (`BO_0273_039`, found by
  the user 2026-09-22).
- **A proposed picture drew nothing.** `ProposalBlock` drew a proposal's own content only when its
  block was text, and fell through to the slot otherwise, so a proposed generation arrived as an
  empty line with a chip on it. It now draws the block's own view for an `image` or a `video`, as
  it draws a paragraph's words, and the row says what it will be made from.
- **The chip said *Starting* for ever.** A send to a sender answers a process and no run, and
  `startRun$` followed the run id it was given without looking — `undefined` — so a chip opened
  that nothing could ever end. It now follows only when there is a run to follow; a sender's work
  is on the Execution list like any other process.
- Proven in `views/proposals/media-proposal.test.ts`: a proposed `image` block drawn as its pending
  box with the words it will be made from, shown as a reader shows proposals. The draw was shown to
  bite by taking the branch away. The proposal and shell suites pass beside it (152 tests).
- **A picture that landed stayed a box** (`CA_0063_005`, found by the user 2026-09-23, the first
  time the shell told the document a sender's process had ended — `ui.shell`'s
  [Processes](../../../../../../docs/system/workspace/processes.md)). The proposals were read again
  and the item held the filled block, but a proposal row is a `ProposalBlock` given `item` as a
  member of a plain row object, which the optimizer hands the component once, at mount, and its
  key was the item id alone — so the row kept the pending block it mounted with until the page
  was reloaded. The row is keyed by the block's revision as a block row is (`CA_0045_003`), the
  item being edited excepted, so a proposed block revised after it was drawn is a new row. Proven
  in `views/proposals/media-proposal.test.ts` through the harness's `[data-harness-proposed]`
  press and `proposalsRead`: the box shown, the process's end told, the picture drawn where the
  box stood; it failed with the key as it was.
