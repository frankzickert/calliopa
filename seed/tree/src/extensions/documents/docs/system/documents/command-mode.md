# Command Mode

## Command Mode

* The block editor surface holds exactly one mode: reading or command. The active block stays a fact within reading presentation rather than a third mode of its own.
* In command mode a click marks a block as a reference, and clicking it again removes the mark. Marking never makes a block editable.
* A reference identifies a block by its identity. Its number is a human-facing alias, never the thing the reference points at, so reordering or restructuring the document must not silently retarget a reference.
* Numbers are assigned in the order the reader marked, not in document order.
* There is no references list. The document is the list: a marked block carries its number in place, and reading the document is reading back what was marked.
* The control that opens and closes the mode is *Point from this block* (`◎`) on the command control of the block being edited: the mode points from that block, the prompt, and the marks made are its own. User decision, 2026-09-18 (`BO_0267`).
* Whatever opens the mode is reachable by pointer, keyboard, and touch. A mode reachable only from a keyboard does not exist on a phone.
* Marking sends nothing. No command runs, no AI is contacted, and no process is produced because a block was marked: the mode delivers the pointing alone, and the pointing travels only when the reader presses *Send* on the prompt's control, as a copy of the marks that stand at the press (`BO_0226`, `BO_0267`).

- Reading presentation stays the resting state and is still not a mode the reader selects. Command mode is a mode the reader enters and leaves back to reading, which does not make reading into a chosen state. A document always opens reading, since pointing ends with the page, so `A document opens as a reading surface with no block active` holds: what the mode changes is what a click means, not what the surface presents.
- Two modes rather than three, because editing does not need to be one. `At most one block is active per tab` already tells activation apart from everything else, and command mode is the first state that cannot be inferred from whether a block is active, which is why it is the first one the surface holds.
* Pointing keeps the prompt's editor: the block the command is written in stays edited while other rows are marked, and ending the pointing leaves it edited. User decision, 2026-09-18 (`BO_0267_023`).
- The prompt is the one block active in command mode. Marking is not activation: a press on another row marks it and opens no editor there, and a press outside the prompt does not end its edit while the mode is on. The bar carries the prompt's groups, as it does for any block being edited (`CA_0053`).
- Entering and leaving move no document content, which is the rule the bar already keeps. The reader's scroll position and every block's position on screen are the same before and after.
- The mode is never ambiguous. At any moment the surface is reading or command, a click does what the current mode says it does, and entering the mode is announced to assistive technology.
- `◎` reads as pressed while the mode is open, so it says which mode the surface is in rather than only offering a way in, and the prompt pointed from carries an accent edge on its start side, visibly not a marked block's dashed outline (`data-pointing-from`).
- `Ctrl`/`Cmd`+`Enter` sends the block being edited, or the prompt pointed from, as a prompt (`BO_0267_012`, user decision 2026-09-18). It is unbound elsewhere in this editor, which binds `Ctrl`/`Cmd`+`Z`, `Y`, `B` and `I` along with `Escape`, `Enter`, `Backspace`, `Delete` and the arrows, and it must not also split the block.
- `Escape` leaves the most local surface first and then the mode, decided in one place. The shell's message surface holds the floor and takes `Escape` before anything in a view sees it, and that ordering stays the shell's.
- Leaving preserves what was marked, so closing the mode by accident costs nothing.
- The way in is the block the command is written in: pointing starts where the words are, so the reader does not learn one place to start pointing and another to say what the pointing was for. The reading surface stays content-only; the control stands only on the block being edited and on the prompt pointed from.
- A marked block carries a visible treatment and its number, so the state never rests on colour alone. The treatment is visibly not the active-block treatment and visibly not authored formatting, and it leaves no trace when the mode ends.
- A marked block's accessible name says that it is marked and which reference it is, and marking is reachable from the keyboard, as activation already is.
- Several blocks can be marked across the document, and the marks survive scrolling.
- A number is retired with its mark. Unmarking one reference leaves every standing reference the number it already carries, so a block's number never changes under a reader who did not touch it, and the freed number is not reissued while any mark stands. Numbering starts again at `#1` once nothing is marked.
- A reference whose row has since gone — a block retired, a proposal rejected, a retired block restored — stays, as what was marked, and is taken back from its chip on the prompt's command control, which carries a × for it since no number is left in the document to press ([Marking Every Drawn Row](#marking-every-drawn-row)). Only a reference from before `BO_0263`, which names no revision, is dropped when its block has gone: there is nothing to tell a run about it as it was.
- A retired block is markable where it is revealed, and so are a proposed change and a discarded block ([Marking Every Drawn Row](#marking-every-drawn-row)). A retired block is still read-only and offers only `Restore`; the mark points at it as retired, and the run is told so.
- The blank-page placeholder creates no block in command mode. Clicking empty space below the last block appends a paragraph while reading; in this mode the surface is for pointing, and a click there does nothing.
- Marking is device-local presentation state per prompt block. It never becomes graph truth, and nothing here writes a revision, so a document that was only marked has the same change count it had before.
- A prompt's marks outlive the page; the mode does not. A block's marks come back whenever it is edited again, on this page from what the page held and after a reload from the device, and from its latest run the person may see when the device holds none, so a reload or another device shows what the block last carried (`BO_0267_013`). Pointing ends with the page: a reloaded document opens reading, as every document does.
- That the document is the list is the call [Retired Blocks In Place](./document-panel.md#retired-blocks-in-place) already made, for the reason given there: the position is what makes it mean anything. A second surface enumerating blocks that are already on screen, numbered, would say the same thing twice and could disagree with itself.
- It is also why the numbers are assigned in mark order. Read top to bottom, a document showing `#2`, `#1`, `#3` says both which blocks were marked and the order they were marked in, which a list is otherwise needed to carry.
- The prompt's command control carries what is marked as chips on its line, one per reference in mark order, then each fixated block (`commands-and-runs.md`, `CA_0039_003`, `BO_0267_012`). The document is still the list of what was marked; the chips are the command.
- Until `BO_0226` nothing rendered in the composer at all, for the reason this document gave then: feeding a composer that could not run would settle a shape the first real command had not had a chance to decide. The first real command decided it — pointing, not targets: the run is told what the reader marked and in which order, and the command's own words say what to do with it (`tighten #2`).
- Until `BO_0227`, not a passage reference: marking a range inside a block, anchoring it, and deciding what a stale anchor means was work of its own, and whole blocks were what made the mode usable at all. `BO_0227` is that work — [Passages](#passages) below.
- Not comments or annotations. Disposition, which this document also excluded, arrived with `BO_0227` as a block's standing ([Block Editor View](./block-editor.md#standing)); it is not pointing, and nothing about it is device-local.
- Not a change to what a document stores. [Block Document Model](./block-document-model.md) gains nothing: no reference node, no stored context, and no new vocabulary.
- A command context, since `BO_0226`: a command from a document carries the document, where its work goes, and the references in mark order, each as a field of the run, and since `BO_0267` the block it was sent from (`commands-and-runs.md`). The references are pointing, never a fence — a run may write anywhere in the document the command asks it to.

## Implementation

- `store.marking.mode` is the surface's mode, and `point$` in `use-marking.ts` is the only place it changes: `point$(blockId)` makes the block the prompt and enters the mode, leaving its edit as it is; `point$(null)` leaves the mode (`CA_0020_002`, `BO_0267_013`, `BO_0267_023`). The page's press listener, which ends an edit on a press outside the block, answers nothing while the mode is on, and the active block's `Escape` is the surface's then, ending the pointing rather than the edit; the prompt row's own keys and presses never mark it.
- The document's render reads the mode, and a mode change rebuilds the block list. That is the one moment it is safe to: entering ended the edit and leaving opens none, so there is no caret in the elements being rebuilt (`CA_0020_002`).
- One `keydown` listener on the document decides `Ctrl`/`Cmd`+`Enter` and `Escape`, and `ActiveBlockText` leaves the shortcut alone rather than splitting on the `Enter` inside it. Two handlers arbitrating one event is the mistake the old artifact editor made three times; the surface owns the mode, so the surface hears the key (`CA_0020_002`).
- That listener ignores a key while the view's own surface is inert. A message holding the floor makes the frame inert, so the shell's `Escape` stays the message's and the ordering stays the shell's, without the view knowing a message exists (`CA_0020_002`).
- `startWriting$` returns in command mode, which covers both ways into writing at once — the blank page and the area below the last block — rather than guarding each control that calls it (`CA_0020_002`).
- The mode is announced through a visually hidden `role="status"` in the view, empty while reading. Out of the flow, so what it says moves no document content, and silent about a resting state nobody chose (`CA_0020_002`).

- The whole block row is what a click marks in command mode, and the marking control carries `role="button"`, `aria-pressed`, and a name that says either `Mark block 3` or `Block 3, reference 2`. Since `BO_0231` a text block's control is the element around its words, so that its attributes are patched as the block is marked ([Block Editor View](./block-editor.md#standing)); a divider's is still the row. A reference points at a block, so the reader pointing at one does not have to hit its text; in reading mode the row is a plain row again, its marking attributes absent rather than set to nothing (`CA_0020_003`).
- The treatment is a dashed outline on the row rather than a border on the text. An outline changes no geometry, and dashed around the whole block is visibly neither the active block's solid accent border nor a `blockquote`'s authored rule (`CA_0020_003`).
- The number renders in the gutter the grips use, out of the row's flow, and is `aria-hidden`: the row's own accessible name already says which reference it is, so the badge would otherwise be the same fact twice (`CA_0020_003`).
- The badge takes the accent as its border and `--panel-raised` as its ground. Text that size reversed out of the accent reads at 3.5:1, which the axe scan fails and a reader would too (`CA_0020_003`).
- `data-reference` is written only while the mode is on, so leaving the mode leaves no trace in the markup either, and what a scenario reads is what the reader sees (`CA_0020_003`).

- `src/lib/references.ts` is the marking model, pure and unit-tested: which block carries which number, what unmarking does to the rest, dropping the references whose blocks have gone, and reading a stored session back. Where a number comes from is the part worth being sure of, and none of it needs a browser to check (`CA_0020_004`).
- The mode and the marks are one record, kept under `calliopa.marking.<document>` in `localStorage`. One record because they are recovered together: marks kept but not drawn would be state the reader has no way to see (`CA_0020_004`).
- The record is read before the document is, so the read that follows is what drops the references naming blocks the document no longer holds. A stored counter is raised past every number still standing, so a tampered or truncated record cannot put two blocks under one reference (`CA_0020_004`).
- The task that writes it refuses to write before the document is ready. A write from the state this view starts in would clear the record it is about to recover (`CA_0020_004`).
- A returning tab does not activate its remembered block while the mode is command. Entering the mode already cleared the tab's selection, so this is the invariant kept locally rather than inferred from how the record was written (`CA_0020_004`).
- Storage that throws is a browser that keeps nothing, and both the read and the write pass over it. The marks then live for the page's lifetime; the document is untouched either way, so there is nothing to recover from and nothing to report (`CA_0020_004`).

- The mode is proven in Qwik's render harness through the editor's own JSX (`block-editor.test.ts`, `marking/mark-rows.test.ts`, `command/command-control.test.ts`), entering it from a block's control through `pointFrom` in `testing/editor-harness.ts` and leaving it through `stopPointing`.

- The editor reports what is marked through `setPointing$` on the view bridge, naming its document, from a visible task tracking the references and the document's status — after the document is ready, as the record is kept, so what is reported is what the reader sees numbered: the recovered marks with the references to departed blocks dropped. The shell keeps the report per document, as the marks themselves are kept, and the composer reads the active document's (`BO_0226_006`).
- The editor reads `reveal` for its document and shows what the chip points at: the block scrolled to the middle of the view and ringed for a moment in the selection colour — visibly neither the marked block's dashed accent outline nor the active block's accent border, and a ring as well as a colour — or a passage's words, resolved through the marking and painted under a highlight of their own (`calliopa-reveal`) beside the ring. A stale passage reveals the block that lost its words. It works in command mode and in reading mode, changes no content and no mode, and ends by itself after `REVEAL_MS`, leaving no trace in the markup; a second press ends the first emphasis before its own (`src/components/views/reveal.ts`, `CA_0039_005`). The editor's harness proves a block revealed while reading and in command mode, a passage, a stale passage and a second press, and the emphasis gone afterwards; a passage is revealed there only while reading, since this DOM has no `Range` for command mode's painter.

## Passages

* In command mode a reader can reference words inside a block, not only the whole block. Selecting words marks nothing; referencing them is an explicit act, **Reference** beside the selection, or `Enter` on a row holding one.
* A passage is anchored by its words — the exact quote, with the text either side to tell repeated words apart — never by a position, so it never silently retargets: it matches its words or says it no longer does.
* Blocks and passages share one number sequence in the order the reader marked them. A block marked and then a passage read `#1` and `#2`, and the rules for numbers hold across both kinds.
* A stale passage keeps its number and says so, and is repaired by selecting the words it should mean and choosing **Re-point #n**, keeping the number the command may already name. A command carrying a stale passage is refused until it is re-pointed or taken back.
* A passage is taken back by pressing its number, standing or stale, or by selecting its own words again, where **Take back #n** stands in place of Reference — as a marked block is unmarked by pressing it again. Pressing a passage's number never toggles the block it sits in; the row's one click handler asks which it was (`passageNumberAt`) before it marks.

- One block per passage: a selection dragged past a block's edge keeps the part inside the block it began in. A block marked whole and a passage inside it may both stand — *this paragraph* and *this clause of it* are different pointing.
- The press is decided once. A press that did not move marks the block; a press that dragged selects words and marks nothing; a release that ended a swipe marks nothing. Until `BO_0227`, a drag selecting a sentence marked its block, because a browser fires the click on the row both ends of the drag were in.
- A resolved passage is drawn where it sits, with its number beside it, and leaves no trace when the mode ends; the treatment is a tint and a dotted underline, visibly not the marked block's outline, not the active block and not authored formatting.
- A passage's quote is at most 2,000 characters, counted in code points on both sides of the kernel's intake. A reader pointing at more marks the block.
- A passage is kept with its row as a block reference is: whose block has gone, or has been discarded, it stays as what was marked. A passage whose words have gone from a block still present is stale, never dropped.

- `src/lib/passage.ts` anchors and resolves a passage over code points, as the editor's offsets count them: `anchorAt`, `resolvePassage`, `CONTEXT_CHARS` (32) and `MAX_PASSAGE_QUOTE` (2,000), ported from the retired artifact editor's `lib/passage.ts` (`BO_0137`), which counted UTF-16 units. `Reference` in `src/lib/references.ts` is a union on `kind` — a block, or a passage carrying its anchor — with `addPassage`, `repointPassage`, `removeReference`, `restoreReferences` and `passageState`; an entry stored with no kind reads as a block reference, so every `CA_0020` record survives (`BO_0227_008`).
- `src/components/views/passages/`: `selection.ts` reads the selected words out of the block the selection began in, clamped to it (`clampedOffsets` in `editor-dom.ts`); `use-passages.ts` tracks the selection in command mode and paints; `painter.ts` paints resolved passages with the CSS Custom Highlight API under `calliopa-passage`, writing no node into the text, and answers where each number goes; `passage-affordance.tsx` is **Reference** and **Re-point #n**, acting on `pointerdown` with that press's default prevented, since the press that reaches a control is otherwise the one that collapses the selection; `passage-numbers.tsx` draws the numbers and the stale ones in the gutter. The affordance reads its own store, so the words being selected are never re-rendered under the selection (`BO_0227_009`).
- `clickMarks` in `src/components/views/press.ts` is the one answer the command row's click handler asks, and the row's `Enter` references selected words rather than toggling the block. A row's accessible name says its passages and which are stale (`markingName`, `row-name.ts`) (`BO_0227_007`, `BO_0227_009`).
- The editor's marking lives in `views/marking/use-marking.ts` — the prompt, its record, recovery and persistence, and the report to the shell — and rows read it from `MarkingContext` (`BO_0227_006`).

## Marking Every Drawn Row

- Under `calliopa-bootstrap`'s `BO_0263` (2026-09-18), command mode marks every row the editor draws: a proposed change, a revealed retired block and a revealed discarded block, as well as a block of the document.
* A reference is what was marked. It keeps what its target was at the moment of marking, and a run gets it that way even when the target was answered, restored, reopened, retired or discarded since. The run is also told what has happened to it since. User decision, 2026-09-18.
* Marking a proposal points at the proposal: the run is told it is a proposal, who proposed it, and its proposed words. When the proposal is accepted, the reference's number moves to the block it became. When it is rejected, the reference stays as a chip in the composer, with no number in the document, since the row is gone, and it is taken back from the chip. User decision, 2026-09-18.
* A reference whose target changed is never a reason to refuse *Send*. User decision, 2026-09-18.
* Words inside a proposed, retired or discarded block can be referenced as a passage, under the same rules. User decision, 2026-09-18.
* A removal or a move proposal frames its block, and the two are marked apart: a click on the block's text marks the block, and the proposal is marked through its own face or edge. User decision, 2026-09-18.
- *A reference is what was marked* applies to every reference, not only the three new kinds: a block of the document that is retired or discarded after it was marked keeps its reference too, as a chip saying *since retired* or *since discarded*. Derived from the user's answer at transfer, 2026-09-18 (*"use it in the way it was marked. therefore, the same with retired, discarded"*), and taken as confirmed when the user set the change ready; a stale passage keeps its number and its refusal (`BO_0227`), since its words are gone from a block that still stands.
- The reference record (`BO_0263_004`, `src/extensions/documents/lib/references.ts`): a `Reference` carries what it points at — `target` absent for a block of the document, `proposal` with its `group` and `item`, or `retired` — and `revisionId`, the revision the reader saw: the block's, a retired block's last, a proposal's candidate, or, for a removal, the block it frames. It keeps the opening `words` and the `proposer` to show a reference whose row has gone, and `discarded` when the block was discarded as marked. `rowKey` says which row a reference stands on, so a block, a proposal on it and the block as retired are three references; `toggleReference` and `addPassage` take the marked target, and `referenceFor` and `passagesIn` the row. `followDocument` replaced the drop: it keeps every reference, moves a proposal's to the block it became when the document holds that block at the marked revision — CCGW establishes an accepted candidate under its own revision id — and drops only a reference naming no revision whose block has gone. A stored entry naming no target reads as a block reference, so every earlier record survives. The marking hook fills in the revision, the words and the discard of a block of the document as it marks (`asMarked`, `use-marking.ts`), and takes the proposals read so a proposal reference is followed only once the proposals are known. Discarding a block no longer drops its marks, and the undo's restore went with the drop.
- The rows (`BO_0263_005`, `src/extensions/documents/views/marking/row-marks.tsx`): `ProposalBlock` of the four kinds — its face for every kind, and its words for an insert and a rewrite — `RetiredRow` and `DiscardedRow` — their words — are the marking controls in command mode, with `aria-pressed`, a name saying what the row is and which reference it is (*Proposed new block by Claude Code, reference 1*, *Retired block: “Gone.”, reference 4*; `rowMarkingName`), the number in the gutter and the dashed outline on the row (`data-reference`, `block-editor.css`), and their passages' numbers, each a button that takes its passage back (`RowMarks`). A proposal's words are not editable in command mode, since typing into them accepts. A row names what it is for the selection (`rowMarkAttributes`, `data-mark-row` and `data-mark-text`), so selecting words in it offers **Reference**, anchored in the row's own words and standing on that row (`selection.ts`, `passage-affordance.tsx`). A derived candidate and a work item are not marked this way: a derived candidate is referenced by use (`BO_0246_006`).
- The report (`BO_0263_006`, `src/extensions/documents/lib/pointing.ts`): `pointingOf` reports each reference's `target`, `group`, `item` and `revisionId` to be sent, and shows `what` it is (proposal, retired, discarded), the `proposer`, `since` (rejected, restored, reopened, retired, discarded) and `rowless` when no row is left to carry its number. A passage is stale only against words that still stand where it was marked — a block of the document, or a proposal still open — so what has gone is told as marked and never refused. The reveal channel carries the chip's × (`{kind: "takeBack", number}`), which the editor answers by taking the reference back; revealing a proposal, retired or discarded reference finds its row by `data-mark-row`.

The accept-follow and the discarded row's control were each shown to bite by removing them. The render harness now establishes an accepted candidate under its own revision id, as CCGW does.

## Blocks As Commands

- Under `calliopa-bootstrap`'s `BO_0267`, promoted to draft by the user on 2026-09-18 and transferred here the same day, a block is the command. While the person edits a block, a control on it chooses the agent, points from it, attaches files and sends it; a sent block becomes a prompt, which leaves the reading order unless it is kept as content. The shell's half is `ui.shell`'s `commands-and-runs.md` and `agent-activity.md`, Blocks As Commands and Execution (`BO_0267_007`–`BO_0267_011`); the kernel's half is `calliopa-bootstrap`'s `ui-kernel.md`, Blocks As Commands (`BO_0267_001`–`BO_0267_006`).
* While a text block is being edited, one control stands on its bottom border: the agent, pointing (`◎`), attaching, and *Send* with a caret. A plain *Send* sends the block as a prompt; the caret offers *Send, keep as content*. User decision, 2026-09-18.
* Command mode starts from `◎` on the active block's control and points for that block: a click on another row marks it as a reference of this block, and `◎` again ends pointing. User decision, 2026-09-18.
* References belong to the prompt block: sending it again reuses them, and each run gets a copy of the marks as they stood at its send. User decision, 2026-09-18.
* Editing a sent prompt and sending it again starts a new run on the same block, from the new revision. User decision, 2026-09-18.
* Typing `#` in the block being edited offers its references by number, as the command field did. User decision, 2026-09-18.
* Files are attached to the prompt block, from its control or by dropping them on the active block, show as chips on its control line, and go with the next *Send*. User decision, 2026-09-18.
* `Ctrl`/`Cmd`+`Enter` in the block being edited sends it as a prompt. User decision, 2026-09-18.
* *Send as prompt* names its shortcut in its tooltip. User decision, 2026-09-23 (`DO_0015`).
- The button's `title` reads `Send as prompt · Ctrl+Enter`, the cost after it as before (`Send as prompt · Ctrl+Enter · about …`); on an Apple platform it reads `⌘+Enter`, the key the listener also takes (`sendShortcut` in `command-control.tsx`, from `navigator.platform` at render, which happens in the browser since the control is drawn only on the block being edited). Its label stays *Send as prompt*. `command/command-control.test.ts` proves the title names the shortcut (`DO_0015_007`, landed 2026-09-23).
- The command control (`BO_0267_012`, `views/command/command-control.tsx`) stands just below the bottom border of the block being edited, and of the prompt pointed from, where the agent's mark and a proposal's line stand: inset by the gutter, its middle 0.9375rem (15px) below the edge so it covers little of the block being edited, and out of the flow, so showing it moves no block (user decisions, 2026-09-18, `BO_0267_024`, and the 15px the same day). One chip holds the whole line — a single border around five icon buttons of one size, 24px, each named by its label and titled with it, and the chips of what the command carries between them (user decisions, 2026-09-18, `BO_0267_027`, `BO_0267_028`) — in this order: `AgentMenu` over `bridge.agents`, *Point from this block* (`data-block-point`, Phosphor `crosshair-simple`, `aria-pressed` while pointing), *Attach files* (the shell's `command-attachments.tsx`), and *Send* as two buttons — the press named *Send as prompt* (`data-block-send`, the play glyph alone), the caret *More ways to send* opening a menu with *Send, keep as content*. The agent shows its face alone in the chip. Send and its caret stand at the line's end, after the chips (`BO_0267_028`). The line's rules are written through `.block-command__line`, so the shell's rules for the dock's own agent dropdown and paperclip, which keep their fingertip size there, never outweigh them whatever order the stylesheets load in. Measured in Chromium on the editor's own markup with `shell.css` loaded after `block-editor.css`, on a fine and a coarse pointer: agent, point, attach, `#1`, `#2`, send, caret on one line in a 28px chip, the five buttons 24×24 and the chips 20px high, 15px below the block's bottom edge, the following row where it was. The chips of what the command carries stand in the line after *Attach files* (`AttachmentChips`, then `ReferenceChips` over the prompt's report, `store.report`), and a chip's press asks the view for its area through `reveal`. Its presses are its own (`stoppropagation:click`), so a press on it never marks the row. `sendBlock$` in the editor sends: a block being edited is saved first and stays edited, so the revision sent is the one the graph holds (`editor.baseRevisionId`); the prompt pointed from is sent as the document read it; an empty block is refused in words. It calls `sendCommand$` with the block, the revision, the words and the ready attachments; on success it ends pointing, and a plain *Send* writes the `prompt` standing through `setStanding$`, which offers *Undo: Sent as prompt …*, while *keep as content* writes nothing. A refusal — the shell's or the kernel's, a stale passage, a dangling `#n` — is said in a note floating under the control, over what follows (`data-block-send-refusal`), and writes nothing. A file dropped on the block being edited is attached to its command (`preventdefault:dragover`/`drop` on the active row); the attachments are the editor's, per block for the page (`commandFiles`), so the paperclip and a drop fill one list.
- Pointing from a prompt block (`BO_0267_013`). `◎` calls `point$(blockId)`, which makes the block the prompt (`selectPrompt$`) and enters the mode, the block still edited; a click on any other drawn row marks it for that block under the rules above and `BO_0263`'s, and the prompt itself is not marked from itself. `◎` again ends pointing, the prompt still edited, and `Escape` ends it too. The marks are one set per prompt: `markingKey(documentId, prompt)` is `calliopa.marking.<document>.<block>`, numbered from `#1` for each block and kept without the mode; `store.byPrompt` holds each prompt's marks for the page; a block with none on the page or the device takes its latest visible run's `references` (`GET /api/runs?artifact=`, `markingFromSent` in `lib/references.ts`), a passage anchored by its words alone; and the record a document kept before (`legacyMarkingKey`) is dropped on the way in. Editing a block makes it the prompt. `#` in the block being edited offers the prompt's references through `pendingReference` and `referenceMatches` in a list above the control, and choosing one writes `#<number> ` at the caret through `editRuns$`, keeping the marks of the words around it.
- Proven in the render harness (`command/command-control.test.ts`, `BO_0267_023`): pointing from the block being edited leaves its editor, a row marked from it opens none, a press through the page's own listener on another row leaves the prompt edited — failing without the listener's guard — and ending the pointing leaves it edited.

## A Contributed Control In The Chip

- Under `calliopa-bootstrap`'s `BO_0273`, an extension may put a control in the chip. The slot is
  `ui.shell`'s — one more `BlockPlace`, `command`
  ([Contribution Contract](../../../../../../docs/system/workspace/contribution-contract.md#a-control-in-the-command-chip),
  `BO_0273_007`); drawing it is this extension's.
* A contributed control is drawn like the chip's own: one border around controls of one size, 24px
  on every pointer, no touch minimum, as `BO_0267_027` set it. The chip does not grow a second row.
  User decision, 2026-09-21.
- The chip draws it (`BO_0273_009`). `CommandControl`
  (`views/command/command-control.tsx`) renders `BlockDecorations at="command"` after
  *Attach files* and before the chips of what the command carries, so *Send* and its caret keep the
  line's end (`BO_0267_028`); it hands the block's id, the document's, the revision the editor is
  based on while this block is the one being edited, and `active`. The chip knows nothing of what
  it draws. Its presses are already its own (`stoppropagation:click` on the control), so a
  contributed press never marks the row in command mode, and the line's rules stay written through
  `.block-command__line`.
- Proven in `views/command/command-decorations.test.ts` in the render harness, with the generated
  registry — the build's own seam, written from the manifests in the tree — supplying a fixture
  decorating extension and nothing else stood in for: the control drawn on the block being edited
  with its ids and `active`, its place in the line after pointing and before *Send*, two extensions
  drawn in contribution order, and an extension offering another place drawing nothing here while
  the chip stays itself. Each was shown to fail with the draw site wrong. The command suites and
  the registry suites pass (48 tests) and the tree typechecks.
