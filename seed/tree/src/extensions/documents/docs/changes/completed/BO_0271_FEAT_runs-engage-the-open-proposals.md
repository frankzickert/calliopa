# A Run Works With What Is Already Proposed

Status: completed

A run that works in a document with unanswered proposals should read them and refine them where they need it, instead of writing new content beside them. Every proposal the person has not accepted is open matter: the run may argue with it, sharpen it, or supersede it. An accepted block is the settled ground, and a run proposes against it only exceptionally — unless the person's command referenced it, which makes it the subject. The rules are carried by the prompt guides Calliopa gives the run: the `ext.skill` members it reads and the kernel's run instructions. Requested by the user, 2026-09-20, and decided with them the same day. It authorizes no implementation and transfers no system tasks.

## What Is Wrong Today

- **A run cannot see the open proposals at all.** `read_document` and `read_blocks` answer established truth at the run's pin (`ui-kernel.md`, the document tools). A candidate is visible only through an overlay — the run's own group, or the branch a run is bound to (`BO_0250_005`, `BO_0250_007`) — and CCGW otherwise resolves `established` over `candidate` unless a read asks for candidates (`ccgw.md`, `INCLUDE CANDIDATES`). The one path by which another group's proposal reaches a run today is the person marking it in command mode: the instructions then render `#n → proposal by <proposer> (<rewrite | new block | removal | move>) for block <id>: "<words>"` with the words quoted **because the run cannot read a candidate with `read_document`** (`ui-kernel.md`, `BO_0263_009`). A run the person did not point at a proposal works as if the document were settled.
- **The document is not settled, and increasingly so.** A command run's items stand at their targets until they are answered, and several runs may work in one document at once, each staging its own group (`documents`' [The Agent At Work](../../graph/tree/src/extensions/documents/docs/system/documents/agent-at-work.md), *Several Runs At Once*; `BO_0269`). The second run writes over the same ground as the first without knowing the first exists.
- **The block model already refuses the naive answer.** Every block type declares `singleOpenCandidate`, so a block carries at most one open proposal rather than a stack of them (`data-model.md`; `ccgw.md`, which counts members only, so carry-forward anchors do not collide). A run that decides a standing rewrite is nearly right and stages its own rewrite of that block is refused — there is no second candidate. Refining the proposal that stands is therefore not only the better manners the user asks for; for a rewritten block it is the only shape the core admits.
- **Nothing in the guides says any of this.** `ui.shell.documents`'s conventions cover prompts, notes, per-item answers, claims and relations, and the commit gesture; `calliopa-base.working` covers staging, the work vocabulary and `proofsAreNotProposals`. Neither mentions what stands unanswered in the document. The kernel's `deliveryNote` tells the run to read the document and stage into it, and for a question to place one insert after the command block (`ui-kernel.md`, Blocks As Commands, `BO_0267_003`) — a rule about where new content goes, with nothing about content already proposed.
- **The nearest existing rule is about standing, not proposals.** The instructions already say what a disposition asks of a run: a kept block is left standing — the run proposes neither removing nor rewriting it unless the command names it — and discarded and resolved blocks are set aside and not material to build on unless the command asks (`BO_0227_003`, `DispositionMeaning`). The user's rule is that shape applied to acceptance itself: established words are left alone unless the command reaches for them, and unanswered proposals are where the run is free to work.
- **Duplicate proposals spend the person's attention twice.** `calliopa-base.working`'s `proofsAreNotProposals` already says that frequent near-identical almost-always-correct proposals spend down the attention acceptance is worth. Two runs proposing the same paragraph in two groups is exactly that, and the person has to answer both to settle one question.

## Scope

* A run working in a document with unanswered proposals reviews them and refines them where they need refining, rather than only adding new content. User request, 2026-09-20.
* Any proposal the person has not yet accepted is subject to discussion: the run may refine it, argue with it, or replace it with something better. User request, 2026-09-20.
* A run may propose a change to an accepted block, but this is the exception unless the person's command referenced that block. User request, 2026-09-20.
* The rules are carried by the prompt guides Calliopa gives the run — its `ext.skill` members and the kernel's run instructions — not by the person having to say them in every command. User request, 2026-09-20.
* A run refines a standing proposal by building on the candidate that stands, not by staging a second one: an item of `propose_document_changes` names the group and the item it refines, and the staging builds on that group's candidate, as the editor already stages into another proposer's group when a reader moves their proposal. One block keeps one open proposal, and the person answers once. User decision, 2026-09-20.
* What the run is told and what it reads: the delivery note says how many proposals stand unanswered in the document, and `read_document` answers each block's standing proposal — its group, its item, its proposer, its kind and its words — with the proposed inserts, which are in no block, as a list of their own. User decision, 2026-09-20.
* A run may propose against an accepted block when the command referenced it — a reference or a passage marked in command mode — and when the command plainly asks for those words to change; otherwise settled words are left alone. This is `BO_0227_003`'s *unless the command names it*, applied to acceptance. User decision, 2026-09-20.
* A person's branch is refined only by a run working in it — the run bound to that group (`BO_0250_005`). Another person's branch is read as context and never touched. User decision, 2026-09-20.
* A system run's derived candidates are read as context and never proposed against: they are answered by use, and a pinned framing is never overwritten (`BO_0246`). User decision, 2026-09-20.
* A proposal is refined once its run has ended. A run still staging may restage the same block a moment later, so its items are left to finish, and the refining run's final words say what it left standing. User decision, 2026-09-20.
* The run stages only what needs changing. Where a standing proposal already says what the run would say, it leaves those words as they are; it says so only when there is really nothing to add anywhere. User decision, 2026-09-20.
* A refined proposal is the refiner's work with its origin kept: the chip carries the refining run's face and words and says it refines an earlier proposal, naming its proposer. User decision, 2026-09-20.
* A commit command is answered as it is today — one phase item on the document — and its one sentence of consequences names the proposals standing unanswered in it. User decision, 2026-09-20.
- A guide can only ask for what the run can see and do, so this change carries whatever the run needs to read the open proposals, and whatever it needs to refine one, beside the guide's words.
- The rule reads the same for every agent and every delivery a document takes: a command sent from a block, a command from the composer aimed at the open document, and a system run's refinement all meet the same standing proposals.
- Refining builds on a candidate rather than beside it, so `singleOpenCandidate` is honoured rather than worked around: a block still carries at most one open proposal, which is what makes the person's answer one answer.
- Nothing here lets a run answer a proposal. Accepting and rejecting stay the person's, as they are for every proposal a run stages (`calliopa-base.working`, `proofsAreNotProposals`).
- An item the person has already answered is settled and is not refined. A group's members are answered one at a time (`ccgw.md`, `ACCEPT PROPOSAL p MEMBER m`), so a group may hold answered and unanswered items at once, and only the unanswered ones are open matter.
- The count in the delivery note, and what `read_document` answers, name only the proposals the run may refine: a live run's items, another person's branch and the derived candidates are read as context and counted apart, so the count never sends the run looking for items it must leave alone.

- The guide half is a revision of the `ui.shell.documents` member — the `ext.skill` of `documents` that every run working in a document reads (`ui-kernel.md`, `skillsForRun`) — and, where the rule is about staging rather than documents, of `calliopa-base.working`. Both are staged with `kernel commit --members` in this change's graph proposal, and the truth they become is the owning extension's docs in the graph.
- The fixed-layer half is the kernel's: what a run is told about the document's open proposals in `deliveryNote`, and what the document tools answer about them. It is enumerated in `docs/system/ui-kernel.md` when this change reaches draft.

## Verification

- The guide half is verified by a live run: with an unanswered proposal standing on a block from an ended run, a command that bears on that block is answered by the run refining that proposal in place rather than by a second proposal beside it — the block still carries one item, its chip carries the refining run's face and says what it refines, and the person answers once. A standing proposal that already says what the run would say is left as it is, and the run says so.
- The accepted-block rule is verified the way `BO_0227`'s kept blocks were: a command that would plausibly rewrite settled words without naming them stages nothing against them, and the same command with the block referenced does propose against it.
- The exclusions are verified on the instance: a run staging while another run works in the same document leaves the live run's items alone (`BO_0269`'s two-runs-at-once walk is the shape); a run in one person's branch does not touch another's; and a command run stages nothing against a derived candidate or a pinned framing.
- The kernel half is verified by the golden instruction renderings, as `BO_0267_006` and `BO_0263_011` verified theirs: the new sentences where decided, every other rendering byte-identical, and a document with no open proposal rendering exactly as it does today.
