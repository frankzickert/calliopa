# Bunny Stream

Under `PU_0004`, requested 2026-09-14: the first kind whose unit is an item, and the host every video slot of a website needs.

## Bunny Stream Is A Channel

* A `bunny-stream` channel is a video library at Bunny Stream: its configuration is the library's address at Bunny — `https://video.bunnycdn.com/library/<numeric id>` — its credential the library's key presented as `AccessKey`, probed by listing one video of the library — the smallest authenticated call, and one that changes nothing. Its offer is fixed: one slot of class `video` with no constraint of its own. Its unit is the **item**; its acts are `publish` and `retire`. It is created, configured, tested, retired and deleted as a website channel is.
* A video item is published to a Bunny channel from its tab. Publishing uploads the export's bytes once — a create call answering the video's id, then the bytes — and logs the entry with that id as the external id; the state at the channel derives from the log as for any record. The same export published again uploads nothing. A replaced rendition is a new upload, and the old video stays at Bunny; deleting there is no act of this extension. User decision, 2026-09-14.
* Bunny shows `<deliverable title> — <part title>` as the video's title when the item fills a part, and the item's label when it stands alone. User decision, 2026-09-14.
* Homepage's `host_id` slot field is not filled: the id travels as the entry's `host` ([Website](./website.md), The Container Document), and the field is homepage's to drop from its index in the change that accepts the container document. User decision, 2026-09-14.
- The Stream API is two calls under the library's address: `POST /videos` with the title, answering the `guid`, then `PUT /videos/<guid>` with the bytes; retiring is `DELETE /videos/<guid>`. The library's address is the channel's one configuration field, checked as an address like a website's, so the kind's paths sit under it the way a website's sit under its address and the broker needs nothing written beside the field; a wrong library is what the probe reports. The address rather than a bare numeric id: the settings row refuses a stored key the kind does not list, so a fixed address written beside a library id would read as unconfigured. Technical decision, 2026-09-14.
- The kernel's broker takes bytes base64 in a JSON body of at most 512 MiB, so an export above roughly 380 MB is refused before the upload as `tooLargeToBroker`, naming `BO_0252`, which streams a blob by hash. Homepage's episodes are minutes long and fit.
- `server/kinds/bunny-stream.ts` is the kind against the kind contract: the descriptor (`address` labelled *Library*, checked as `address`; `authorization: { header: "AccessKey", scheme: "", secretField: "apiKey" }`; probe `GET {configuration.address}/videos?itemsPerPage=1` expecting `200`), `offer` fixed to one video slot, `units: ["item"]`, `acts: ["publish", "retire"]`; `projectVideo`, pure over an item and the title, answering the upload — the item's first export, the ingested rendition — or its refusals (`notAVideo`, `noExport`, `tooLargeToBroker` naming `BO_0252`, `titleRequired`); `deliverVideo` as the two calls answering the `guid`, a `2xx` that is not Bunny's JSON a failure in Bunny's words; `retireVideo` as the delete; `takesItemsOf` is the test a video slot's host must pass — a kind whose unit is the item and whose fixed offer holds the class. `server/kinds/registry.ts` lists it; the channel's row draws the globe, the icon a kind the table does not name gets. `server/kinds/bunny-stream.test.ts` proves the projection and every refusal over records and the calls over a recording transport (`PU_0004_001`).
- `tests/behavior/host.ts` is a stub Bunny library in the harness that validates what it receives — the `AccessKey` header, the library in the path, a title on the create call, a guid it minted on the upload, bytes that are not empty — answers the Stream API's shapes and lists videos for the probe. `tests/behavior/publish.test.ts` creates a `bunny-stream` channel beside the stub site, assigns the video part with it (`hostRequired`, `notAVideoHost` and `hostNotForClass` refused first), reads the item's rows, publishes the video from them under *E1 — Main video* with the guid in the entry, publishes it again with nothing sent and the same guid, logs a wrong key as failed in Bunny's words, proves the website's refusal naming the host while the video is retired there and the document carrying the guid as the entry's `host` once published, refuses the item's deletion while live, and retires it with a delete at Bunny (`PU_0004_006`).
- `pnpm run verify:publish:bunny-stream` is the gate in the `publish` vitest project (`tests/publish/bunny-stream.test.ts`): `CALLIOPA_PUBLISH_CHANNEL` names a verified `bunny-stream` channel and `CALLIOPA_PUBLISH_ITEM` the video item; it fails rather than skips without them, and proves the upload against a real library (`PU_0004_007`).
