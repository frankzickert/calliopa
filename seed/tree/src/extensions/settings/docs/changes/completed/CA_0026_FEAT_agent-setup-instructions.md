# CA_0026_FEAT_agent-setup-instructions

Status: completed

Requested: 2026-09-03

## Intent

When the agent is not fully configured, the tool should say what is missing and
what the human has to do about it, in the tool — including the one setup step
the product cannot perform for them.

Reported after a first configuration against a real agent container: the
runtimes were signed in from the settings surface, but issuing the agent's own
`cak_` credential, writing it into `.env.dev`, and restarting the stack were
found by asking an agent in a terminal rather than by reading anything in the
product. Nothing in the tool says the agent has no tools, and nothing says what
to run.

[Calliopa Agent](../../../../../../docs/system/agent/calliopa-agent.md) already holds the design this
builds on: the runtimes' status is what the agent's probe reports, the
application holds no control over the Docker daemon, and the agent's credential
is issued by the operator command like any other machine caller's. The gap is
that none of it is visible to the human doing it for the first time.

## What Happens

### The `hermes` row never reports the agent

`probe_adapters()` writes an entry for `codex` and one for `claude-code` and
nothing else (`hermes-login-broker.py:139`). The `hermes` row is a `status`
party like the other two, so reading it falls to the no-report branch of
`withStatus` (`src/server/connections.ts:75`): state `unconfigured`, and the
error `The agent has not reported on this runtime.`

That is what the row says on a stack where the agent is healthy, both runtimes
are signed in, and runs work. The one row named after the agent is the one row
that is never true, and it offers no `Sign in` either, because signing in is not
what it needs (`src/components/views/settings.tsx:232`).

### Nothing says the agent has no tools

`CALLIOPA_AGENT_TOOLS_TOKEN` is deliberately not generated by bootstrap: it is
issued by `pnpm run client issue hermes --proposer`. Absent, the entrypoint
skips both registrations and says nothing to anyone
(`hermes-entrypoint.sh:105`, `hermes-entrypoint.sh:126`) — which is the right
behaviour for the container, because an agent that cannot reach documents is
still a working service to sign a subscription into.

The cost is that the failure is silent everywhere a human looks. The agent
starts, `/health` answers, the runtimes report `ready`, a goal opens a run and
the run reasons. The only symptom is an agent that cannot see a single document,
and nothing distinguishes that from an agent that read them and had nothing to
say.

The application cannot infer this either. The variable is passed to the `hermes`
service alone (`docker-compose.yml:72`), so the only honest source is what the
agent reports about itself over the shared volume — the same route the runtime
probe already uses. The entrypoint stamps the active runtime there and nothing
in the application reads it (`hermes-entrypoint.sh:159`; the only readers are
the verification stack's assertions).

### The step the product cannot take

Issuing the credential, writing it into `.env.dev`, and restarting the agent are
a terminal's work. The application deliberately holds no control over the Docker
daemon, and a token that the surface could write into `.env.dev` would be a
secret round-tripping through a surface that is built to hold none.

So the instruction is the deliverable. The tool cannot do this step; it can name
it exactly, and today it does not name it at all.

## Shape

- The tool reports what is missing between a running agent and one that can do
  the work, in the reader's words, and names the command for the part only a
  terminal can do.
- What is missing is read from what the agent reports, not inferred from what
  the application happens to know about its own environment.
- Nothing here presents a secret. The credential is printed once by the operator
  command in the terminal; the surface names the command and never the token.

## Decided Behaviour

Answered by the user on 2026-09-03.

### Where it appears

- The `hermes` connection row is the only place. The settings surface is where
  configuration already lives, and this is the row named after the agent.
- The command dock gets nothing. A second surface would be a second account of
  the same state, and the reader who is configuring the agent is in settings.

### What the row says when something is missing

- The row is the whole picture: everything standing between the agent and doing
  its work, in one place, whichever row fixes it.
- That includes a runtime that is not signed in, even though the `codex` and
  `claude-code` rows show it too. The Hermes row names it and points at the row
  that fixes it rather than offering a second `Sign in` control, so the state is
  read in two places and acted on in one.
- The agent not answering at all is one of the conditions. The surface already
  distinguishes it during a sign-in; here it is a standing state of the row.
- The absent tools credential is the condition this change exists for, and it is
  the one the reader can do nothing about from inside the product.
- The agent's memory is named too, as a lower line marked optional rather than
  blocking. The `honcho` key does not stop the agent working and has its own
  key-taking row; a reader still deserves to see the whole of what the agent
  could have.

### The command

- `pnpm run client issue hermes --proposer` is shown literally, with a control
  that copies it.
- The name is not incidental and must not be paraphrased: the application
  resolves a run's owner by the client name `hermes`.
- What follows the command — the `.env.dev` line and the agent restart — is
  named in the same block, because the credential does nothing until the
  entrypoint reads it at start.
- This is the first shell command the product puts in front of its reader. It is
  accepted because the alternative is a step the product cannot take and does
  not mention.

### What the row says when nothing is missing

- The row reads as a configured row rather than falling silent: the active
  runtime the agent is running, and that its toolset is registered.
- The active runtime is already stamped by the entrypoint
  (`hermes-entrypoint.sh:159`) and read by nothing in the application. This is
  the surface that reads it.
- The tools state has no source yet. The entrypoint knows whether it registered
  the toolset and must report it onto the shared volume the way the runtime
  probe already reports, so the row states a fact rather than inferring one.

### Coming to the truth after the terminal step

- The settings surface re-reads the connections on an interval while the agent
  is not ready, so the row catches up on its own once the human has run the
  command and restarted the agent.
- The restart is the agent's, not the application's, so nothing else would bring
  the surface to the truth; a reader who has just come back from a terminal
  should not have to guess that a reload is what they owe the page.
- The polling stops once the agent is ready. A surface that keeps asking after
  the answer stops changing is a cost with no reader.

## State

- Every task this change enumerated in
  [Calliopa Agent](../../../../../../docs/system/agent/calliopa-agent.md) is implemented and folded into
  truth: the entrypoint's stamp, the `hermes` row reading from it, the row's
  whole picture, the literal command with its copy control, and the polling
  that stops when nothing blocks the agent.
- `CA_0026_006` remains open and is not this change's work: every status row
  still says `No key` while unconfigured, which is the key-taking vocabulary on
  parties that hold none.
- `pnpm run verify` passed every gate, including `hermes service` with the
  token-absent case this change added and this change's own four
  `agent-settings` scenarios on both form factors.
- The run before it failed on `browser scenarios` alone, on the cross-block drag
  scenario the unowned note in
  [Block Editor View](../../../../../../docs/system/documents/block-editor.md) already describes as
  intermittent on trees that do not touch dragging. It passed unchanged on the
  next run against the same tree, which is the behaviour that note records.

## Verification Impact

- `tests/browser/agent-settings.spec.ts` runs with no agent container beside it,
  which is exactly the unconfigured state this change is about. The missing
  lines, the literal command, the copy control, and the pointer to the runtime
  rows can all be proven there.
- The configured half cannot be proven there: it needs an agent that reports a
  registered toolset and a signed-in runtime, which the ordinary gate has no
  subscription for. It belongs with the environment-gated work `CA_0022_019`
  names in [Calliopa Agent](../../../../../../docs/system/agent/calliopa-agent.md).
- The entrypoint reporting its tools state is provable in the ordinary gate. The
  `hermes image` stage in `scripts/lib/verify-stack.mjs` already starts the image
  with a tools token, reads what the entrypoint stamped, and asserts both
  registrations (`verify-stack.mjs:409`, `verify-stack.mjs:502`), so what it now
  reports about the toolset is assertable beside them. The token-absent case is
  the one the gate does not run today and this change needs, because that is the
  state the row exists to describe.

## Notes

- `CA_0025_FIX_sign-in-code-and-status-refresh` is `wip` and is editing the
  sign-in block of `src/components/views/settings.tsx`. This change touches the
  same rows, so it should not be implemented alongside it.
- Whatever the agent reports about its tools has to be written by the entrypoint
  or the broker onto the shared volume, which means this change reaches the
  agent image as well as the surface.
