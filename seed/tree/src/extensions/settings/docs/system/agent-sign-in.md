# Agent Sign In

## Subscription Sign-In

* Credential homes live on the agent's own data volume, under `HOME` pointed at the Hermes home. No subscription credential is stored in Postgres and none is written to `.env.dev`.
* An agent belongs to the instance it runs in. Each stack has its own data volume, so its subscriptions are signed in there, its memory is derived there, and its `cak_` tool credential names a client row in that stack's own database. A credential copied between instances names a client that does not exist. The production instance's agent is a proposer and may not write truth; [Application Foundation](../../../../../docs/system/foundation/production-instance.md), Production Stack, owns why.
* The human signs in from the settings surface. A login broker inside the agent container serves the flows over a shared volume, so signing in never requires `docker compose exec`.
* Codex signs in with `codex login --device-auth`, which prints a URL and a one-time code and polls. Claude Code signs in with `claude setup-token`, which prints a URL and takes a code pasted back.

- The broker adopts the Codex CLI's token pair into Hermes's own auth store, refreshing an expired pair first. Hermes's `openai-codex` provider resolves credentials from its own store while the device-code login lands them in the CLI's home, and Codex's refresh tokens are single-use, so the fresh pair has to land in both stores in one operation.
- A probe reports each runtime's installed state, version, verified authentication, and billing mode without exposing any credential. That report is what the `claude-code` and `codex` connection rows show, and it is why those rows hold status rather than a secret.
- Authentication is verified by asking each runtime — `codex login status` and `claude auth status` — rather than by looking for a credential file. A file that exists is not a session that works: an expired or revoked login leaves the file exactly where it was.
- The sign-in URL and the one-time device code are mirrored to the surface, because they are what the human must see and use once. What is never mirrored is anything that would authenticate again: the long-lived token the Claude flow prints is captured for the gateway and redacted from the state in the same pass that reads it.
- Losing the agent's data volume means signing in again. That is the accepted cost of keeping the credentials where their own tooling expects them, on a development stack where signing in is a minute's work.
- Agent configuration is a first-start step in the settings surface, not an install secret. Install stays zero-secret for the human.

- `hermes-login-broker.py` runs inside the agent container and serves both sign-ins over the shared volume: the settings surface writes a request, the broker runs the runtime's own flow, and the state it mirrors is what the surface renders. The alternative is `docker compose exec`, which means a human at a terminal on the machine — and an agent nobody can configure from the product is an agent nobody configures (`CA_0022_006`).
- The flows are the runtimes' own rather than reimplemented. Codex's device-auth prints a URL and a one-time code and polls; Claude's `setup-token` is an Ink TUI that renders nothing without a terminal, so it runs on a pseudo-terminal, wide enough that the URL does not wrap into a fragment, and the pasted code is written to it and submitted a moment later because one combined write races the input handling (`CA_0022_006`).
- A successful Codex login is adopted into Hermes's own auth store in the same operation, refreshing an aged pair first and writing the fresh pair to both stores: the provider reads one, the app-server subprocess reads the other, and refresh tokens are single-use, so a second copy taken later would already be spent (`CA_0022_006`).
- One broker at a time, held by a lock for the life of the process: a second would race the first for requests and for the pseudo-terminal. A failed token adoption is reported and never takes the broker down with it (`CA_0022_006`).
- The gate proves what a fresh instance actually is, because neither runtime can be signed in without a real subscription: the probe reports both runtimes installed, versioned, and `unconfigured`; the broker answers a request over the shared volume, proven with the one request that needs no account; and nothing matching a credential, a bearer, or a signed token reaches the volume the settings surface reads or the container's log (`CA_0022_006`).
- A connection is one of two kinds. An `apiKey` party takes a secret Calliopa stores and presents; a `status` party takes none and holds only what something else reports about it. `hermes`, `codex`, and `claude-code` are the status parties, and the database refuses a secret on one, so a later change cannot quietly store what this design says never enters the store (`CA_0022_007`).
- A status row's state is not stored. The runtime's own answer is the truth and a copy in the database would be a second account of it that can go stale, so the probe's report is laid over the row when it is read — and expressed in the states every connection already has, so the surface reads one vocabulary rather than two (`CA_0022_007`).
- A status row offers no key field, no `Save`, no `Test`, and no `Clear`; asking to test one answers that it holds no key to test. Signing in is the only thing to do on one, and only while the runtime is not signed in (`CA_0022_007`).
- The application and the agent talk through files on the shared volume, which the application mounts. It can ask the agent for a sign-in and follow how it is going; it cannot restart it, because it holds no control over the Docker daemon. When nothing answers at all, the surface says the agent is not running rather than leaving a control disabled for as long as a login could have taken (`CA_0022_007`).
- The code the Claude flow asks for is sent by a `Send` button beside the field, or by `Enter` in it. Leaving the field sends nothing: sending is a deliberate gesture, and a field that spent its code on blur spent it for a reader who had not decided to. An empty field sends nothing (`CA_0025_001`).
- Once the code is sent, the field and its button give way to a line saying the code was sent and the runtime is finishing. The surface knows it has sent one the moment it does; the broker says the same a poll later by moving `awaiting` to `cli`. Nothing interactive is left in the block, which is true to a code that is one-time and already spent (`CA_0025_001`).
- The `Sign in` control reads `Signing in…` while its flow runs, because a control still reading `Sign in` names an action already under way. This is the one part of a sign-in the ordinary browser gate can prove: the flow is under way from the moment it is asked for, whether or not anything answers (`CA_0025_002`).
- The broker adopts, probes, then publishes. The surface stops watching the moment the login state stops being `running` and re-reads the row, and a status row is what the probe last reported — so a success announced before the probe is a success the row cannot yet show, and the human is left reloading to see it. The adoption goes first either way: the probe asks `codex login status`, and the adopted pair is what makes that answer true (`CA_0025_003`).
- A sign-in is therefore reported when the runtime agrees it happened, not when its flow exits. The human watches it for as long as the two `status` calls take, which is honest rather than slow (`CA_0025_003`).
- [ ] CA_0022_019 Prove a sign-in flow end to end on a machine that may reach the internet. Codex's device-auth call reaches OpenAI to mint a code before anyone signs in, so the URL and the one-time code the surface presents can be proven without an account — but not in a gate that must not depend on an external service being up. Prove that the surface presents the URL and the code, that pasting a code back reaches the Claude flow, and that a failing sign-in reports what the flow returned by name. This belongs with `pnpm run verify:agent`, the environment-gated gate `CA_0022_017` built, not with the ordinary suite. It is also where `CA_0025_001` and `CA_0025_003` prove themselves, because a real flow is the only place the code control, the state after sending, and the row being true without a reload can be observed.

## Setup Reporting

- What the agent is configured with is known to the application only through what the agent reports onto the shared volume. The tools credential reaches the `hermes` service alone, so the application cannot see it and has to be told.
- Issuing that credential, writing it into `.env.dev`, and restarting the agent are a terminal's work. The application holds no control over the Docker daemon, and a token a surface could write into `.env.dev` would be a secret inside a surface built to hold none — so the instruction is what the product offers instead of the action. `CA_0026_FEAT_agent-setup-instructions` is the originating change for what the reader is told.

- The entrypoint stamps what the start assembled: the active runtime, whether the agent holds a tools credential, and whether the toolset reached Codex. The credential is passed to the `hermes` service alone, so what the application can say about the agent's tools is only what the agent stamped (`CA_0026_001`).
- A missing credential and a failed registration are stamped apart. They ask different things of the reader: one is a credential to issue at a terminal, and the other is not fixed by issuing a second one (`CA_0026_001`).
- Codex's registration is removed when the agent holds no credential, because Codex keeps its configuration on the volume and an entry left behind would outlive the credential it names (`CA_0026_001`).
- The gate proves both states. The configured one stamps a credential and a registered toolset beside the runtime it already asserted; an instance whose credential was never issued stamps neither and leaves neither runtime holding the toolset, which is the state the reporting exists to describe and the one the gate did not run before (`CA_0026_001`).
- The `hermes` row reports the agent rather than a runtime. What it says is what the agent stamped, laid over what its reasoning runtime reports about itself: verified when that runtime is signed in and the toolset is registered, failing when a credential is held and the toolset is not, and unconfigured otherwise — including when the agent has stamped nothing at all, which is the agent not running (`CA_0026_002`).
- The row carries what the agent stamped beside the runtime reports, so a surface renders a fact rather than deriving one from a state word (`CA_0026_002`).
- The directory the application and the agent meet in is read when it is read rather than when the module loads. A test then proves what an instance reports from a directory of its own, instead of reading the machine's agent volume — where the same assertion passed or failed depending on whether whoever ran the suite happened to be signed in (`CA_0026_002`).
- The agent's row says everything standing between the agent and its work, composed from the rows the surface already holds rather than from a second report. More than one thing can be missing at once, so it is a list rather than the single error line every other row carries (`CA_0026_003`).
- A runtime that is not signed in is named in the agent's row and pointed at its own row. The state is read in one place and acted on in another, rather than the agent's row growing a control that belongs to a runtime (`CA_0026_003`).
- The agent's memory is named there too, and reads as optional rather than as a failure, because it does not stop the agent working (`CA_0026_003`).
- An agent that has stamped nothing reads as not running, and that is the whole of what its row can say: what it would report about a credential or a toolset is not knowable until it has started (`CA_0026_003`).
- When nothing is missing the row says what the agent is reasoning on and that the toolset is registered, so a reader who has just configured it sees it confirmed (`CA_0026_003`).
- The browser gate proves the not-running picture, which is the honest state of a stack with no agent container beside it, and that no runtime row carries the agent's report. What the row says about a credential or a registration is proven where those states can be composed at all (`CA_0026_003`).
- The credential the product cannot issue for itself is offered as the literal command `pnpm run client issue hermes --proposer`, with a control that copies it and the two steps that follow: the token it prints once goes into `.env.dev`, and the agent reads it at its next start. It is the first shell command the product puts in front of its reader, and it is there because the alternative is a step the product cannot take and does not mention (`CA_0026_004`).
- Nothing paraphrases the client name. A run's owner is resolved by the name `hermes`, so a command issued under another name produces a credential the application will not attribute a run to (`CA_0026_004`).
- The copy control says what happened either way. The clipboard is not reachable from a page served over plain HTTP, and a control that silently did nothing would be worse than none (`CA_0026_004`).
- The settings surface re-reads the connections on an interval while something still blocks the agent, and stops as soon as nothing does. The reader's terminal step ends in the agent restarting rather than the application, so nothing else would bring the row to the truth, and a reader coming back from a terminal should not have to guess that a reload is what they owe the page (`CA_0026_005`).
- Memory is not waited on, because it blocks nothing, and a request the reader made or a sign-in already following its own flow is never raced (`CA_0026_005`).
- The gate proves the re-reading happens against a stack whose agent is not running. That it stops needs an agent that becomes ready, which a stack with no subscription cannot offer (`CA_0026_005`).

- [ ] CA_0026_006 Give a status row a state word that is true of it. Every row says `No key` while it is unconfigured, which is the key-taking vocabulary: `hermes`, `codex` and `claude-code` hold no key and never could, so the one word above the agent's report contradicts the report under it. The three status rows want their own words for the four states — the agent's row now says what is missing directly beneath it, so the word above it should say only whether the party is ready.
