# Settings Surface

## The Settings Surface

* Settings is reached from a control in the shell header, which opens settings in a tab.
* The tab is sectioned, `Connections` is the first section, `Channels` is the second, and `People` is the third; `Update` is the fourth, the owner's alone.
* The settings extension contributes a second tab, `Update`, reached from the header's hint and from the settings tab: it shows the installed release, the releases above it worth installing, every release on request, and starts and follows the update. Nobody but the owner sees it.

- The header is already the row for chrome belonging to the instance rather than to any document: the theme toggle, the layout controls, and the process indicator. A settings control is the same kind of thing and takes the same idiom — a transparent icon button that gains a surface on hover.
- Settings opens as a tab so it inherits everything a tab already does, rather than becoming a second kind of place with its own rules. The tab kind, its synthetic target, and the reveal that follows from it are in [Workspace Shell](../../../../../docs/system/workspace/tabs.md).
- Human sign-in is the kernel's (`ui-kernel.md`, `BO_0208_005`), and in prod its public port shows an anonymous browser nothing but sign-in (`BO_0214_009`); the settings tab is reached signed in, like the rest of the shell.
- `People` (since `BO_0209`, 2026-09-08) is who holds authority in this instance, read from the kernel's account routes as the signed-in person on every visit and cached nowhere: each principal's name, kind, class, state, whether it is the owner, when its credential was last used and when its session was last active. The owner's controls — suspend, resume or reactivate, retire, and the move between the class that may establish truth and the class that proposes only — and the form adding a person with an initial password handed over out of band are calls the core refuses on its own terms; a refusal is shown in the section in the core's words with its code, `unlicensed` for a second authority-holding human without a licence and `forbidden` for anyone but the owner. Above the list the section states the active count and the licence: one of one seats and no licence, or the count alone with the licensee and the expiry. Every signed-in person changes their own password with the current one, which signs their other sessions out. Nothing in the section decides anything; a fork that redraws it changes nothing about who may write.
- Themes, layout, and anything else that might later belong in settings are not moved into the tab here. Sections are the extension point, and a section arrives with the change that needs it.
- The agent's row says what Hermes reasons with — *the ChatGPT subscription* or *the API-key model*, with the model's name, whether or not Hermes is the agent running — and offers the switch between them (`PUT /api/x/settings/agent/hermes-model`, which the kernel's agent config takes as `hermesModel`). The API-key model is offered only while one is configured, and the row otherwise says how one is; the kernel refuses it without one rather than writing a choice that would fall back. The agent applies the change when its gateway restarts, so the row says it is switching until the agent's stamp agrees. The row reads Hermes's own loop as signed in when the party it reasons on is — Codex's sign-in on the subscription — rather than looking for a runtime called `hermes` that nothing reports on (`BO_0228_012`).
- A connection row reads as one thing: its party, its state, whether a key is set with its last characters, and one error at a time. A row shows the error from its last test or the error from the request the reader just made, never both.
- The settings view reports no save state and contributes no dock action. A key is saved by a press, not by typing, so there is nothing for the header to say about it.

- `src/components/views/settings.tsx` is the view. It renders the sectioned tab and the `Connections` section, and a row shows the party, what it needs a key for, its state, the last characters when a key is set, and its last error. The component is never handed a secret, so there is nothing in it that could render one (`CA_0021_006`).
- Every request re-reads the row the server answered rather than patching one in the browser, so the surface cannot disagree with what the next read would say. One request is in flight at a time and its row's controls are disabled while it runs (`CA_0021_006`).
- `tests/browser/settings.spec.ts` proves saving a key showing that it is set and its last characters and never the key, a reload showing the same, `Test` with a key the service refuses moving the row to `failing` with the message that came back, `Clear` returning the row to `unconfigured`, and the axe scan clean (`CA_0021_006`).
- The key flow runs on desktop only, while both form factors prove the tab it lives in. Connections are instance-wide, so there is no per-scenario connection the way there is a per-scenario workspace, and two form factors driving the one row at once would be a race rather than a proof. What differs between them is the surface, not what saving a key does, and the store itself is proven against real Postgres (`CA_0021_006`).

## The Update Tab

Under `BO_0223` (the repository's change, 2026-09-09), transferred as `BO_0223_014`–`_016`.

* The release check runs in the owner's browser against GitHub's public release list — `src/lib/releases.ts`, `RELEASES_URL` — and nowhere in the stack; it is on unless `.env` says `CALLIOPA_UPDATE_CHECK=off`, which the kernel relays and the tab says in words. GitHub unreachable is said in words too and never as an error.
* The tab decides nothing the review path would not: the host-side updater runs the install, the proposal it stages is accepted through the kernel's confirmation origin, and the release pin moves through the kernel's promotion gate, as the signed-in owner.
* The shell renders no release body: each release links its GitHub page for the notes.

- The kind is `settings:update`, on the same synthetic instance-wide target as settings, so opening it from the header's hint or from the settings tab reveals the open tab (`src/extensions/settings/contributions.ts`, `BO_0223_014`). The view is `src/extensions/settings/update.tsx`.
- What it shows, read from the kernel's update surface through `src/server/kernel/update.ts` and the routes under `/api/x/settings/update…` (`GET update`, `GET update/proposal`, `POST update`, `POST update/accept`, `POST update/promote`), every one as the signed-in person and refused `forbidden` for anyone but the owner: the installed release and the served pin; the candidates for the installed `M.m.p` — the newest patch of `M.m`, the newest minor of `M`, the newest major, each once under its highest type, with its date and its release-notes link (`src/lib/releases.ts`, `candidates`); *Show all versions*, every release newest first with the installed one marked and an older one offered as a **downgrade** with the sentence that graph content does not roll back with the images; *Check again*.
- Starting the update is one press, *Update to <version>* or *Downgrade to*: the tab posts the version, the kernel writes the request for the host-side updater, and the tab follows `status.json` through the kernel every two seconds — the step and the log tail, the restart during which the kernel stops answering and the tab keeps retrying, the kernel back on the chosen release — then shows the update proposal the install staged with the files it changes (`GET update/proposal`), **Accept the proposal**, which the kernel keeps behind its confirmation origin (the tab links the confirmation and moves on when the proposal is no longer open), and **Promote**, which moves the release pin through the promotion gate; the tab ends on *Serving release <version>*. A failed step, a refused promotion, or a refused request is shown in the kernel's words.
- Where the kernel reports the updater `absent`, the button becomes the three commands to run on the host — `cd ~/calliopa`, `git fetch --tags && git checkout --detach v<version>`, `./install.sh` — and the tab waits for the kernel to come back the same way.
- The settings tab's `Update` section, shown only when the kernel answers the update read (the owner), says the installed release and one line — a newer release, on the newest, the check off, or GitHub unreachable — and opens the Update tab through the view bridge.
- `tests/behavior/update.test.ts` proves, against the kernel harness (`BO_0223_015`): the owner's session marked as the owner and the update read answering the release, the check on, the updater absent and nothing pending; a request refused `updater_absent` and a malformed version `version_invalid`; a second person marked not the owner and refused `forbidden` on every update call. `src/lib/releases.test.ts` proves the candidates over a captured list. The browser walk-through — the hint, the tab from both entries, the fallback commands — is the on-instance verification (`BO_0223_016`), recorded in the repository's `docs/system/ui-shell.md`.
