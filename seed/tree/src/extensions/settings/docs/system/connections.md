# Connections

## Connections

* A connection is a record for one external party.
* Connection states are `unconfigured`, `configured`, `verified`, and `failing`.
* On an instance, a connection's secret lives in the kernel's secret store, encrypted at rest under the kernel's own key (`ui-kernel.md`, `BO_0207_003`). No shell code ever holds a plaintext secret and no API response contains one.
* An API-key connection takes a key that is write-only in the interface. After saving, the row shows that a key is set and its last characters, and never the key.
* A connection can be cleared, which removes the stored secret and returns the state to `unconfigured`.

- The set of connections is application source, not user data. There is no affordance for adding, renaming, or removing a connection, and a party arrives by the change that needs it.
- A platform whose credential is an OAuth token with a refresh lifecycle is not the `apiKey` shape, and the kind it needs is decided by the first adapter that has one.
- Saving the `honcho` key takes effect the next time `pnpm run dev` runs: the application deliberately holds no control over the Docker daemon, so it cannot start the memory service the key turns on. [Application Foundation](../../../../../docs/system/foundation/development-environment.md) carries that profile.
- `honcho` is the one connection this document builds. Its secret is the OpenAI key the agent's memory in [Calliopa Agent](../../../../../docs/system/agent/memory.md) needs, and it is the only secret Calliopa is built to hold at rest.
- The row is seeded `unconfigured` by the migration that creates the table, so the settings surface reads rows rather than inventing them and an empty instance already shows the connection it does not have a key for.
- A connection carries a `kind`. An `apiKey` party takes a secret this store holds; a `status` party takes none and holds only what something else reports about it, which is what the agent's runtimes in [Calliopa Agent](./agent-sign-in.md) are. A status party's secret columns are refused by the database, and its state is read live from what the agent reports rather than stored here.
- Connections are instance-wide. Calliopa has no project or user to scope them to, so the table carries no owner column and gains one when that arrives.
- A connection records its state, the last characters of its secret, when it was last tested, and the error from that test. The masked suffix is stored beside the ciphertext rather than derived on read, so answering the settings surface never decrypts.
- Clearing development data leaves connections untouched, for the reason it leaves API clients untouched: clearing is about content, not about access. `connection` is a preserved table in the classification [Application Foundation](../../../../../docs/system/foundation/development-environment.md) fixes.
- Server code never reads a party's credential at all. Proving a party is the kernel running the party's probe with the stored key; presenting the key to a party is the kernel brokering the request (`POST /__kernel/secrets/parties/<party>/request`), so publishing sends through the kernel and the shell holds nothing to leak. The operator alone reads a value, with `kernel secret read`. `BO_0207_013`
- A party's test is the smallest real authenticated call to it. For `honcho` that is the OpenAI request the key is for; the Honcho service's own health joins the test when that service exists, in [Calliopa Agent](../../../../../docs/system/agent/memory.md).

- `src/lib/connections.ts` names the states and what a connection is outside the kernel's store: a party, a state, whether a key is set, the last characters of it, the last-tested stamp, and the last error, and — since `BO_0202_008` — what the party's descriptor says of it: its label, its purpose, whether it is a channel and the fields it holds, so the settings surface holds no roster of its own. The parties themselves are contributions: the settings extension contributes `honcho`, `hermes`, `codex` and `claude-code`, the publishing extension its channels, and the registry is the roster (`listConnections` reads it; a party nothing contributes any more keeps its kernel record unshown). There is no field a secret could travel in.
- `migrations/0006_connection.sql` creates `connection` keyed by party and seeds the `honcho` row. A check constraint keeps the stored suffix and the ciphertext present or absent together, so a row cannot say a key is set while holding none (`CA_0021_003`).
- `src/extensions/settings/server/connections.ts` is the store over the kernel's party records (`src/server/kernel/client.ts`): listing walks the roster in source so a party the kernel holds nothing for still lists unconfigured, saving hands the key to the kernel together with the party's authorization and probe, clearing removes the record, and proving asks the kernel to run the probe and reads the outcome back. Since `BO_0207_013` the previous store over the `connection` table is gone with its encryption. Before it: listing and reading never decrypted, saving encrypted and recorded the last four characters, clearing left no ciphertext, and recording a test outcome refused a row with no key stored, so an outcome always belonged to a key that was presented. Saving a new key returns the row to `configured` and drops the previous outcome, because what an earlier test said is not about the key stored now (`CA_0021_003`).
- The secrets key is handed to the store the way the SQL client is, so no caller depends on how another reaches it. `secretsKey` reads the one variable it needs rather than the whole application environment, which is validated at server startup and is not available everywhere the store runs (`CA_0021_003`).
- `tests/integration/connections.test.ts` proves against real Postgres that the column holds ciphertext that opens back to what was saved and never the key itself, that a record carries only the last four characters, that the accessor opens a stored key and another key does not, that an empty key is refused with nothing stored, that clearing leaves no ciphertext, that an outcome moves the row to `verified` or to `failing` with the service's message, and that a row with no key is never tested. `tests/integration/db-clear.test.ts` proves a stored key still opens after a clear (`CA_0021_003`).
- `GET /api/x/settings/connections` lists them, `PUT` and `DELETE` on `/api/x/settings/connections/<party>` save and clear a key, and `POST .../<party>/test` proves one. The routes stay thin: `writeConnectionSecret` and `proveConnection` take the SQL client and the key the way the store does, so a route supplies them and a test supplies its own (`CA_0021_004`).
- A party's descriptor holds what proving it means, as data the kernel runs rather than a function the shell runs: each key-holding party's authorization (header, scheme, secret field) and probe (method, URL template naming `{configuration.<key>}`, expected status), handed to the kernel with every save (`BO_0202_008`, once `server/connection-tests.ts`). For `honcho` it is `GET https://api.openai.com/v1/models` presenting the stored key as a bearer, which is the cheapest call that requires the key and changes nothing. `BO_0207_013` A failure answers the service's own message, a transport failure answers the transport's, and either way the row says so rather than reporting success (`CA_0021_004`).
- A service's own words never carry the key back into a row: the message is stripped of the presented secret before it is stored. OpenAI answers a rejected key with `Incorrect API key provided: sk-proj-**********-key`, masked by OpenAI itself, and what a row already shows of a key is its last characters (`CA_0021_004`).
- The API-level coverage proves that no response shape carries the secret or the ciphertext under any state, that a request with no key in it and an unknown party are refused, that a connection with no key is refused rather than tested, and that a key the service will not accept lands as `failing` with what came back and without the key in it. That last one makes the real request; a gate without egress reports the transport's refusal, which is the same proof that a refusal is not swallowed (`CA_0021_004`).


## On A Device

* On a device, the settings extension's connections are where the person enters the keys the apps use: Anthropic, OpenAI and OpenRouter for agent runs, a search vendor, the media vendors that offer a key-based API, and an embedding key. User decisions, 2026-09-30 and 2026-10-01 (`BO_0319`).
- [ ] BO_0319_047 The device's parties: the settings extension contributes `anthropic`, `openai`, `openrouter`, `search` and `embeddings` as API-key parties with their probes (the cheapest authenticated call each), saved through the port into the keystore (`BO_0319_045`); the media parties come from `media` where its vendor offers a key. On an instance these parties are not shown, so nothing changes there. Verified by each key saved, proven against the real API, cleared, and never present in a response.
- [ ] BO_0319_048 The app lock: a setting, off by default, that asks for the device's biometrics or passcode when the app opens or returns from the background, through the host's lock plugin. Shown on a device only.

## Out Of Scope

- The agent layer. No Hermes, no Honcho service, no compose service, no Postgres image change, no tool surface, and no delegation; they are [Calliopa Agent](../../../../../docs/system/agent/calliopa-agent.md).
- Subscription sign-ins. The Claude and Codex credentials never enter this store: the design that works keeps their credential homes on the agent's own data volume and drives the logins from inside the agent container, so a token round-tripped through Postgres would have to be adopted back anyway. Their status rows and the thing that reports them belong to [Calliopa Agent](./agent-sign-in.md).
- Users, roles, and authorization. Connections are instance-wide and the settings surface is unprotected, like the rest of the shell.
- A general settings area, sections beyond `Connections` and `Channels`, and further header controls.
- Adapters, mappings, transports, and anything that publishes. A channel holds a credential and grants no authority to use it; the extension that publishes owns what leaves Calliopa.
- Every channel other than `homepage`. Each arrives with its own change, and the OAuth credential kind arrives with the first platform that needs one — together with the problem that a platform's redirect cannot reach an instance on a Tailscale address.
- Re-encrypting stored secrets under a new key.
