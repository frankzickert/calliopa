# Channels

## Channels

* A channel is a destination the author's work goes to. It is a connection with configuration beside its secret, in the same store — the kernel's, since `BO_0207_013` — under its own settings section.
* The set of channels is application source, not user data. There is no affordance for adding, renaming, or removing one; a channel arrives with the change that needs it, as a connection does.
* A channel holds configuration alongside its secret. The configuration is readable back; the secret never is. A channel whose configuration is absent is `unconfigured` however good its key.
* A channel grants no authority to publish. Holding a credential and using it are separate, and [Publishing](../../../calliopa-video/docs/system/publishing/publishing.md) owns the second.

- A party record says which extension declared it (`BO_0276_002`): `specOf` writes `extension` with every save, from `RegisteredParty.extension`, and `PartyChange` carries it. Only this side knows it, since the registry is where a contribution's owner is recorded, and the kernel keeps it so that a run's tool reaches the party its own extension declared and no other's. A record written before this has no extension and is owned by nobody, which the kernel refuses rather than admits. The kernel's half — the grant a run presents in place of a session, and the refusals — is `calliopa-bootstrap`'s `ui-kernel.md`, A Run Uses What Is Signed In.
- A service row's *Save* writes what was typed and nothing else (`calliopa-bootstrap`'s `BO_0280_009`, `serviceSave` in `src/lib/connections.ts`): the key when a key was typed, the configuration when the party declares fields, and it is not offered when neither was touched. An empty key box is a person who did not touch it, never a person asking for an empty key — sending it either way would clear the credential of anyone who came only to change a field, which is what the row did when fields first appeared on it.
- A service row draws the fields its party declares, as a channel's row does, and saves them with the key (`calliopa-bootstrap`'s `BO_0280_008`). `configurationRefusal` takes, for a service, the keys it fixes and the fields it declares and nothing else; a service that declares neither still takes nothing, which is every service but `evaluation` today. Before this a service could be given a credential and nothing else, so anything the owner had to decide about how a service behaves had nowhere to be decided.
- `evaluation` asks the owner one thing: *Data retention*, `require` or `allow` (`BO_0280_008`). Zero data retention is the provider's guarantee that it keeps nothing it was sent, and it is a paid plan's feature — Vercel answers `403` to a hobby plan asking for it, refusing the whole call — so requiring it unconditionally would not protect the work, it would stop the service running. A record that says nothing asks for the guarantee, because silence is not the owner saying they do not mind.
- `evaluation` is the party of the instance's evaluation service (`calliopa-bootstrap`'s `BO_0280_001`): a `service` party taking an API key, the gateway's root as `fixed` configuration so nothing anyone enters can send the work to another host, and `GET {configuration.address}/credits` as its probe. The probe was measured rather than guessed: `GET /v1/models` answers `200` with no credential at all, so a probe on it would report every key — and no key — as verified. Its row is the whole of the consent: with a key entered, any agent run may ask the model and the material it judges leaves the instance, and clearing the key is how it stops. The kernel holds the credential and makes the call ([UI Kernel](../../../../../docs/system/ui-kernel.md), Evaluation Is A Service); nothing here reads its value.
- A service holds no configuration the reader types, and may still fix its own — the address of the API it is reached at — the way a channel's kind does (`RF_0002_009`, 2026-09-22). `configurationRefusal` in `src/lib/connections.ts` counts only the keys the descriptor does not fix, so a service that declares `fixed` is tested and brokered, and one that declares none takes nothing at all, exactly as before. Without this a service could be given a credential and never be used with it: the save writes a descriptor's `fixed` keys into the record (`specOf`), the row then refused *Test* in words before the kernel was asked, and the kernel's broker refuses a party with no configured address (`no_address`, `internal/kernel/serve/secrets.go`) — so the two rules together left no way for a service to be reached at all. Found when the evaluation party of `calliopa-refine` was saved and *Test* did nothing but say so.

- `bunny` is the second channel: the video host a published film's bytes go to. It holds the numeric id of its Bunny Stream video library beside its key, and proving it lists one video in that library — the smallest real authenticated call, and one that changes nothing. A library name rather than its id is refused where it is typed (`CA_0033_010`).
- `homepage` is the first channel and the only one that change built. It holds the base address of the homepage instance this Calliopa publishes to, and an `hpk_` token presented as `Authorization: Bearer`.
- The address is entered rather than fixed because the instances are separate. There is one homepage on this machine today, the development instance at `http://100.114.122.91:4460`, and homepage carries a production compose file for one that does not yet run; a development Calliopa must be able to point at a development homepage while a production Calliopa points at the real one. A hardcoded address would make a development experiment write to the live site.
- The token is issued by an operator running `pnpm run client` in the homepage repository against its real database. There is no environment-seeded credential and no shared package, so obtaining it is a deliberate act in that repository which Calliopa neither automates nor assumes.
- Proving `homepage` is `GET /v1/contract/author` against the stored address presenting the stored token. That route sits behind homepage's write guard: it answers the author contract with a valid token and homepage's uniform 401 without one, which makes it the smallest real authenticated call to this destination. Confirmed against the running instance on 2026-09-04.
- A channel is instance-wide and its secret is kept by the instance's kernel, so credentials entered in development do not configure production and are entered again there. Publishing to a channel is a brokered request: the transport in `src/server/publishing/client.ts` names the party, the method, the path and the body, and the kernel adds the credential (`BO_0207_013`). `connection` is a preserved table, so a channel's credentials survive `pnpm run db:clear`.
- An OAuth channel is not this shape. The kind it needs, and the problem that a platform's redirect cannot reach an instance answering on a Tailscale address, arrive with the first platform that has one.

- A channel is a party descriptor the publishing extension contributes — `ui.shell`'s server half today, `calliopa-video`'s after `BO_0203` — with kind `channel`, its label and purpose, the fields it holds beside its key and the probe the kernel runs (`BO_0202_008`; [Contribution Contract](../../../../../docs/system/workspace/contribution-contract.md)). The roster is the registry's, so `CHANNEL_PARTIES` and `CHANNEL_CONFIGURATION` no longer exist in `src/lib/connections.ts`; `configurationRefusal` there takes the descriptor and answers in the words a reader is shown, refusing an address that is not absolute `http` or `https` (a field checked as `address`), a value that is not numeric (`numeric`), a field the channel does not have, and configuration offered to a party that takes none. It is a function over plain values, so the rule is proven without a store (`CA_0036_002`, rewritten under `BO_0202_008`).
- `migrations/0013_connection_configuration.sql` adds `configuration jsonb not null default '{}'`, constrains a `status` party to hold none, and seeds the `homepage` row. A channel is an `apiKey` party rather than a third kind: `kind` says how the credential works and the roster says what the row is for, and conflating the two axes would make a channel that signs in differently unrepresentable (`CA_0036_001`).
- `src/server/connections.ts` reads and writes the column without decrypting anything. `saveConnectionConfiguration` trims, refuses through the same rule, and never touches the secret, so an address changes without retyping a token. `withConfiguration` is where a channel that cannot be reached yet becomes `unconfigured` whatever its key, laid over the stored state at read time for the reason a status row's state is: a second copy of a derivable fact is a copy that can disagree (`CA_0036_001`).
- `writeConnectionSecret` takes both halves and writes the configuration first, so a request carrying both leaves a row that is wholly the new one or wholly the old — a refused address never lands beside a key that was accepted. A request carrying neither is refused, and a configuration value that is not text is refused before any row is touched (`CA_0036_004`).
- The `homepage` descriptor's probe proves it with `GET /v1/contract/author` against the stored address presenting the stored token (once `src/server/connection-tests.ts`, now the descriptor `ui.shell` contributes, `BO_0202_008`). Homepage answers a refusal as `{error:{code,message}}`, which is the shape `errorFrom` already read, so the destination's own words reach the row unchanged. `proveConnection` refuses a channel whose configuration is incomplete rather than reporting it as failing, for the reason a row with no key is refused: nothing was refused (`CA_0036_003`).
- `src/components/views/settings.tsx` renders `Channels` below `Connections`, each row carrying its configuration fields, its write-only key field, and `Save`, `Test` and `Clear`. A field the reader has not touched shows the stored value, so an address is readable back while the key beside it is never rendered at all (`CA_0036_005`).
- `src/lib/connections.test.ts` covers the refusal rule over plain values. `tests/integration/connections.test.ts` proves against real Postgres that configuration round-trips, that a refused address stores nothing, that a key with no address is `unconfigured` and says why, that no answered shape carries the secret while it does carry the address, that a channel with no address is refused rather than tested, and that saving only an address leaves a stored key alone. The shape assertion enumerates the record's keys, so a field added later has to be admitted deliberately rather than arriving unnoticed (`CA_0036_001`, `CA_0036_002`, `CA_0036_004`).
- `tests/browser/settings.spec.ts` proves the section against the real application and the real destination: an address and a key saved, a reload showing the address and the masked key and never the key, an address that is not one refused with nothing stored, a key homepage will not accept landing as `failing` with what came back, clearing, and a clean axe scan (`CA_0036_005`).
- The whole path was exercised against the running homepage on 2026-09-04: the address stored and read back, the key stored showing only its last characters, a real request to `/v1/contract/author`, and homepage's own `A valid publishing credential is required.` recorded on the row. What a credential homepage accepts does is not proven here and could not be — issuing one is a deliberate act in that repository, and this instance holds no account there (`CA_0036_003`).

## Channels As Data

* Since the `publishing` extension (`PU_0001`), a channel is data the author creates from the library's Channels category — a kind and a title — with its credential and configuration in the kernel's secret store under `publishing-<channelId>`; the Channels section here is where that credential is entered, tested and cleared. The channel's own tab holds no credential field and links here. User decision, 2026-09-14 (`CA_0049`); the channel's side is [Channels](../../../publishing/docs/system/channels/channels.md).
* The section lists one row per channel node beside the parties the build contributes: the kind's fields, its write-only key, *Save*, *Test* and *Clear*, exactly as a contributed channel's row.
* A party whose credential kind is `oauth` has a row of its own shape: the provider's client id and client secret as its fields, *Sign in* in place of a key — the row shows the user code and the verification URL the kernel answered while the flow is `awaiting`, and the state after — and *Test* and *Clear* as any row. User decision, 2026-09-15 (`BO_0252`).
- `settings.tsx` draws an oauth party's row with *Client secret* in place of *Key*, *Sign in* (withheld while a flow is `awaiting`, *Sign in again* once verified), the code and the verification link while `awaiting`, *signed in* or *sign-in failed: <reason>* beside the state, and *Test* only once signed in; the view re-reads its rows every three seconds while any flow is `awaiting`. `server/connections.ts` writes the descriptor's `provider`, `paths` and `fixed` configuration with every save (`specOf`), takes the client secret as the oauth party's one typed secret (`secretFieldOf`), answers `flow` on the record, refuses *Test* until the flow is `verified`, and `startSignIn` behind `POST /api/x/settings/connections/<party>/sign-in` writes the spec and starts the kernel's flow; `configurationRefusal` in `src/lib/connections.ts` ignores a kind's fixed keys. The flow itself is the kernel's and proven there (`BO_0252_005`) and through the shell client (`BO_0252_006`); a row of this kind is drawn once a kind of credential `oauth` exists (`PU_0005`) (`BO_0252_007`). The row is labelled by the channel's title with its kind's label beside it, so two channels of one kind read as two rows. A channel that was deleted has no row on the next read.
- The roster is read, not contributed: `publishing` answers its descriptors through the shell's party roster contribution (`CA_0049_001`), one per `channel` node, and the registry's build-time roster is unchanged. An instance whose tree holds no `publishing` lists no such rows, and one whose graph holds no channel lists none either.
- The set of contributed channels is still application source; what this section adds is the rows for channels the author made. A static channel — `homepage` and `bunny`, contributed by `calliopa-video` — lists only while that extension is present in the tree, as before.
- The channel tab's *Open Settings* opens the settings tab; the row is found by the channel's title. Revealing the row itself — scrolling to it, marking it — is a nicety this change does not build.

- `listConnections` and `assertParty` in `src/extensions/settings/server/connections.ts` read the shell's async roster, so a channel's party saves, tests and clears through the same routes as a contributed one (`PUT`, `POST …/test`, `DELETE` on `/api/x/settings/connections/<party>`), the descriptor's authorization and probe handed to the kernel with every save as before; the listing orders the contributed parties by credential kind then id and the rosters' rows after them by label; `asRecord` carries the channel's title as the row's label and the kind's purpose beneath it, so `settings.tsx` renders the row unchanged. A party is a roster's rather than the build's when its id is namespaced by its extension (`CA_0049_003`).
- The rows a channel adds are proven from the channel's side, in `publishing`'s `tests/behavior/roster.test.ts` ([Channels](../../../publishing/docs/system/channels/channels.md)); this extension's `tests/behavior/parties.test.ts` proves the contributed parties alone, the listing naming them unconfigured and a key-less party's proof refused. `src/registry.test.ts` proves the merge's rules. The surface was walked on the served build with a channel's row (`CA_0049_004`).
- The release-notes line is under *Added* in `calliopa-bootstrap`'s `docs/release-notes/unreleased.md` (`CA_0049_005`).

### Without Publishing

Transferred from `CA_0051` on 2026-09-17. `0.3.9` bundled `publishing`, which an owner may switch off, and every install that did had its promotion refused at the typecheck: `tests/behavior/parties.test.ts` imports `createChannel`, `deleteChannel`, `partyOf` and `readChannel` from `~/extensions/publishing/server/channels`. The section's code already reads the dynamic rows through the roster contribution and lists none without `publishing`; only the test reaches into it. The same pair of fixes ships alone as release `0.3.11` (user decision, 2026-09-17), and the check that keeps it from returning is `BO_0260` in `calliopa-bootstrap`.

* `settings` imports nothing from `publishing`, in its code or its tests: an instance with `publishing` switched off builds, typechecks and serves.
- `publishing` depends on `settings`, so the proof of a channel's row lives with the channel, in `publishing`'s tests, and reaches `settings`' connection functions the permitted way.

- `tests/behavior/parties.test.ts` imports nothing from `publishing` (`CA_0051_001`, 2026-09-17): it keeps its two tests of the contributed parties, and its channel block moved unchanged into `publishing`'s `tests/behavior/roster.test.ts`.
- Verified on the tree (`CA_0051_003`), 2026-09-17, at dataRevision 36: the behavior project over the kernel harness (`TestShellDocumentsOverCCGW`, a real kernel over a scratch CCGW) passed 108 tests in 23 files, `parties.test.ts` (2) and `roster.test.ts` (3) among them; `pnpm run typecheck` is clean and the unit project passes (821). A copy of the tree without `publishing` and the four `individual` extensions, through `kernel toolchain install` and `kernel toolchain build`, failed before the split on `parties.test.ts(5,68)` and builds after it; without `documents` as well it builds too.
- Walked on the dev instance (`CA_0051_003`), 2026-09-17, the change served at pin 41: `kernel extension deactivate publishing` promoted pin 43, whose served tree holds `calliopa-base`, `calliopa-extension`, `documents`, `settings` and `ui.shell` and no `publishing`, so the library's categories are *Documents* and *Extensions* alone; `kernel extension activate publishing` promoted pin 45, serving it again. On `0.3.10` the same deactivation was refused at the typecheck. A second person could not be signed in to look at the page (the instance's licence covers one human), so the library was read from the served tree's contributions.
- The release-notes line is under *Fixed* in `calliopa-bootstrap`'s `docs/release-notes/unreleased.md` (`CA_0051_004`).
