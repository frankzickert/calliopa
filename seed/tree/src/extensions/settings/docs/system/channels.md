# Channels

## Channels

* A channel is a destination the author's work goes to. It is a connection with configuration beside its secret, in the same store — the kernel's, since `BO_0207_013` — under its own settings section.
* The set of channels is application source, not user data. There is no affordance for adding, renaming, or removing one; a channel arrives with the change that needs it, as a connection does.
* A channel holds configuration alongside its secret. The configuration is readable back; the secret never is. A channel whose configuration is absent is `unconfigured` however good its key.
* A channel grants no authority to publish. Holding a credential and using it are separate, and [Publishing](../../../calliopa-video/docs/system/publishing/publishing.md) owns the second.

- `bunny` is the second channel: the video host a published film's bytes go to. It holds the numeric id of its Bunny Stream video library beside its key, and proving it lists one video in that library — the smallest real authenticated call, and one that changes nothing. A library name rather than its id is refused where it is typed (`CA_0033_010`).
- `homepage` is the first channel and the only one that change built. It holds the base address of the homepage instance this Calliopa publishes to, and an `hpk_` token presented as `Authorization: Bearer`.
- The address is entered rather than fixed because the instances are separate. There is one homepage on this machine today, the development instance at `http://100.114.122.91:4460`, and homepage carries a production compose file for one that does not yet run; a development Calliopa must be able to point at a development homepage while a production Calliopa points at the real one. A hardcoded address would make a development experiment write to the live site.
- The token is issued by an operator running `pnpm run client` in the homepage repository against its real database. There is no environment-seeded credential and no shared package, so obtaining it is a deliberate act in that repository which Calliopa neither automates nor assumes.
- Proving `homepage` is `GET /v1/contract/author` against the stored address presenting the stored token. That route sits behind homepage's write guard: it answers the author contract with a valid token and homepage's uniform 401 without one, which makes it the smallest real authenticated call to this destination. Confirmed against the running instance on 2026-09-04.
- A channel is instance-wide and its secret is kept by the instance's kernel, so credentials entered in development do not configure production and are entered again there. Publishing to a channel is a brokered request: the transport in `src/server/publishing/client.ts` names the party, the method, the path and the body, and the kernel adds the credential (`BO_0207_013`). `connection` is a preserved table, so a channel's credentials survive `pnpm run db:clear`.
- An OAuth channel is not this shape. The kind it needs, and the problem that a platform's redirect cannot reach an instance answering on a Tailscale address, arrive with the first platform that has one.

- A channel is a party descriptor the publishing extension contributes — `ui.shell`'s server half today, `calliopa-video`'s after `BO_0203` — with kind `channel`, its label and purpose, the fields it holds beside its key and the probe the kernel runs (`BO_0202_008`; [Contribution Contract](../../../../../docs/system/workspace/contribution-contract.md)). The roster is the registry's, so `CHANNEL_PARTIES` and `CHANNEL_CONFIGURATION` no longer exist in `src/lib/connections.ts`; `configurationRefusal` there takes the descriptor and answers in the words a reader is shown, refusing an address that is not absolute `http` or `https` (a field checked as `address`), a value that is not numeric (`numeric`), a field the channel does not have, and configuration offered to a party that takes none. It is a function over plain values, so the rule is proven without a store (`CA_0036_002`, rewritten under `BO_0202_008`).
- `migrations/0013_connection_configuration.sql` adds `configuration jsonb not null default '{}'`, constrains a `status` party to hold none, and seeds the `homepage` row. A channel is an `apiKey` party rather than a third kind: `kind` says how the credential works and the roster says what the row is for, and conflating the two axes would make a channel that signs in differently unrepresentable (`CA_0036_001`).
- `src/server/connections.ts` reads and writes the column without decrypting anything. `saveConnectionConfiguration` trims, refuses through the same rule, and never touches the secret, so an address changes without retyping a token. `withConfiguration` is where a channel that cannot be reached yet becomes `unconfigured` whatever its key, laid over the stored state at read time for the reason a status row's state is: a second copy of a derivable fact is a copy that can disagree (`CA_0036_001`).
- `writeConnectionSecret` takes both halves and writes the configuration first, so a request carrying both leaves a row that is wholly the new one or wholly the old — a refused address never lands beside a key that was accepted. A request carrying neither is refused, and a configuration value that is not text is refused before any row is touched (`CA_0036_004`).
- The `homepage` descriptor's probe proves it with `GET /v1/contract/author` against the stored address presenting the stored token (once `src/server/connection-tests.ts`, now the descriptor `ui.shell` contributes, `BO_0202_008`). Homepage answers a refusal as `{error:{code,message}}`, which is the shape `errorFrom` already read, so the destination's own words reach the row unchanged. `proveConnection` refuses a channel whose configuration is incomplete rather than reporting it as failing, for the reason a row with no key is refused: nothing was refused (`CA_0036_003`).
- `src/components/views/settings.tsx` renders `Channels` below `Connections`, each row carrying its configuration fields, its write-only key field, and `Save`, `Test` and `Clear`. A field the reader has not touched shows the stored value, so an address is readable back while the key beside it is never rendered at all (`CA_0036_005`).
- `src/lib/connections.test.ts` covers the refusal rule over plain values. `tests/integration/connections.test.ts` proves against real Postgres that configuration round-trips, that a refused address stores nothing, that a key with no address is `unconfigured` and says why, that no answered shape carries the secret while it does carry the address, that a channel with no address is refused rather than tested, and that saving only an address leaves a stored key alone. The shape assertion enumerates the record's keys, so a field added later has to be admitted deliberately rather than arriving unnoticed (`CA_0036_001`, `CA_0036_002`, `CA_0036_004`).
- `tests/browser/settings.spec.ts` proves the section against the real application and the real destination: an address and a key saved, a reload showing the address and the masked key and never the key, an address that is not one refused with nothing stored, a key homepage will not accept landing as `failing` with what came back, clearing, and a clean axe scan (`CA_0036_005`).
- The whole path was exercised against the running homepage on 2026-09-04: the address stored and read back, the key stored showing only its last characters, a real request to `/v1/contract/author`, and homepage's own `A valid publishing credential is required.` recorded on the row. What a credential homepage accepts does is not proven here and could not be — issuing one is a deliberate act in that repository, and this instance holds no account there (`CA_0036_003`).
