# BO_0320_FEAT_codex-image-generation

Status: rejected

## Summary

Build on `BO_0312_FEAT_formats-replace-manuscripts-and-publishing.md`: add Codex image generation as an option of `media.generate`. When a person sets up an image profile, they can choose Codex alongside the existing generation backends. The user chooses the format and the backend; the profile guides generation, and the resulting image is returned for review.

## What Is Asked

- **Answered BO_0320_Q1:** Codex generation is selected as the backend in an image profile; it is an option of `media.generate`, alongside the existing generation backends. It does not replace `media.generate` or the other backends.
- **Answered BO_0320_Q2:** The Codex option reuses the Codex credentials already entered in Calliopa. It does not require separate credentials or sign-in in Media.
- **Answered BO_0320_Q3:** Codex generation may proceed on Send without a quote. Calliopa indicates the cost is unavailable; it does not ask for a second confirmation.
- **Answered BO_0320_Q4:** Save the backend as structured profile data selected during profile setup; written instructions do not select it.
- **Answered BO_0320_Q5:** An image-generation profile has an explicit type, and that type reveals the backend selector.
- **Answered BO_0320_Q6:** Hide and deactivate Codex in the app. Do not change to a separate
  `OPENAI_API_KEY` route. Preserve saved profile values and refuse their generation without
  fallback because the current Codex sign-in route cannot generate images.

## Closure

Rejected on 2026-10-01 at the user's direction. The current Codex app-server sign-in route does
not support image generation; repeated dev Sends returned no PNG. The user directed Calliopa to
hide Codex and refuse saved Codex profiles without fallback, and declined changing to an API-key
route. The implementation and verification tasks that depend on producing an image cannot be
completed through this route. The app deactivation is deployed and documented; this change makes
no claim that Codex image generation works.
## Context

- The fixed-layer media service already supports image generation and returns generated bytes to the `media` extension.
- `BO_0312` already says image and video are user-authored profiles, a person chooses the format, and a Send-started run can make paid generation through `media.generate`. It proposes Higgsfield and OpenArt as current backends; this change adds Codex as another selectable backend for image generation.
- The media service currently owns the Higgsfield and OpenArt credentials. The Codex `media.generate` option reuses the Codex credentials already entered in Calliopa.
- The current headless Codex route has repeatedly returned no PNG. OpenAI documents image generation as unsupported through Codex app-server with Sign in with ChatGPT. At the user's direction, the option is hidden and blocked in the app and the change is closed as rejected. [Sign in with ChatGPT preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations).

## Acceptance Examples

- Given an image profile whose backend is Codex and an existing Codex sign-in, when the user sends
  a block with that profile, the Codex image-generation option produces one image through
  `media.generate`, preserves the format the user chose, and returns the result for review.
- Given an image profile whose backend is Codex and no usable Codex sign-in, when a user sends a
  block, generation is not submitted and the user receives an actionable authentication error.
- Given a run that was not started by a person's Send, when it calls `media.generate` with the
  Codex backend, the existing spending gate refuses it before Codex is invoked.
